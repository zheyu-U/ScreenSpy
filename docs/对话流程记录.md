# 会话压缩摘要（ScreenSpy 项目）

## 三、M0 关键结论（已验证，含客观证据）

**决策链**：先试"真嵌入"（路线 A）→ **失败** → 求证 Rainmeter 源码 → **放弃嵌入，改为路线 B+**。

### 路线 A 失败（真嵌入 WorkerW/Progman 子窗口）
- 表现：窗口**从未上屏**，但所有 API 全绿（`SetParent` 成功、`GA_ROOT==Progman`、`IsWindowVisible=true`、`UpdateLayeredWindow` 返回 true）——**假阳性**。
- 证据：7 个纯色探针 + 截屏像素判定 → 唯一可见的是**顶层对照探针 P0**；所有子窗口探针 0 像素（分层/不透明、WorkerW/Progman 各种组合皆然）。
- 根因：`Progman` 扩展样式含 **`WS_EX_NOREDIRECTIONBITMAP`**，由 **DirectComposition** 呈现；**第三方子 HWND 不在其合成树内 → 永不上屏**。`DWMWA_CLOAKED` 全为 0（不是遮盖）。
- 附带：26H2 上 `SHELLDLL_DefView` **直接是 `Progman` 子窗口**；壁纸层是 `Progman` 的全屏子 `WorkerW`；**不存在**文档 §5.8 说的顶层同级 `WorkerW`（顶层 17 个 `WorkerW` 全是 170×47 无关窗口）。

### Rainmeter 求证（决定性）
**Rainmeter 根本不用 `SetParent`（0 次调用）**，它就是**顶层窗口 + `HWND_BOTTOM` + z 序自锁 + 显示桌面检测/复位**。凭此扛住 Win+D —— **不是阻止最小化，而是发现桌面被抬起就把自己插回桌面之上。**

### 路线 B+ 最终方案（已实测通过）
| 机制 | 落地 |
|---|---|
| z 序自锁 | `WM_WINDOWPOSCHANGING` → `flags \|= SWP_NOZORDER` |
| 隐藏探针窗口 | 用于 z 序探测（`HWND_BOTTOM`，不建表面） |
| 显示桌面检测 | **`显示桌面 ⟺ HostZ < ProbeZ`**（桌面宿主跑到探针之前） |
| 复位 | 正常→`HWND_BOTTOM`；显示桌面→`TOPMOST` 后 `NOTOPMOST`（插到 topmost 带之下） |
| 事件加速 | `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)` |
| 采样密度 | 250ms ⇄ 显示桌面期间 100ms |
| 窗口样式 | `WS_POPUP` + `WS_EX_LAYERED\|TRANSPARENT\|NOACTIVATE\|TOOLWINDOW` |

**验证结果（两轮一致）**：S1 正常 576px → **S2 Win+D 仍 576px（`IsIconic=False`，HostZ 161→15）** → S3 还原一致 → S4 被覆盖 0px → S5 恢复 576px。**三项需求全部达成**：在桌面 ✅、会被窗口覆盖 ✅、Win+D 不最小化 ✅（另有鼠标穿透、任务栏/Alt+Tab 隐藏、无残影，均客观判定通过）。

## 四、可复用教训（9 条，重点 4）
1. **API 全绿 ≠ 像素上屏**——判据必须落到像素/命中测试。
2. **不要嵌入桌面树**（26H2 是 DComp 呈现，第三方子窗口不上屏）。
3. **Win+D 免疫的正解是 z 序复位，而非阻止最小化**。
4. **不要用"读源码推断"替代"实测"**——照抄的判据极性是错的，靠实测纠正。
5. 判定嵌入**不能用 `GetParent`**（带 `WS_POPUP` 时返回 owner）→ 用 `GetAncestor`。
6. `SetParent` 不会自动把 `WS_POPUP` 改 `WS_CHILD`。
7. `WindowFromPoint` 不可靠（否决）。
8. 像素判定必须先校验"桌面是否可见"（首次截屏被 VS 遮挡，结论无效）。
9. 26H2 `0x052C` 仍有效但**先查找、找不到才注入**；注入会新增壁纸 `WorkerW`，注销/重启 Explorer 回收。

## 三、当日最关键的几个认识

1. **API 全绿 ≠ 像素上屏。** 路线 A 的自动检测“全绿”，屏幕上却什么都没有；引入截屏像素判定后才定性为**假阳性**。此后本项目所有“是否真的显示了”都只认像素。
2. **不要嵌入桌面树。** 26H2 上 `Progman` 带 `WS_EX_NOREDIRECTIONBITMAP`（DirectComposition），第三方 `SetParent` 进去的子窗口不上屏；Rainmeter 这类成熟工具也**从不嵌入**。
3. **Win+D 免疫的正确解法是 z 序复位。** 卡片并未被最小化（`IsIconic` 始终 False），只是被抬起的桌面**盖住**；检测到“显示桌面”就把卡片插回桌面之上即可。
4. **（M1）自检的“前提”本身可能掩盖缺陷。** 调度器 bug（`Ticked?.Invoke(ProcessHeartbeat())` 在**无人订阅事件**时实参根本不求值 → 心跳完全不执行）之所以躲过自检，只因自检**恰好订阅了事件**；回归用例必须刻意覆盖退化配置（无订阅者）。
5. **（M2）结构体布局不能靠文档推断，还要问“换个环境会怎样”。** `WTSINFOEX.SessionId` 实测在偏移 **8**（`Level` 后有 4 字节填充），硬编码偏移会静默读错；更隐蔽的是「会话号为 1」时错位命中的「伪头部」恰好**看起来完全合法**——本机（会话号 2）**永远测不出来**，只能靠对抗性构造用例发现。
6. **（M4）事件顺序会决定“能不能拿到数据”。** 调度器跨天时**先** `DayRolled`（榜单被清空）**后** `Ticked`，而 C# 事件按**订阅顺序**调用 —— 于是“到点去读一眼内存榜单再写库”这种看似自然的写法，会在午夜**永久丢掉昨天的尾段**。凡是要持久化的订阅者，都应**自己按拍携带的日期累加**，不依赖别人的内存状态。

7. **（M5a）“能启动”与“看得见在启动”是两件事。** 把采集链路接进产品启动流程之后，如果界面仍是空白模板，就只能靠翻库文件去确认到底有没有生效；把状态做成**可见面板**，才让“接线是否成功”从“需要考古”变成**一秒内可判断**。

8. **（M5b）不要用语义模糊的便捷属性去判定状态。** `Process.MainWindowHandle` 在同一次运行里先报 0、后报非零（它会挑“当前可见的顶层窗口”）；改成 `EnumWindows` 直接列出全部顶层窗口后，结果 2/2 稳定。

9. **（M6）派生值不能是“等着别人来填”的字段。** `TodayTotal` 第一版由组合根赋值，自检立刻发现**手工构造的快照会得到 `0:00`**；改成**计算属性**后，从结构上消除了“漏填且不报错”。同理，**对外展示口径与守恒口径必须分开命名**（`TodayTotal` vs `TodayActive`），否则改一处会同时破坏界面与恒等式。

## M9-1 决策（D52–D58，2026-10-06）

| 编号 | 决策 | 选择 | 影响 / 理由 |
|---|---|---|---|
| D52 | 用户面的“分类”含义 | **多个进程合并成一个软件** + **自定义分类（以软件为最小单元）** | 需要“软件身份表 + 分类表”；限额将来可挂软件或分类 |
| D53 | 一个软件落在多个分类下 | **A 单选**：一个软件只属于一个分类 | `各分类之和 == 各软件之和` 精确成立，分类限额可对账、可相加 |
| D54 | 总限额口径（M9-2） | **今日真实活跃**（`TodayTotal`） | 与主界面大字号、卡片、托盘同一个数 |
| D55 | 提醒技术路线 | **先用托盘气泡**，之后可升级 Toast | 零新增依赖、无需 AUMID/快捷方式；发送抽成接口，换实现不动引擎 |
| D56 | 阈值判定时机 | **每秒判定 + 阈值可配置** | 及时（≤1 秒）、与界面数字同源；去重按 (日期, scope, target, 阈值) 落库 |
| D57 | 合并后已有历史 | **清空全部历史，从今天重新开始** | 身份口径变了；`settings` / `limits` 保留。**唯一一次会删数据的迁移** |
| D58 | 实施顺序 | **先身份层（M9-1），再限额（M9-2）** | 限额与分类都挂在软件键上；先做限额则合并上线要迁移限额条目 |

### 当时最关键的几个认识

1. **“同一个软件多个进程名”是限额的隐形杀手**：限额若挂在原始进程名上，
   合并前设置的单软件限额只会统计到一部分 —— **不报错、只是永远不触发或提前触发**。
   所以身份层必须**先于**限额落地。
2. **合并是三处一起改**（库内行 + 内存榜单 + 待写增量），少一处今天就会多出一条账。
   而且内存侧**必须把“基线”一起搬**：只搬毫秒会让“今天一整天”丢掉合并前那部分历史。
3. **“清空历史”换来了实现的简单与一致**，代价是合并不可拆分。
   但**原始活动日志（JSONL）仍在**，追溯能力没有丢 —— 这是“聚合层可简化、证据层不简化”的分工。
4. **`ActivityScheduler.Pump()` 与 `Sample()` 行为不一致**（`Sample()` 会建立当日基准，`Pump()` 不会）：
   于是“先 `Seed` 基线、再 `Pump`”会触发一次跨天翻页把基线冲掉。
   生产代码先 `Start()` 所以不受影响，但**自检装置必须先 Start/Stop 建立基准**。
   这是一个值得记录的“手动入口与正式入口行为不一致”陷阱。
5. **可交互的界面区域不能跟着每秒刷新重建**：否则用户正在打开的下拉框会被销毁，
   表现为“点了没反应”—— 正是本项目最忌讳的“看起来能用、其实不能用”。

## M9-1b 决策（D59–D62，2026-10-06）

| 编号 | 决策 | 选择 | 影响 / 理由 |
|---|---|---|---|
| D59 | 软件名称自定义 | 新增功能：用户可把软件的**显示名**改成自己习惯的名字 | **只改显示名，不改归一键**；改键会把统计拆成两半（正是 M9-1 要消灭的那类“静默少计”） |
| D60 | 改名入口形态 | **弹对话框**（预填当前名；保存 / 恢复默认名 / 取消） | 比行内编辑安全：确认后才落库，取消不留痕 |
| D61 | 重名规则 | **禁止重名**：候选名与“别的软件现在会显示的名字”冲突时拒写 | 否则榜单 / Top 里出现两个同名行，用户无法分辨谁是谁 |
| D62 | 重名的比对范围 | ① 别的软件**用户设过的名字** ② 别的软件的**当前显示名** ③ **系统友好名表的全部默认名** | ③ 挡住“把 chrome 改名叫 Visual Studio”，**即使 VS 今天一次都没运行过** |

### 当时最关键的几个认识

1. **“自定义名称”必须落在显示层，不能落在身份层**：库里只存软件身份（归一键），
   显示名在**读取时**按身份层现算 —— 于是改名**对所有日期立即生效**，不需要回填历史。
2. **两处刻意的不对称**（都是为了不把用户卡死，不是漏洞）：
   本来就是默认名时点「恢复默认名」是**空操作**、一律放行；
   恢复默认名只与别人的**自定义名**比，**不**与别人的默认名比
   —— 因为名字表本身就有两个键共用“计算器”（`calc` / `CalculatorApp`），那是名字表的账；
   若不做后一条，`calc` 会陷入“想恢复默认名却被拒绝”的死角。
3. **改名要四处一起生效**：身份层（今后采样 + 重启续算）/ 内存榜单（现在）/ 卡片“当前软件”（现在，
   不必等它再次成为前台）/ 界面列表。少第 3 处就会出现“改了名但卡片还是旧名”这种不报错的错
   —— 与合并那次同构。
4. **冲突时一个字都不写库**：改名是“全有或全无”，不是“能写多少写多少”。
   所以重名闸门必须在**写库之前**，而不是界面上拦一下。
5. **纯函数 + 组合根双层回归**：规则放在 `AppNamingRules`（可被自检穷举），
   但另加 **E 组**启动**真实 `ProductRuntime`** 验证“成功 / 重名被拒”两条路径 ——
   针对的正是本项目栽过两次的形态：**函数写对了，但组合根没接上**。

## 六、M9-2 决策与关键认识（2026-10-06）

### 决策（D63–D69）

| 编号 | 决策 | 要点 |
|------|------|------|
| **D63** | 总限额比 **`TodayTotal`** | 与主界面大字号 / 托盘 tooltip / 卡片**同一个数**；另算一套必然出现「限额说超了、大字号看着没超」 |
| **D64** | 提醒先用**托盘气泡** | 零依赖、零 AUMID 注册；发送动作集中在 `TrayIconHost.ShowNotification` **一处** → 将来换真 Toast 不动引擎 / 组合根 / 界面 |
| **D65** | 判定**旁听心跳**（每秒）；阈值可配置 | 挂在 `AppUsageBridge.Observed` 上（与归属同节拍）；设置键 `limit_thresholds`（默认 `80,100`）；没有限额时直接返回（零成本） |
| **D66** | 一次跨两档**只提醒最高那档** | 从 70% 涨到 110% 只弹「已达到」，不连弹两条 |
| **D67** | 去重键 **带日期 + 阈值千分比** | 键形如 `notified|2026-10-06|total||800`；跨天自动重置（无需清标记的定时任务）；千分比整数避免小数格式漂移 |
| **D68** | 改限额 / 改阈值时**清掉今天的标记** | 否则「把限额调低却再也不提醒」，用户会以为功能坏了 |
| **D69** | 存储不可用时**内存去重兜底**；卡片取**最紧急**那条 | 降级时本次运行内仍只提醒一次（绝不刷屏）；卡片只有一根条，放最接近上限的那条才有意义 |

### 关键认识

1. **「提醒」必须与「展示」同源**：限额比的是哪一个数，决定了用户会不会看到两个互相打架的数字 ——
   这与第 16 条教训是同一件事，只是这次发生在“阈值”这一侧。
2. **去重键的编码方式本身就是契约**：用**千分比整数**而不是小数字符串，是因为小数格式会随区域性 / 版本漂移；
   一旦漂移，去重会**静默失效**（表现为每秒弹一条，用户只会以为程序坏了）。
3. **降级路径也要有“不刷屏”的底**：存储不可用时若只依赖落库去重，就会退化成每拍提醒一次；
   内存兜底是**几行代码换一个不会伤害用户的降级**。
4. **判定挂在心跳上，而不是自己起定时器**：与归属同一个节拍，两个数字天然同步；
   且“没有限额时零成本”让这个功能的常态开销为 0。
5. **纯逻辑 / 守门分层再一次奏效**：41 + 20 项断言里绝大多数是“阈值边界 / 只取最高档 / 去重键字面量”
   这类人工几乎无法稳定复现的规则 —— 它们在纯逻辑里被逐条钉死；只有副作用（落库 / 事件）留在守门里。

## M10 决策（D70–D73）

| 决策 | 内容 | 理由 |
|------|------|------|
| **D70** | 近 7 天柱状图的每根柱 = **当天「真实活跃」总量** | 与主界面大字、卡片、托盘**同口径**；若只算已归因软件，柱子会小于大字，用户必然问「为什么和大字对不上」 |
| **D71** | 「今天」那根**只读库**（不掺内存实时口径） | 用户选择：7 根柱完全同源、逻辑最简；代价是最多滞后约 15 秒 —— 因此**必须把代价写到界面上**（说明文字里明说），而不是藏在代码里 |
| **D72** | 维度支持 **总量 / 软件 / 分类** 三者切换 | 用户选择的最全一档；软件候选来自**近 7 天的库**（与图只读库一致，避免「能选却是空图」），分类候选取自身份层 |
| **D73** | 绘制用**零新依赖的纯 WPF**，但把**口径与几何做成纯逻辑**、绘制单独一层 | 用户说「以后要重新做 UI，你看怎样合适」→ 把这句话当成**设计约束**：换 UI 只替换 `Charts/BarChartView`，`ChartBuilder`（口径）与 `BarChartLayout`（几何）及其断言原样保留 |
| **M8 余项** | **不再考虑** | 用户决定（2026-10-06）：相对锚点 / 分辨率换算不做 |

### M10 的关键认识

1. **「以后要重做 UI」是一条可以立刻兑现的设计输入**：把它当成约束的结果是「口径与几何纯逻辑 + 绘制单层」。若忽略它，那套「多少秒算多高」会写在控件代码里，重做 UI 时被重写一遍 —— 于是「图看起来对、数字悄悄变了」会重新出现。
2. **「只读库」这类取舍的代价要写在界面上**：同一个数字可以滞后，但不能不说。图表下方的说明文字显式写明「已落库数据、最多滞后约 15 秒」。
3. **「那天没记录」和「那天这个软件没用过」必须分开**：前者是空槽（`—`），后者是 `0:00`。合并成一种显示，就等于把「没开机」说成「用了 0 秒」。
4. **组合根的「现取」与「缓存」只差一个写法，后果是「永远停在旧名」**：图表标题要跟着改名 / 合并变，所以显示名与分类用**委托现取**，并在自检里专门钉一条「改完名立刻读图」。
5. **自检首跑的 3 项 FAIL 全是我自己的断言写错**（用 0 柱模型断言「无历史记录」、断言标题含进程名而实际用友好名、把非软件 300 秒误算进分类维度）：这说明这批断言真的在跑，而不是照实现抄一遍。**断言写错的成本，远低于「断言根本没跑」的成本。**

## M11 决策（D74–D77）

| 决策 | 内容 | 理由 |
|------|------|------|
| **D74** | UWP 真实应用名的来源取**子窗口进程名 + 扩展友好名表**（不改目标框架、不引入 WinRT 投影） | 用户选择。备选「再加窗口标题作显示名」会让名字在**重启续算时拿不到依据而跳变**（要一致就得把检测到的名字写进 `app_meta`，等于系统替你设一个「自定义名」）；备选 WinRT 包信息最准，但要把 TFM 改为 `net10.0-windows10.0.19041.0`，属工程配置变更 |
| **D75** | 旧的 `app_name='applicationframehost'` 历史行**保留**并改标注（不迁移、不删除） | 用户选择。聚合数据已无法回溯当时跑的是哪个 UWP 应用，任何「自动迁移」都是编造；因此只把显示名改成同时诚实的「UWP 应用（未能识别/旧合并）」 |
| **D76** | 解析做成**两条路径**（子窗口 / 顶层 + 标题配对），标题**只用于配对**、身份仍只来自进程名 | 实测（26H2）表明应用本体是独立顶层窗口、且与宿主无父子 / owner 关系 —— 只按教科书写会「永远认不出且不报错」。标题不参与身份，因此展示名仍可由键推出、重启不跳变 |
| **D77** | 新增取证入口 `--diag-uwp`，并把「真实窗口的端到端断言」写进 `--m11-selfcheck` 的 C 组 | 这次的教训是「假设与真实不符，且不报错」。取证工具让真实窗口关系**可被打印、可被复核**；端到端断言让「路径 2 没实现」这类错误**当场 FAIL**（变异测试已验证：去掉路径 2 → 恰好 1 项 FAIL） |

### M11 的关键认识

1. **教科书写法不等于本机事实**：§5.5 的方案（枚举子窗口找 CoreWindow）在 Windows 11 26H2 上**根本不成立**。它不会报错、不会崩、单测也能过 —— 只是**永远认不出任何 UWP 应用**。这类错误只能靠「把真实环境打印出来看」发现。
2. **「先取证、再写规则」值得成为习惯**：`--diag-uwp` 只花了几十行，却直接决定了实现形态；若无它，我会写出一个「自检全绿、实际全废」的版本。
3. **标题可以是「配对键」，但不能是「身份」**：用标题把「应用窗口」与「它的宿主」配起来是安全的（身份仍来自进程名）；但若用标题当显示名，重启续算时拿不到标题 → 名字跳变。区分「找对窗口」与「叫什么名字」是关键。
4. **保守约束要成组出现**：单看「pid 不同」不够（外壳的 XAML 岛也满足），单看「类名」不够（输入体验也是 CoreWindow）；于是三条约束（宿主标题非空 / 候选可见且非壳 / 必须恰好一个）必须一起用，才能既认得出又不认错。
5. **自检自身的装置错误也要修干净**：B 组一度 FAIL，原因是我把**文件路径**当**目录**传给清理函数 → 库没删掉、每次运行累加 3600 秒。把实际数值打进断言文本后一眼看穿（`SecondsOf=14400s` = 4 × 3600）。

| **D82** | 命令行为 `"<exe 全路径>" --autorun`，**路径一律加引号** | 含空格路径不加引号会被系统拆成两段，表现为"登录后什么都没发生"且**不报错** |

### 关键认识（M12）

1. **"已启用"是个复合判断，不是"值存不存在"**：必须**同时**满足"指向本程序"与"带 `--autorun`"。
   只比路径，界面就会承诺一个不会发生的行为（登录时弹出主界面）。
2. **注册表是最容易被外部改动的地方**（任务管理器、组策略、别的工具），所以它**不能**和 `settings` 里的
   "期望状态"并存 —— 谁是真源必须唯一，且每次**回读**。
3. **写操作要回读，不能自说自话**：`SetValue` 不抛异常不等于值真的写进去了。变异测试 B 正是打在这条上：
   把"写入"去掉只报告成功 → 被"直接读原始值核对"那条断言抓住。
   （第一次变异只改"回报值"、没改"行为"，结果没被抓住 —— **变异要改到行为真的变了**。）
4. **降级契约要一路延续**：M5b 定了"没有托盘就绝不能隐藏窗口"；自启场景下它变成
   "自启时若托盘不可用，**必须显示窗口**" —— 否则用户会失去唯一的入口。
5. **自检能验到"注册表里确实有正确条目 + 该组合根能启动"，验不到"重启后真的自动出现"**；
   这条边界必须**如实声明并交给人工**（M12 文档 §7、§8 第 9 条）。

**同步的关键认识**：
1. **接口今天就有** —— 写 UI 要调用的数据接口**不依赖拆工程**；`ProductRuntime` 公开成员 + `App` 注入的 6 个委托就是接口面。
2. **M14 必须早于 M16** —— 自检锚在 `MainWindow` 静态成员上，先重写 UI 等于删掉验证网。
3. **M15 必须先于换框架** —— XAML 框架加载不可卸载；不进程化，框架选择就没有自由。
4. **卡片要分三层** —— 窗口层冻结（M0 像素结论）、渲染层可换（Skia）、数据层契约不变（`CardModel` 就是接缝）。
5. **GDI+ 的拷贝不是冗余** —— GDI 经 HDC 绘制会丢 per-pixel alpha；Skia 的 CPU 光栅逐像素写内存，所以「直写」对 Skia 成立、对 GDI+ 不成立。
