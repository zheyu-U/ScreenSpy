## 二、Win32 桌面结构与“嵌入”路线（路线 A）

### 问题 2.1　26H2 的桌面结构与《开发文档》§5.8 描述不符
- **现象**：文档假设“存在一个顶层、无 `SHELLDLL_DefView` 的同级 `WorkerW` 作为壁纸层”。实测 26H2 上：
  - `SHELLDLL_DefView`（图标层）**直接是 `Progman` 的子窗口**；
  - 壁纸层是 **`Progman` 的全屏子 `WorkerW`**（注入 `0x052C` 后出现的 `0x1503A0`）；
  - 顶层确有 **17 个 `WorkerW`，但全是 170×47 且不可见**（属其它进程），**不加校验就会误选**。
- **解决**：
  1. 修订 `开发文档.md` §5.8 为**自适应三档定位**（新版 Progman 子 WorkerW → 直接嵌 Progman 压图标层之下 → 精简兜底）；§7.1 标注 ✅ 已实测并附四条实测结论；
  2. 候选窗口一律加**“可见 + 覆盖主屏”**校验。

### 问题 2.2　`0x052C` 的幂等性
- **现象**：`0x052C` 会**新增**壁纸层 `WorkerW`，重复注入会不断新增。
- **解决**：实现时**先查找已存在的壁纸层，找不到才注入**。

### 问题 2.3　“嵌入失败”其实是我的判定方法错了
- **现象**：`SetParent` 返回非零（成功），`GetParent` 却返回 `0`，一度误判失败。
- **根因**：对**仍带 `WS_POPUP`** 的窗口，`GetParent` 返回的是 *owner*（此时为 NULL），不是 parent。
- **解决**：改用 **`GetAncestor(GA_PARENT / GA_ROOT)`** 判定。
- **附带发现**：`SetParent` **不会**自动把 `WS_POPUP` 改成 `WS_CHILD`，必须显式改，否则行为不可预期。

### 问题 2.4　路线 A 的“自动检测全绿，屏幕上却什么都没有”（最贵的一课）
- **现象**：所有 API 都报告成功 —— `SetParent` 返回非零、`GetAncestor(GA_ROOT) == Progman`、`IsWindowVisible=True`、`UpdateLayeredWindow` 连续多帧无异常 —— 但**人眼报告“至始至终窗口未出现”**。
- **根因**：原判定链检查的全是**记账层事实**（窗口树关系、样式位、API 返回值），**没有一项能证明像素真的上了屏**。
- **解决办法（引入客观判定）**：给 Spike 增加 `--diag`：
  - 投放 **7 个纯色探针**，交叉覆盖两个维度：**分层(ULW) / 不透明背景刷** × **顶层 / `WorkerW` 子窗口 / `Progman` 子窗口**；
  - **截屏**并用像素比对客观判定“谁真的上了屏”（不依赖 API、不依赖人眼）；
  - 补充 `DwmGetWindowAttribute(DWMWA_CLOAKED)` 作为不依赖桌面可见性的旁证。
- **决定性结果**：

  | 探针 | 形式 | 宿主 | 截屏命中 | 判定 |
  |---|---|---|---:|---|
  | P0 | 分层，**顶层**，压 `HWND_BOTTOM` | 桌面（不嵌入） | **23400（满框）** | **可见 ✅** |
  | P1 | 分层**子**窗口 | WorkerW | 0 | 不可见 ❌ |
  | P2 | **不透明**子窗口 | WorkerW | 0 | 不可见 ❌ |
  | P4/P6 | 分层子窗口 | Progman（最上/图标层下） | 0 | 不可见 ❌ |
  | P5 | **不透明**子窗口 | Progman（最上） | 0 | 不可见 ❌ |

  → 这**同时排除**了三个常见嫌疑：不是分层的锅（P2/P5 不透明一样不可见）、不是重父化的锅（换宿主一样不可见）、不是被遮挡的锅（P0 在 `HWND_BOTTOM` 都能满框可见）。
- **机理**：`Progman` 的扩展样式含 **`WS_EX_NOREDIRECTIONBITMAP`**（无重定向表面，内容由 **DirectComposition** 呈现）。
  推论（与全部证据一致）：Progman 子树里只有 shell 自己注册进其合成树的子 HWND 会被呈现；**第三方 `SetParent` 进去的子 HWND 无论分层与否都不在合成树里，因此永不上屏**。
  且 `DWMWA_CLOAKED` 对所有窗口都返回 0 —— **所有 API 都说“没问题”**，这正是它最难被发现之处。
- **结论**：**路线 A 在 Windows 11 26H2 上不成立。**

### 问题 2.5　截屏判定被“桌面被遮挡”污染
- **现象**：第一次 `--diag` 的截屏里是**被最大化的 Visual Studio**，不是桌面；此时所有探针都是 0 像素 —— 该结果**不可判定**。
  另有一个进程崩溃（`0xC0000409` / CLR 未处理异常），因诊断代码当时未加 try/catch。
- **解决**：
  1. 诊断代码补 try/catch；
  2. 明确规则：**截屏必须同时校验“桌面是否可见”，否则结论记为“不可判定”**，不得当成“不可见”；
  3. 引入**遮挡对照 + 方法自检**（见问题 4.3）。

## 三、需求澄清与参考实现求证

### 问题 3.1　“在桌面 + 会被窗口覆盖 + Win+D 不最小化”到底要哪条路线？
- **澄清结果**：用户要的是“**窗口就在桌面、会被其它窗口覆盖，但 Win+D 不最小化**”。
- **分析**：这正是路线 B 的观感 + 一项“Win+D 免疫”。而 Win+D 由资源管理器统一最小化顶层窗口，被豁免的只有桌面/外壳自身窗口 —— **第三方顶层窗口没有可靠的豁免手段**。所以问题的本质是“**能不能让桌面树里的窗口渲染出来**”（即路线 A 的机制），而 A 已被证伪。
- **转折**：用户指出 **Rainmeter** 在同类需求上可以做到 —— 这是最有力的反证，说明一定还有别的做法。

### 问题 3.2　从 Rainmeter 源码求证“它到底怎么做的”
- **做法**：浅克隆 Rainmeter 源码到 `_ref/rainmeter`，精读 `Library/System.cpp`、`Library/Skin.cpp`。
- **发现（推翻了我此前的推断）**：
  - **Rainmeter 全仓库为桌面嵌入调用 `SetParent` 0 次 —— 它根本不嵌入！**
  - 它就是**顶层窗口**（`WS_POPUP` + `WS_EX_LAYERED|WS_EX_TOOLWINDOW`）+ `UpdateLayeredWindow(ULW_ALPHA)` + `SetWindowPos(HWND_BOTTOM)`；
  - 与我们路线 B 的差别只有两块，而这两块正是我们缺的：
    1. **z 序自锁**：`WM_WINDOWPOSCHANGING` 里 `wp->flags |= SWP_NOZORDER`（`Skin.cpp`），外力推不动它；
    2. **“显示桌面”检测 + 复位**：探针窗口 + z 序判据（`System.cpp` `CheckDesktopState` / `PrepareHelperWindow`），
       平时 250ms 采样、显示桌面期间加密到 100ms，并用 `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)` 即时响应；
  - 24H2+ 的桌面宿主判定：`SHELLDLL_DefView` 的父窗口（= `Progman`）。
- **它凭什么扛住 Win+D（关键洞察）**：**不是阻止最小化**，而是“**发现桌面被抬到最前，就把自己重新插回桌面之上**”。
  （`Skin.cpp` 里没有任何 `SC_MINIMIZE` 拦截 / `IsIconic` 恢复逻辑。）
- **结论修正**：**路线 B 不是降级方案，而是正解**；路线 C 没必要做。

## 四、B+ 机制实现与判定方法学

### 问题 4.1　照抄源码推出的“判据极性”是错的
- **现象**：B+ 首次 `--verify-bplus`，**S2（Win+D 后）标记像素 = 0，免疫判定失败**。
- **根因**：我按字面理解 Rainmeter 的 `FindWindowEx` 反推极性，把 `HostZ >= ProbeZ` 当成“显示桌面”，结果 **正常态被误判成显示桌面**（把卡片抬走）、**真该抬升时反被判成正常**（把卡片压回底层被盖住）。
- **解决**：按**实测**校正为 **`显示桌面 ⟺ HostZ < ProbeZ`**（桌面宿主跑到压在底部的探针之前）。修正后全部通过。
- **教训**：**不要用“读源码推断”替代“实测”** —— 与问题 2.4 同源。

### 问题 4.2　“Win+D 免疫”的机理与我原先的理解相反
- **现象/数据**（两次运行一致）：

  | 步骤 | 标记像素 | IsIconic | ShowDesktop | z(Host/Probe/Card) |
  |---|---:|---|---|---|
  | S1 正常态 | 576 | False | False | 161/159/160 |
  | **S2 Win+D** | **576** | **False** | **True** | **15/161/14** |
  | S3 还原 | 576 | False | False | 161/159/160 |

- **根因**：**卡片根本没有被最小化**（`IsIconic=False`）。Win+D 只是把 **Progman 从最底层抬到最前**（下标 161 → 15），把压在底层的卡片**盖住**了。
- **解决**：正解是 **z 序复位**（检测到显示桌面 → 把卡片插到 topmost 带之下、桌面之上），而不是拦截最小化。

### 问题 4.3　把“只能靠肉眼”的三项做成客观判定
- **背景**：鼠标穿透、任务栏/Alt+Tab 隐藏、Win+D 还原一致性，原先只能肉眼观察。
- **解决**：扩展 `--verify-bplus`：
  - **鼠标穿透（机制）**：读扩展样式必须含 `WS_EX_TRANSPARENT`；
  - **鼠标穿透（功能）**：标记点命中测试须返回**桌面窗口**而非卡片自身；
  - **任务栏/Alt+Tab 隐藏**：必须含 `WS_EX_TOOLWINDOW` 且**无** `WS_EX_APPWINDOW`；
  - **Win+D 还原一致性**：S3 的标记像素与包围盒必须与 S1 **完全一致**（无残影、无位移）；
  - **方法自检**：在 S4 放一个**不含 `WS_EX_TRANSPARENT` 的不透明对照窗口**，命中测试必须返回**它自己** —— 以此证明 S1/S3/S5 的“返回桌面”是“透明被跳过”，而不是命中测试失效。
- **结果**：`ExStyle=0x080800A0 = LAYERED|TRANSPARENT|NOACTIVATE|TOOLWINDOW`；命中测试在 S1/S3/S5 返回 `SysListView32`、在 S4 返回对照窗口自身；两轮运行全部通过。
- **已知噪声（如实记录）**：报告里“该点最上层外部窗口”是**包围盒启发式**，会产生噪声（曾报出并未绘制在该点的 `Windows.UI.Core.CoreWindow`）。判定一律**以像素 + 命中测试为准**，此列仅作参考。

## 五、抽回产品工程时遇到的问题（工具链 / 工程配置）

### 问题 5.1　工程文件无法用常规文件工具修改
- **现象**：`write_file` / `apply_patch` 修改 `ScreenSpy.csproj` 均报 `A loaded project file requires its project-system edit adapter.`。
- **解决**：改用脚本写入工程文件（保留 UTF-8 无 BOM）。
- **同类现象**：先前编辑 `docs/*.md` 时 VS 编辑通道报“无法打开文本文档”，改用**按精确行号脚本替换**，并保持原编码（`开发文档.md` 为 CRLF、`对话纪要.md` 为 LF、均无 BOM）。

### 问题 5.2　WPF 与 GDI+ 的隐式 using 造成类型二义
- **现象**：产品工程要同时用 WPF（主界面）与 `System.Drawing`（GDI+ 卡片渲染）。若保留 `ImplicitUsings=enable`，WPF 与 WinForms 的隐式 using 会同时引入 `System.Windows*` 与 `System.Drawing`，使 **`Size` / `Point` / `Color` / `FontFamily`** 等类型二义。
- **解决**：产品工程设 **`ImplicitUsings=disable`**，各文件显式引入所需命名空间；并加 `UseWindowsForms=true`（仅为获得 GDI+，不创建任何 WinForms 窗体）与 `AllowUnsafeBlocks=true`（DIB 像素拷贝 / 截屏像素判定）。

### 问题 5.3　`StartupUri` 不能设为 `null`
- **现象**：演示入口尝试 `StartupUri = null` 抛 `ArgumentNullException`，进程崩溃（`-532462766`）。
- **解决**：**移除 `App.xaml` 的 `StartupUri`**，改为在 `App.OnStartup` 中显式决定：命中演示参数 → 跑卡片演示后 `Shutdown`；否则 `new MainWindow().Show()`。

### 问题 5.4　XAML 注释里出现 `--`
- **现象**：`App.xaml` 注释中写了 `--demo-card`，编译报 `MC3000`（XML 非法）。
- **根因**：**XML 注释中不允许出现连续两个连字符 `--`**。
- **解决**：改写注释措辞，避免 `--`。

### 问题 5.5　WinExe 控制台中文乱码
- **现象**：`ScreenSpy` 是 `WinExe`，演示输出中的中文在控制台显示为乱码。
- **解决**：演示入口开头设置 `Console.OutputEncoding = Encoding.UTF8`（失败则忽略）。

## 六、可复用的教训清单

1. **判定“是否真的显示了”，只认截屏像素** —— API 返回值全绿也可能是假阳性（问题 2.4）。
2. **截屏判定必须校验前提**（桌面是否可见）；前提不成立时结论是“**不可判定**”，不是“不可见”（问题 2.5）。
3. **不要用读源码替代实测**（问题 4.1）——极性、阈值、时序都要在本机量。
4. **`GetParent` ≠ 父窗口**：带 `WS_POPUP` 时返回 owner。用 `GetAncestor`（问题 2.3）。
5. **`SetParent` 不改样式**，`WS_POPUP`→`WS_CHILD` 必须显式改（问题 2.3）。
6. **未公开消息要幂等**：先查找、找不到才注入（问题 2.2）。
7. **桌面窗口树 ≠ 会被合成**：`WS_EX_NOREDIRECTIONBITMAP`（DComp）下第三方子窗口不上屏（问题 2.4）。
8. **对外力免疫不要靠“周期性纠正”**，要靠**样式/消息层自锁**（`SWP_NOZORDER`）（问题 3.2）。
9. **任何自动化判定都要有对照/自检**，否则无法区分“真的没有”与“工具坏了”（问题 4.3）。
10. **`a?.M(arg)` 的实参只在 `a` 非 null 时求值** —— 写成 `Ticked?.Invoke(ProcessHeartbeat())`，会让“无人订阅事件”时的心跳**完全不执行**（计时恒为 0）。凡“先算再抛”的语义，必须**先求值再抛事件**（M1，详见 `docs/M1-验证.md` §4）。
11. **自检若与被检对象共享同一前提，会一起漏掉缺陷** —— 上述 bug 正因自检**恰好订阅了事件**而躲过；回归用例要**刻意覆盖“无订阅者”等退化配置**。
