# M9-1 · 软件身份层（进程名合并 + 分类）

> 日期：2026-10-06
> 目标：解决"同一个软件有多个进程名"的问题 —— 让统计、榜单、卡片与**将来的限额**都挂在
> **一个**"软件"上，而不是挂在原始进程名上；并让用户能给软件指定分类。
> 定位：**M9（限额引擎 + 提醒）的第一段**。身份层必须**先于**限额落地，否则限额条目日后要整体迁移。

## 1. 开工前确认的决策（均按用户选择执行）

| 编号 | 决策 | 选择 | 影响 / 理由 |
|---|---|---|---|
| D52 | 用户面的"分类"含义 | **可把多个进程合并成一个软件** + **自定义分类（以软件为最小单元）** | 需要一张"软件"身份表 + 一张分类表；限额将来可挂"软件"或"分类" |
| D53 | 一个软件落在多个分类下怎么办 | **A 单选**：一个软件只属于一个分类 | `各分类之和 == 各软件之和` **精确成立**，分类限额可对账、可相加。代价：不能表达"VS Code 既是工作又是工具"（限额场景里本也不需要） |
| D54 | 总限额口径（M9-2 用） | **今日真实活跃**（`TodayTotal`） | 与主界面大字号、卡片、托盘**同一个数**，不会出现"限额说超了、界面看着没超" |
| D55 | 提醒技术路线 | **先用托盘气泡**（`NotifyIcon.ShowBalloonTip`），之后可升级 Toast | 零新增依赖、无需 AUMID/快捷方式注册；发送动作将抽成接口，换实现不动引擎 |
| D56 | 阈值判定时机 | **每秒判定 + 阈值可配置** | 提醒及时（≤1 秒）、与界面数字同源；去重标记按 `(日期, scope, target, 阈值)` 落库 |
| D57 | 合并后已有历史数据怎么办 | **清空全部历史，从今天重新开始** | 身份口径变了，旧行按原始进程名存着会让同一软件分成两半。`settings`（卡片形态/坐标）与 `limits` **不受影响** |
| D58 | 实施顺序 | **先身份层（本次），再做限额** | 限额与分类都挂在软件键上；先做限额则合并上线时要迁移限额条目 |

> **不可拆分**是本次决策的必然结果，界面与文档都要写明：合并会把历史与今日时长一并并入目标软件，
> 库里的行**已被重写**，原始键的信息在**聚合层**不再存在。
> 但**原始活动日志（JSONL）仍保留原始进程名 / 类名 / 标题**，追溯能力不丢。

## 3. 关键设计

### 3.1 一个解析点

```
进程名(原始键)  →  【别名：raw → canonical】  →  软件(归一键)  →  【app_meta】  →  显示名 + 分类
   devenv                                              devenv                    工作
   code ────────────────────────────────────────────→ vscode                    （VS Code）
```

解析**只在 `ForegroundAppRules.Create` 里做一次**，下游（榜单 / 卡片 / 存储 / 将来的限额引擎）
全部只见归一键。多一处解析就多一处可能与别处分叉 —— 这是本项目的分层红线。

### 3.2 三处必须一起改（合并的动作）

| # | 位置 | 为什么不能少 |
|---|---|---|
| ① | 库内历史行（`SqliteStore.MergeAppKey`） | 合并可能发生在一天的中途，今天早些时候已按**原始键**落库。不重写就会出现"vscode 1:20 + code 0:40"两行 —— 用户以为合并没生效，限额也只会统计到一半 |
| ② | 内存榜单（`AppUsageTracker.MergeKeys`） | 毫秒**与基线**都要搬；只搬毫秒会让"今天一整天"丢掉合并前的那部分历史 |
| ③ | 待写增量（`AppUsageStore.MergePendingKeys`） | 尚未落库的那些毫秒若不重键，下一轮 flush 又会写成原始键 |

顺序刻意是**先库、后内存**：库写失败会抛出，此时内存一个字都没动 → "要么都改、要么都没改"。

### 3.3 表设计（schema v3）

```sql
CREATE TABLE IF NOT EXISTS app_alias (      -- 原始进程名 → 归一键（**只存用户做过的合并**）
    raw_key TEXT PRIMARY KEY,
    app_key TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS app_meta (       -- 只存用户改过的行；没有行 = 用系统默认
    app_key      TEXT PRIMARY KEY,
    display_name TEXT NOT NULL DEFAULT '',  -- 空串 = 未设置（按友好名映射表现算）
    category     TEXT NOT NULL DEFAULT ''   -- 空串 = 未分类（不是 NULL，理由同 limits.target）
);

CREATE TABLE IF NOT EXISTS categories (
    name       TEXT PRIMARY KEY,
    sort_order INTEGER NOT NULL DEFAULT 0
);
```

### 3.4 迁移：清空时间历史（**唯一一次会删数据的迁移**）

`v2 → v3` 时删除 `app_usage` 与 `daily_activity` 的**全部行**（`settings` / `limits` 保留）。
分版本判断：`v1` 的库里还没有 `daily_activity`，直接 DELETE 会报错。

### 3.5 界面「软件与分类」一节按需重建（不跟每秒刷新）

状态区每秒重建文本（无交互、无副作用），而这一节含下拉框与文本框。
若跟着每秒刷新重建，用户正在打开的下拉框会在半秒后被销毁，表现为"点了没反应"。
因此改成**按需重建**：进窗口时 / 点「刷新列表」/ 每次改动之后。

分类下拉框保存失败时会**把显示值拉回真实值**（而不是留在屏幕上骗人），回到的是**上一次的真实选择**
（`currentSelection`），不是无条件回到「未分类」。

### 3.6 自定义软件名称（M9-1b）：一条规则，两个不对称

界面上每一行只能靠名字区分软件。两个软件同名时，用户看到两行一样的文字，
而它们的时长、分类、将来的限额**各自独立** —— 用户会把设置下到另一个上，**且不会有任何报错**。
所以选择**禁止重名**，并把"什么算重名"放进 `AppNamingRules`（**全项目唯一定义**；
对话框预检、组合根、写库前的最后一道闸门都调它）。

**冲突范围**（判据只有一条：别的软件"现在会显示的名字"等于候选名）：

| # | 来源 | 为什么必须在范围内 |
|---|---|---|
| ① | 别的软件**用户设过的名字**（`app_meta.display_name`） | 哪怕它今天没出现，它占着的名字也得算数 |
| ② | 别的**今日出现的软件**当前显示名 | 今日名单就是用户此刻看到的列表 |
| ③ | **系统友好名表**里的全部默认名 | 挡住"把 chrome 改名叫 Visual Studio"——即便 VS 今天一次都没运行过 |

**两个刻意的不对称**（都是为了让用户**不被卡住**，不是漏洞；自检各有一条断言钉住）：

1. **本来就是默认名**时的「恢复默认名」是**空操作** → 一律放行（否则用户会卡在"想恢复却被拒绝"的死角）。
2. **恢复默认名**时只与别人的**自定义名**比较，**不**与别人的**默认名**比较 ——
   因为名字表本身就可能有两个键共用一个默认名（本项目的 `calc` 与 `CalculatorApp` 都叫"计算器"），
   那是名字表的账，不该让用户背。

**四态结果**（`AppRenameResult`）：`Ok` / `Invalid`（名字本身不合法）/ `Conflict`（并指出**跟谁**撞了）/ `NoStore`。
刻意不合并成一个 bool：界面要靠它给出**准确**的原因 —— 只说"失败"会让用户猜，而"把原因说错"本身就是一种界面骗人。

**已知边界**：若某软件既没人给它设过名字、今天没运行、也不在友好名表里，它的名字不在搜索范围内；
那种重名只会在它**首次运行时**浮现（届时它会以重名出现在列表里）。我们接受这个边界，
而不是把"今后可能出现的一切进程名"预先塞进一张名单（那既做不到，也会凭空误判）。

### 3.7 改名要在"四处"一起生效

| # | 位置 | 少了会怎样 |
|---|---|---|
| ① | 身份层（`_identity`） | **今后**的采样与**重启后**的续算仍用旧名 |
| ② | 内存榜单（`AppUsageTracker` 的桶） | 主界面「Top 5」与卡片榜单**仍是旧名** |
| ③ | "当前软件"（`_last`） | 卡片上"正在使用 …"仍是旧名，**直到它下一次成为前台**（可能几分钟后） |
| ④ | 界面列表 | 上面榜单已变、下面那一行还是旧名 —— 自相矛盾 |

②③由 `AppUsageTracker.SetDisplayName` 一并处理。它是**纯展示层**动作：不碰毫秒、不碰键、不动分类 ——
所以**守恒等式与全部统计口径一个字都不变**。

## 5. 过程中发现的两个"真问题"（如实记录）

### 5.1 `ActivityScheduler.Pump()` 与 `Sample()` 行为不一致（陷阱，非产品缺陷）

`Sample()` 会在 `_day` 为默认值时**先建立当日基准**，而 `Pump()` **没有这个保护** ——
于是"先 `Seed` 基线、再 `Pump`"会让首次心跳触发一次**跨天翻页**（`DayRolled` → 榜单清零），
把刚灌入的基线冲掉。

- **生产代码不受影响**：`Start()` 会建立当日基准，而播种发生在 `Start()` 之前。
- **自检装置受影响**：我的 Harness 从不调用 `Start()`，因此第一次跑就出现了"基线 5000ms 不见了"两项 FAIL。
  修法是装置里先 `Start()` 后 `Stop()`（与产品顺序一致），并把这个陷阱写在代码注释里。
- **是否要修 `Pump()`**：建议远期让 `Pump()` 与 `Sample()` 行为一致（一行保护），
  但会触碰 M1 的既有语义，**本次不动**，留给后续决策。

### 5.2 自检自身的写法错误（不是产品缺陷）

首次运行时 C 组两项 FAIL，查下来是**我把 Seed 放在观测之后**（`Seed` 会重置当日状态）。
修正顺序后通过 —— 这正说明这组断言真的在跑。

## 6. 已知局限

1. **合并不可拆分**：已并入的历史秒数不会退回（原始活动日志仍保留原始进程名，可追溯）。
   「取消合并」的语义是"**对今后生效**"：删掉别名，之后该进程名不再并入目标。
2. ~~**没有"重命名软件"入口**：`SetAppDisplayName` 的 API 已就绪（合并时会用到），但界面暂未提供单独的改名控件。~~
   → **已在 M9-1b 补齐**（每行「重命名…」+ 弹对话框 + 禁止重名 + 四处立即生效）。
   新的局限随之而来：**对话框本身不被自检覆盖**（它需要真的显示窗口），因此它被刻意写得很薄
   （只有一个模态循环与三个按钮，所有判断都在 `AppNamingRules` 里）；
   但"控件真的被正确赋值、错误文案真的显示出来"仍需人眼确认。
2b. **改名不改键、不回填历史**：库里只存归一键，改名只影响显示文字；"取消合并"之后
   已并过去的历史秒数同样不会退回（与本节第 1 条同源）。
3. **UWP 真实名修正仍属 M11**：身份层可以让用户把 `applicationframehost` 合并/改名，但那是**手动兜底**，不是自动识别。
4. **分类不能改名**：只支持新建/删除；改名要等后续（删除会让该分类下的软件回到未分类，且该分类的限额一并删除）。
5. **迁移会清空时间历史**：这是本次的**既定决策**（D57），不是缺陷；但意味着 M10 的 7 天图在刚升级后没有历史数据可画。
6. **界面可用性未做自检**：分类下拉/合并按钮的**纯逻辑**（`AppIdentity` 的规则）已全部客观断言，
   但"控件真的被正确赋值、禁用状态真的生效"需要人眼确认（自检刻意不去驱动真实 WPF 控件）。
