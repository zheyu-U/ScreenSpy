# M2 验证 · 锁屏 / 睡眠监听

> 对应《开发文档》§5.3。完成日期：2026-10-05。环境：Windows 11 26H2 / build **26300.9457**、`.NET 10.0.12`、1920×1200 @125%。

## 1. 目标

锁屏、睡眠（含休眠）期间**不计入**活跃使用时长。

比 M1 更难的地方在于：M1 的输入源（`GetLastInputInfo`）是**持续可查询**的，而锁屏/睡眠是**事件驱动**的，
一旦事件漏发，程序**不会自己知道**——尤其“解锁事件丢失”会导致**永久停止计时**（比多计更隐蔽、更严重）。

## 3. 设计：三条防线（层层递进）

单一手段都不够可靠，因此叠加三层，任一失效都不至于把睡眠算成活跃：

**① 事件（主路径，及时）**
`SystemEvents.SessionSwitch`（`SessionLock`/`SessionUnlock`，另把控制台/远程 断开-连接 也视作离开/回来）
+ `SystemEvents.PowerModeChanged`（`Suspend`/`Resume`）。
`SystemEvents` 自带专用消息泵线程，**不需要**调用方跑消息循环。

**② 探测（初值 + 自愈，兜住事件的两个天然缺口）**
`WTSQuerySessionInformation(WTSSessionInfoEx)` 读 `SessionFlags`（0 = 锁定，1 = 未锁定）。
- 缺口一：**进程启动时已经锁屏** —— 事件不会补发，只能用探测取初值；
- 缺口二：**解锁事件丢失** —— 会永久少计，靠周期探测（默认 5s）纠正回来。

关键约束：探测**只在结果确定时**才改动状态；返回“不确定”时**什么都不做**，绝不用猜测覆盖事件给出的状态。

**③ 时间空洞（与事件完全无关的兜底）**
单拍间隔超过 `MaxCreditedInterval`（默认 **60s**）即判为时间空洞，一律不计入。
理由：睡眠时进程被挂起，恢复后第一拍会看到数小时的间隔；而在 S0 新式待机等场景下 `Suspend` 事件
可能缺失或滞后，此时只有这条客观护栏能拦住“把整晚算成活跃”。取舍：宁可少计（有界、可配置）。

### 3.1 为什么是“两个独立标志位”而不是一个状态

锁屏与睡眠会**重叠**：例如先锁屏、再合盖睡眠，唤醒时**先收到 `Resume` 而尚未解锁**。
若用单一三态，后到的 `Resume` 会覆盖“锁屏”从而**错误恢复计时**。
因此二者各用一个布尔量，`ShouldPause = 锁屏 || 睡眠`，并专门写了重叠顺序的检查用例。

## 6. C 段：睡眠测试（`--sleep-test`）

真实“睡眠 → 自动唤醒”闭环，由程序自己发起、自己唤醒，并用**客观指标**判定“睡眠期间有没有被计入活跃”。

```powershell
dotnet run --project ScreenSpy/ScreenSpy.csproj -- --m2-selfcheck --sleep-test --sleep-seconds=20
```

### 6.1 为什么能自动唤醒

睡眠测试的关键是“**能不能自己醒过来**”。这里的做法是先设一个**可等待定时器**，再入睡：

1. `CreateWaitableTimer(manualReset: true)` 建一个可等待定时器；
2. `SetWaitableTimer(..., fResume: TRUE)`，到期时间 = 现在 + `--sleep-seconds`（绝对 UTC 时间，FILETIME）；
   `fResume = TRUE` 的含义就是**该定时器到期时唤醒系统**；
3. `SetSuspendState(FALSE, FALSE, FALSE)` 进入睡眠 —— 第三个参数必须是 `false`，
   否则会**禁用唤醒事件**，我们设的定时器就白费了；
4. 唤醒并返回后，等待定时器信号 + 给电源事件 3s 投放时间，再采集数据。

**安全顺序（缺失任何一步都不安全）**：

| 步骤 | 作用 |
|---|---|
| 先设定时器并**校验返回值** | 定时器设置失败 → **立即中止，绝不入睡**（“拿不到保命绳就不睡觉”） |
| 启用 `SE_SHUTDOWN_NAME` | `SetSuspendState` 的前置条件；失败不阻断，最终以 `SetSuspendState` 返回码定论（错误码 1314 = 权限不足） |
| 入睡前**日志落盘** | 万一睡眠期间异常终止，睡眠之前的证据已在 `artifacts/m2/m2-selfcheck.log` |
| 默认关闭 | 只有显式传 `--sleep-test` 才会执行；不加时程序**绝不会**睡眠 |

### 6.2 判定指标（打印在 C 段末尾）

| 指标 | 含义 | 期望 |
|---|---|---|
| 墙钟时长 | `DateTime.UtcNow` 增量 | ≈ 计划时长（含唤醒开销） |
| **今日活跃增量** | 调度器 `TodayActive` 增量 | **关键项**，应远小于墙钟时长 |
| `TickCount64` 增量 | `Environment.TickCount64` 增量 | 用于**观察**它在睡眠期间是否推进（这是本测试要搞清的事实之一） |
| 心跳增量 | `Sequence` 增量 | 睡眠期间定时器被挂起 → 应接近 0 |
| 时间空洞增量 | `GapTicks` 增量 | 第二道防线是否触发 |
| 电源事件 | `Suspend` / `Resume` | 第一道防线是否到达 |

判定规则（`SleepAssessment`，纯逻辑，已由 A 段 9 项检查覆盖）：

- `LooksLikeRealSleep`：墙钟增量 ≥ 计划时长 × 80%，否则**本轮结论不可用**（不是产品失败）；
- `OverCredited`：今日活跃增量 > `max(5s, 墙钟 × 10%)` 即判为**防护失效**；
- `HasDefenseEvidence`：空洞 > 0 **或** 收到电源事件。两者皆无只作**提示** ——
  若 `TickCount64` 在睡眠期间不推进，则本就没有“可计入的时长”，此时“未被计入活跃”依然成立。

### 6.3 已知风险（无法在本进程内完全排除）

- 若系统策略关闭了“允许唤醒定时器”，而 `SetWaitableTimer` 仍返回成功，则机器可能**不会自动醒来**，
  需要按一下键盘；日志已在入睡前落盘，证据不会丢。
- 本测试会**真实挂起整机**（VS、下载、播放都会暂停）。因此应在你方便时运行，建议先用 `--sleep-seconds=20`。
- `SetSuspendState` 的实际效果由电源策略决定（可能被解析为休眠），这对判定无影响。

## 7. 过程中发现并修复的缺陷（两处，都值得留档）

### 7.1 `WTSINFOEX` 的 `SessionId` 不紧跟 `Level`（结构体填充）

`WTSINFOEX = { DWORD Level; union { LEVEL1; LEVEL2; } }`，两个 union 成员内含 `LARGE_INTEGER`（8 字节对齐）。
本机实测布局为：**`Level@0`、4 字节填充、`SessionId@8`、`SessionState@12`、`SessionFlags@16`**
（自检打印的“自定位偏移=8”就是证据）。

若按直觉硬编码 `SessionId@4`，会**静默读到错位数据**。因此改为**自定位 + 交叉校验**：
用 `WTSSessionId` 查会话号、`WTSConnectState` 查连接状态（两个独立来源），
在缓冲区里寻找“会话号 + 真实连接状态 + 合法 SessionFlags”这个三元组。

### 7.2 “会话号为 1”时的错位误判（由 7.1 引出，若不修会长期潜伏）

扫描若从偏移 0 起步，而**会话号恰好是 1**（控制台会话很常见），偏移 0 的 `Level = 1` 就会命中，
其后两个 DWORD（填充 0 + 会话号 1）又**恰好都是合法值**（`WTSActive` + `UNLOCK`）——
于是会把错位数据当成真头部，导致**每台会话号为 1 的机器**都解码错误
（症状：探测恒为“未锁定”，从而**与锁屏事件互相打架**，把真实的锁屏保护抵消掉）。

修复：候选偏移必须 **≥ 4**（`SessionId` 必然在 `Level` 之后），并加了交叉校验。
已写成两条确定性回归检查（本机会话号是 2，若不专门构造用例，这个 bug 在本机测不出来）。

## 8. 已知局限（如实声明）

1. **真实锁屏闭环未由我执行**：逻辑分支 100% 由确定性检查覆盖，真实事件字节只验证到“订阅成功 + 探测解码正确”；
   完整闭环需你跑一次 `--lock-test`（见 §5.1）。
2. **真实睡眠测试由你执行**：C 段已实现并有安全前提，但“让整机睡眠”这件事我不宜替你发起。
   在未跑之前，睡眠分支由 A 段的“2 小时间隔 → 时间空洞”确定性覆盖。
3. **精度为 ±1 拍（约 ±1s）**：暂停按心跳生效。锁屏侧偏“少计”，解锁侧偏“多计”，方向与幅度都有界。
4. **无测试工程**（按 D12 决策），上述场景没有自动化回归保护——**这两处 WTS 缺陷正说明了这个代价**：
   它们只能靠内嵌的确定性检查兜住，不能靠 `dotnet test` 常态守护。
