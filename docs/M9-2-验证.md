# M9-2 验证：限额引擎与提醒

> 里程碑：**M9-2（限额引擎 + 提醒）** ✅ 已实现（2026-10-06）
> 依赖：M1（计时）、M3（按软件归属）、M4（SQLite）、M9-1（软件身份层：归一键 / 分类 / 显示名）
> 自检入口：`ScreenSpy.exe --m9-selfcheck [--dir=<目录>] [--log=<文件>]`（与 M9-1 / M9-1b 共用，新增 **F / G / H** 三组）

## 1. 目标与范围

| 要做 | 不在此里程碑 |
|---|---|
| 总限额 / 单软件限额 / **分类**限额 | 真实的 Windows Toast（先用托盘气泡；发送动作已抽成单一入口） |
| 阈值**可配置**（默认 80 / 100，可多档） | 强制阻止使用（本项目**只提醒**，不锁屏、不拦截） |
| **每秒**判定、阈值只提醒一次、去重入库 | 按周 / 按月的限额（今日口径） |
| 主界面设置 + 卡片进度条 + 托盘气泡 | 多显示器 / 云同步（非目标，见 `开发文档.md` §1.3） |

### 1.1 口径（沿用既有决定，未改动）

* **总限额比的是「今日真实活跃」** —— 与主界面大字号、托盘 tooltip、桌面卡片**同一个数**
  （`= 本次运行活跃 − 锁屏剔除 + 库中基线`）。若另算一套，就会出现「限额说超了、大字号看着没超」。
* **单软件限额比「该软件今天的时长」**（榜单同一口径，含库中基线）；键是**归一键**（M9-1），
  因此用户给「VS Code」设的限额不会因为 `Code` / `Code-Insiders` 两个进程名而只统计到一半。
* **分类限额 = 该分类下各软件时长之和**。分类口径是「一个软件只属于一个分类」（M9-1），
  所以**不会重复计**，且 `各分类之和 ≤ 各软件之和` 恒成立（未分类的不计入任何分类）。
* **锁屏 / 睡眠不计入任何限额**：它按已确认口径「完全不计入」，连总数都不进。

### 1.2 提醒规则

| 规则 | 实现 |
|---|---|
| 阈值 | 设置键 `limit_thresholds`，值是逗号分隔的**百分比**（默认 `"80,100"`）；解析后升序、去重 |
| 一次跨两档 | 只提醒**最高那档**（从 70% 涨到 110% 只弹「已达到」，不连弹两条） |
| 去重 | 设置键 `notified\|{日期}\|{scope}\|{target}\|{阈值千分比}`，**带日期** → 跨天自动重置 |
| 改限额 / 改阈值 | **清掉今天的去重标记** → 同一档会重新提醒（否则「把限额调低却再也不提醒」） |
| 存储不可用 | 退回**内存去重**（本次运行内仍只提醒一次）—— 降级时绝不刷屏 |
| 发送方式 | 托盘气泡（`NotifyIcon.ShowBalloonTip`），失败静默吞掉 |

### 1.3 刻意不做（诚实标注）

* **不阻止使用**：到点只弹一条提醒。
* **不做真实 Toast**：气泡零依赖、零 AUMID 注册；将来换 Toast 只需改 `TrayIconHost.ShowNotification` 一处。
* **气泡可能被系统「专注助手」吞掉**：那是系统行为，我们没有检测手段，也不假装能检测。

## 3. 关键设计

### 3.1 为什么把「纯逻辑」与「守门」分开

`LimitRules` / `LimitEngine` **无 IO、无状态**，因此下面这些最容易写错、又最难人工复现的规则
可以被逐条确定性推演：阈值边界（79 / 80 / 95 / 100 / 110%）、「一次跨两档只取最高档」、
去重键的**字面量契约**、分类求和、非法阈值或时长**不写库**。

去重与存储（副作用）集中在 `LimitGuard`，它**永不抛异常**（每秒都会走的路径，一次异常不该让心跳停摆）。

### 3.2 判定挂在哪里：`AppUsageBridge.Observed`

限额判定**旁听心跳**（默认 1s），而不是自己再起一个定时器：

* 与「按软件归属」同一个节拍 → 两个数字天然同步，不会出现「归属已更新、限额还停在上一秒」；
* 没有限额时**直接返回**（连判定输入都不组装），成本为零；
* 判定在**心跳线程**上，因此只做纯算术 + 偶发一次落库（只有真的跨过阈值才写）。

### 3.3 卡片放哪一条限额

卡片只有**一根**进度条，所以放**最接近上限**的那条（比例最高者）。
`LimitText` 为空的唯一含义是「没有任何限额」→ 渲染器**整块不画**
（宁可不显示，也不显示一个并不存在的约束 —— M6 就定下的口径）。

### 3.4 界面为什么这样分

| 部分 | 刷新方式 | 理由 |
|---|---|---|
| 限额进度文字 | **每秒**（纯文本、无交互） | 用户要看到它涨 |
| 分类下拉框 / 已设限额列表 / 阈值输入框 | **按需重建** | 含交互控件；跟着每秒重建会把用户正打开的下拉框销毁掉（「点了没反应」） |
| 单软件限额 | 软件行上的「限额…」按钮 → **对话框** | 判定规则只有一处定义（`LimitRules.TryParseDuration`），对话框不做判断 |

阈值输入框在**用户正在输入**时不会被重建覆盖（`IsKeyboardFocusWithin` 守卫）——
否则点一下「刷新列表」就把人打了一半的字冲掉。

## 5. 已知局限（诚实写明）

1. **E / H 两组依赖单实例互斥体**：本机有产品实例在运行时会被 SKIP（既有设计，非缺陷）。
2. **对话框与气泡本身不可被自检覆盖**（需要真的显示窗口 / 真的弹通知）。
   因此对话框被写得很薄（只有小时/分钟两个输入框与三个按钮，判定全在 `LimitRules`），
   但「控件真的被赋值」「气泡真的出现」只能靠人眼 —— 见 §6。
3. **系统「专注助手」可能吞掉气泡**：没有可靠的检测手段，不做假检测。
4. **限额按「今日」**：不提供按周 / 按月（如需要，属新里程碑）。
5. **分类限额要求该软件已归到分类**：未分类软件不计入任何分类限额。
6. **不提供「限额历史」或「被提醒了多少次」的统计**。

## 7. 结论

* **功能**：总 / 单软件 / 分类限额可设、可删、可改；阈值可配置；每秒判定；阈值只提醒一次；
  跨天自动重置；改限额后重新提醒；卡片与主界面都显示；托盘气泡提醒。
* **证据**：构建 **0 错误 0 警告**；`--m9-selfcheck` **153 项通过 / 0 失败**
  （E/H 共 23 项因产品实例占用互斥体按设计跳过）；M1–M7 回归全绿；
  两轮变异测试各命中 **7 / 4** 项，证明新回归**不是空检查**。
* **口径一致性**：限额比的是「今日真实活跃 / 该软件今日时长 / 该分类今日时长」，
  与榜单、卡片、托盘**同源**；锁屏按既有口径完全不计入。
