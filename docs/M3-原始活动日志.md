# M3 增补：原始活动日志（JSONL）

> 日期：2026-10-05　环境：Windows 11 **26H2 / 26300.9457**、`.NET 10.0.12`
> 对应开发文档 §5.4 的增补；依赖 M3 的归属链路（`AppUsageBridge.Observed`）。**不含 M4 存储**——两者分工不同。
> 相关：`docs/M3-验证.md`（M3 主体验证）、`docs/开发文档.md` §5.4。

---

## 1. 为什么需要它：聚合数据的三个盲区

M3 的 `AppUsageTracker` 输出的是**规范化后的聚合结果**（合并键 + 显示名 + 毫秒）。这在“看今天用了什么”上足够，
但对**事后日志分析**有三个盲区：

| 盲区 | 具体表现 |
|---|---|
| **显示名覆盖了原始名** | `devenv` → `Visual Studio`；`ApplicationFrameHost` → `UWP 应用（待修正）`。榜单上**看不到原始名**（只有合并键里藏着小写进程名） |
| **进程名本身已不是“最原始”** | 取自 `Process.ProcessName`，**既丢了 `.exe`、也丢了目录**。两个不同目录下的 `python.exe` 会被合并成一条，事后无法拆开 |
| **逐拍细节随拍丢弃** | 窗口类名、窗口标题、pid、hwnd 只存在当拍内存里；下一拍就被覆盖。因此“某一秒前台到底是谁、当时为什么没计入”**事后无法回答** |

本增补即为此：把**未规范化的原始观测**以追加式文本日志留存，供日后分析、排查 M11 的 UWP 真实名、以及复盘“未知应用”到底是什么。

## 2. 决策（经确认）

| 项 | 决策 |
|---|---|
| **粒度** | **仅变化时记录** —— 前台软件或“是否计入”发生变化时落一行，行内含该状态的**总时长与拍数** |
| **额外字段** | **窗口标题**（首/末 + 变更次数） |
| **启用范围** | **产品默认开启，可关闭** |
| 未采纳（本次） | 完整可执行路径、版本信息（`FileDescription`/`ProductName`）。前者能区分同名程序、后者为 M11 打底，但都要额外读进程模块且对权限受限进程会失败——留待需要时再加 |

> 关键性质：**仅变化时记录**意味着日常只有几百行/天，仍能**完整重建时间线**——
> 因为一行自带 `dur_ms` 与 `ticks`，把同一天所有行的时长相加即等于当日活跃时长（已由验证证实，见 §9）。

## 3. 字段表（一行 = 一段状态）

| 字段 | 含义 | 示例 |
|---|---|---|
| `ts` | 状态**开始**的本地时间（含时区偏移） | `2026-10-05T20:54:34.089+08:00` |
| `day` | 状态所属本地日期（= 分片文件名，保证一行不跨天） | `2026-10-05` |
| `dur_ms` | 本状态累计时长（毫秒，各拍真实间隔之和） | `11000` |
| `ticks` | 本状态包含的拍数 | `11` |
| `seq_from` / `seq_to` | 首/末拍的心跳序号（可与自检日志对齐） | `1` / `11` |
| `counted` | 本状态是否被计入活跃时长 | `true` |
| `reason` | `active` / `idle` / `paused` / `gap` | `active` |
| `kind` | 分类：`app` / `uwp_host` / `desktop` / `shell` / `lockscreen` / `self` / `unknown` / `none` | `app` |
| **`proc`** | **原始进程名**（未规范化、不含 `.exe`） | `devenv` |
| **`cls`** | **原始窗口类名**（状态下首次观测） | `HwndWrapper[DefaultDomain;;f0a15d81-…]` |
| `pid` | 进程 ID（状态下**最近**观测） | `3232` |
| `hwnd` | 窗口句柄（状态下**最近**观测，仅用于跨日志关联） | `0xB0846` |
| `title` / `title_last` | 窗口标题的**首次** / **最后**观测（关闭标题记录时省略） | `ScreenSpy - … - Microsoft Visual Studio` |
| `title_changes` | 状态内标题**变更次数**（0 = 期间未变） | `0` |
| `display` | 规范化显示名（与聚合榜单一致） | `Visual Studio` |
| `merge_key` | 合并键（过滤类为 `#shell` 等） | `devenv` |
| `diag` | 采样问题（仅在非空时出现） | `Win32Exception（pid=…）` |

**首值/末值的取法（刻意如此，避免误导）**：`cls` / `title` 取**首次**观测（说明“切到了什么”），
`title_last` / `pid` / `hwnd` / `diag` 取**最近**观测。

### 3.1 `seq_from` / `seq_to` 指什么

指**这段状态覆盖的心跳序号区间**：`seq_from` = 首拍序号，`seq_to` = 末拍序号。
序号即 `ActivityTick.Sequence`——**进程自启动起从 1 开始、每心跳一次 +1**（默认 1 秒一拍）。

因为本日志是“**仅变化时记录**”：一行 = 一段连续同状态，可能跨很多拍。例如连续 11 拍都是 `devenv`，
就合成一行，`seq_from=1`、`seq_to=11`、`ticks=11`、`dur_ms=11000`。相关字段分工：

| 字段 | 含义 | 单位 |
|---|---|---|
| `seq_from` / `seq_to` | 首拍 / 末拍的心跳序号（离散、可对账） | 拍 |
| `ticks` | 本段拍数，恒等于 `seq_to - seq_from + 1` | 拍 |
| `dur_ms` | 本段真实时长（各拍实测间隔之和） | 毫秒 |

- **`seq_to - seq_from + 1 == ticks` 是一条自洽校验**：若不等，说明跨度内有拍未被观测到。
- **`dur_ms / ticks` = 本段平均心跳间隔**（正常 ≈ 1000ms），可用来判断“心跳有没有被拖慢”。
- **用途一：检测丢行**。队列满时会丢弃并计数，丢行后相邻序号就对不上——
  校验“下一行 `seq_from` 是否恰好 = 上一行 `seq_to + 1`”即可发现。
- **用途二：与其他日志对账**。M2 自检逐拍打印的 `#N` 是同一个序号，
  可用它互查“第 137 拍当时是哪个软件、idle 多少、为什么没计入”。

**两个坑**：①序号**按进程启动重置**，跨运行不可比较（昨天的 5000 与今天的 5000 无关）；
②一行**不跨天**，跨天处会切开，故序号在跨天处仍连续，无需特殊处理。

## 4. 语义要点

### 4.1 状态界定键

```
(counted, reason, kind, merge_key)
```

键不变 → 累加到同一行；键变化 → 关闭上一行、开新行。因此：

- 同一软件连续用 2 小时 → **一行**（`dur_ms ≈ 7200000`）；
- 换软件 / 换分类 / 计入与否变化 / 不计入的原因变化（挂机 ⇄ 暂停 ⇄ 空洞）→ 各切一行。

### 4.2 标题**不**参与状态界定

否则浏览器每翻一页就切一行，日志会被刷爆。代价是“一行只能记首末标题”，
因此额外记录 `title_changes`——它明确告诉你“期间标题变过”，而不会假装标题没变。

### 4.3 跨天与原因优先级

- **一行不跨天**：日期一变先关闭上一行、再开新行；**触发跨天的那一拍整拍归入新的一天**——
  这与 `ActivityScheduler` 的跨天处理（先重置今日累计、再累加本拍间隔）**刻意保持一致**，否则日志与统计会对不上。
- `reason` 优先级：**`paused` > `gap` > `idle`**（锁屏/睡眠期间谈“挂机”没有意义）。

---

## 5. 三条硬约束（绝不拖慢心跳）

日志是**旁路**功能，最坏结果只能是“日志不全”，绝不能是“计时变慢”。

| 约束 | 实现 |
|---|---|
| **永不阻塞** | 心跳线程只做“折叠 + 入队”；队列有界（默认 4096），**满则丢弃并计数**（`Dropped`） |
| **永不抛异常** | 折叠与写盘的所有异常都转成计数与 `LastError`，绝不冒泡到心跳线程 |
| **不阻止退出** | 写盘线程是**后台线程**（`IsBackground = true`） |
| 另 | `Dispose` 会**刷出最后一段未关闭的状态**，否则每次退出都会丢掉尾段 |

分片按**记录自身的日期**（而非写盘时刻）命名，因此跨天时先关闭的尾段仍落到正确的那一天文件。

## 6. 文件位置 / 轮转 / 保留

| 项 | 值 |
|---|---|
| 产品默认目录 | `%LOCALAPPDATA%\ScreenSpy\logs` |
| 开发期入口默认目录 | `artifacts/m3-rawlog`（自检）、`artifacts/demo-rawlog`（卡片演示）——避免开发期污染用户目录 |
| 文件名 | `app-activity-YYYYMMDD.jsonl` |
| 格式 | **JSONL**（一行一个 JSON 对象）、**LF** 换行、UTF-8 **无 BOM**、逐行 Flush |
| 保留期 | **30 天**（按文件名中的日期剪枝，不依赖文件时间戳） |
| 编码器 | `JavaScriptEncoder.UnsafeRelaxedJsonEscaping`——中文标题保持可读（不是 `\uXXXX`）。这里的 “Unsafe” 指 HTML 注入场景；本文件是本地 JSONL、不嵌入 HTML，故可读性收益更大 |

## 7. 隐私（务必知悉）

- 窗口标题**可能包含敏感内容**（网页标题、文档名、聊天对象名），且本文件是**明文**；
- 关闭方式：`ActivityLogOptions.IncludeWindowTitle = false`（字段整体省略），或 `--no-raw-log` 完全关闭；
- 进程名 / 类名 / pid / hwnd **不含**隐私内容，是排查问题的必要信息，故不提供单独关闭。

### 9.5 分析示例（已实测可用）

```powershell
Get-Content 'D:\project\ScreenSpy\artifacts\m3-rawlog\app-activity-20261005.jsonl' |
  ConvertFrom-Json |
  Where-Object { $_.counted } |
  Group-Object merge_key |
  ForEach-Object {
    [pscustomobject]@{
      软件 = $_.Name
      秒   = [math]::Round((($_.Group | Measure-Object -Property dur_ms -Sum).Sum) / 1000, 1)
      段数 = $_.Count
    }
  } | Sort-Object -Property 秒 -Descending
```

## 10. 已知局限（如实声明）

1. **崩溃会丢尾段**：最后一段状态只在“下次变化 / 正常退出（`Dispose`）”时才落盘；进程被强杀时该段丢失（最多一行，量级 = 该状态持续时长）。
2. **长时间不变化 = 一行代表很长时间**：标题只留首末（用 `title_changes` 作为“期间变过”的信号），**不保留完整标题序列**——这是“仅变化时记录”的固有取舍。
3. **不因新增日志而改变归属语义**：同名合并仍按**进程名**，`pid` 只留最近值；因此“两个不同目录的 `python.exe` 合并”这一既有行为**没有变化**（要拆开需启用 §2 未采纳的完整路径字段）。
4. **未记录**完整可执行路径与版本信息（本次未选）。
5. **无独立测试工程**（D12 决策），上述检查为内嵌式，不构成自动化回归保护网。
6. **产品默认路径未经实机验证**：验证全程使用开发目录（`artifacts/*`），
   `%LOCALAPPDATA%\ScreenSpy\logs` 只做了**字符串断言**（A9 的默认选项检查），尚未在真实产品启动流程里落盘——该接线属 M5。
