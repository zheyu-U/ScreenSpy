## 2. 关键设计决策（及理由）

1. **按差值累计，而非每拍固定 +1s**：每拍取 `TickCount64` 与上拍求差并累加**真实间隔**。
   定时器抖动 / 短暂卡顿不产生累计漂移（这是 §5.1 的验收点）。
2. **判定为纯函数 + 时间源可注入**：`ActivityRules` 无 IO、无状态；`ITickSource` / `localNow` / `IIdleClock`
   均可注入，使“阈值边界”“回绕”“跨天”这类**人工无法复现**的场景可被确定性推演。
3. **32 位回绕归一化**：`LASTINPUTINFO.dwTime` 与 `GetTickCount` 同为 32 位 tick（约 49.7 天回绕）。
   实现取 `TickCount64` 的**低 32 位**再做 **uint 无符号减法**，回绕自动正确；
   **反例**：有符号相减在回绕附近得负数 → 被误判成“刚有输入” → 挂机被计时。
4. **判定边界取严格小于**：`idle < 阈值` 才算活跃；恰好等于阈值算挂机，避免阈值处抖动导致一秒两判。
5. **暂停位预留**：`ActivityScheduler.Paused` 供 M2 锁屏/睡眠复用，避免届时改动心跳结构。
6. **心跳在线程池，属性加锁；事件在锁外触发**：避免调用方回调里再取锁造成死锁；
   心跳内异常不外泄（记录到 `LastError`），保证常驻进程不因单拍异常崩溃。

## 4. 过程中发现并修复的缺陷（重要）

**症状**：演示卡片里调度器“3 秒后仍是 0 拍、今日 0.0s”；而自检里同样的调度器正常（15 拍）。
诊断显示“定时器回调 3 次、成功心跳 0 拍、无异常”——回调进了处理函数，却从未累加。

**根因（C# 语义）**：

```csharp
Ticked?.Invoke(ProcessHeartbeat());   // 错误
```

**空条件调用 `a?.M(arg)` 的实参，只在 `a` 非 null 时才求值**。
演示卡片**没有订阅 `Ticked`**，于是 `ProcessHeartbeat()` **从未被调用** → 心跳完全不累计。
自检里订阅了 `Ticked`，所以它**能通过**——这正是该缺陷躲过自检的原因。
在产品里这是**致命**的（若无人订阅事件，计时恒为 0）。

**修复**：先求值再抛事件。

```csharp
ActivityTick tick = ProcessHeartbeat();   // 正确：无论如何都先求值
Ticked?.Invoke(tick);
```

**回归保护**：`M1SelfCheck` 新增“**无订阅者**”用例（`Pump()` 路径刻意不订阅任何事件），
断言此时心跳仍累计、回调计数正确、无异常。

## 5. 已知局限（如实声明）

1. **无测试工程**（按既定决策：不建 `ScreenSpy.Tests`）。因此“阈值边界 / 32 位回绕 / 跨天”
   由 `--m1-selfcheck` 的**内嵌**确定性检查覆盖，**没有自动化回归保护**；将来若需要，须先抽接口再建测试工程。
2. **真实采样本轮未触发挂机分支**（`idle` 始终 ≈0s）。挂机、暂停、边界、跨天**已由 A 段确定性检查覆盖**，
   但“真实静置 5 分钟不计时”（§5.2 验收、§9-1）**需要人工静置**，尚未做。
3. **“运行 10 分钟无内存增长、tick 无漂移”（§5.1 验收）尚未做长跑**。
   当前只做了 6s 采样的漂移度量；`ActivityTick` 为 `readonly struct`、心跳无堆积，
   设计上利于该验收，但**未经实测**。
4. 真实采样中的 −990.6ms 尾段偏差见 §3.2 说明。
