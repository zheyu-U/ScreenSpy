## 3. 设计决策与踩过的风险（重点）

### 3.1 ⚠️ 跨天顺序陷阱 → 存储**不读内存榜单**

调度器 `ProcessHeartbeat` **先**触发 `DayRolled`（`AppUsageBridge` 收到后立即清空榜单）、**后**触发 `Ticked`；
C# 事件按订阅顺序调用，M4 必然**晚于**清空。

> 若采用「到点去读一眼榜单再写库」，午夜那一拍会读到**已清空的新一天**，昨天的尾段**永久丢失**。

**对策**：存储自己在每拍观测里按**该拍携带的本地日期**（`ActivityTick.LocalTime`）累加增量，
与榜单清空**完全解耦**；跨天天然写成两行，无需任何特殊处理。（A 段「跨天分行」为专门回归。）

### 3.2 ⚠️ 秒级取整会累积漂移 → **余数结转**

schema 是 `seconds INTEGER`，每拍是毫秒。若每拍各自取整成秒再累加，每拍最多丢 0.5 秒。

**对策**：内存按**毫秒**累加，落库只写**整秒**，不足 1 秒的余数**留在内存继续攒**。
实测（A 段）：每拍 900ms、**逐拍 flush**、共 10 拍 → 库中恰为 **9 秒**、余数 **0**，无漂移。
另有「900ms 不落库 → 补 100ms 后落 1 秒」的结转回归。

### 3.3 写入模型：**增量累加 + 单事务 + 成功后才扣减**

- SQL：`INSERT ... ON CONFLICT(date, app_name) DO UPDATE SET seconds = seconds + excluded.seconds`
- 一个 flush = 一个事务；**提交成功后**才从待写缓冲区扣减；失败则**原样保留**、下一轮重试。
- 因此写盘失败**不会丢数据**，也不会把已有数据改小（对比「绝对值覆盖」模型：一旦内存总量算错会把数据改小，属静默毁数据）。
- 唯一可能丢的是「尚未 flush 的内存增量」，上限即 flush 间隔（§5.6：断电最多丢 15 秒）。

### 3.4 SQL 语义坑：`limits` 的 `target` 用**空串**而非 `NULL`

SQLite 的 UNIQUE / PRIMARY KEY 认为 **NULL 之间互不相等**，
若 `scope='total'` 时把 `target` 存成 `NULL`，`ON CONFLICT(scope,target)` **永远匹配不上**，
每次写入都会**新增一行**而不是更新。故规定：**total 用 `""`**，并在建表时写成 `NOT NULL DEFAULT ''`。
（A 段专门回归：`total` 连写两次只保留一行。）

### 3.5 线程与退出

- 心跳线程只做**入队**（有界队列、`TryAdd(...,0)`、**永不阻塞、永不抛异常**，满则丢弃并计数）。
- 唯一的聚合者与写盘者是**后台线程**；`_flushGate` 串行化 flush，避免「后台线程收尾」与「Dispose 兜底」把同一份数据写两遍。
- `Dispose`：`CompleteAdding` → `Join(5s)` → 兜底再 flush 一次 → 仅在后台线程确已退出时释放队列。

### 3.6 启动续算的语义边界

基线存入 `Bucket.SeedMilliseconds`（独立字段），**不计入** `AttributedTotal`。
于是两件事同时成立：榜单显示**今天一整天**；而**时间守恒不变量**仍只描述**本次运行**，不被历史数据污染。
（A 段回归：「续算不污染时间守恒」。）

## 4. 数据库 schema（`PRAGMA user_version = 2`）

> 🔄 **2026-10-06（schema v1 → v2）**：新增 `daily_activity`，用于修复“重启后今日真实活跃变小”的口径缺陷。
> 迁移是**纯增量**的（`CreateSchema` 全部 `IF NOT EXISTS`），旧库升级只是多建一张空表，**不改动、不丢失**任何既有数据。

```sql
CREATE TABLE IF NOT EXISTS app_usage (
    date      TEXT    NOT NULL,           -- 'YYYY-MM-DD'
    app_name  TEXT    NOT NULL,           -- 合并键（进程名小写）
    seconds   INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY (date, app_name)
);

-- 2026-10-06 新增：每天“不计入使用时长 / 无前台·未知”的秒数。
-- 与 app_usage 分开 → app_usage 保持“纯软件”，Top 排名与占比分母不被污染。
-- 锁屏不在此表（按口径完全不计入，既不展示也不续算）。
CREATE TABLE IF NOT EXISTS daily_activity (
    date                 TEXT    PRIMARY KEY,           -- 'YYYY-MM-DD'
    filtered_seconds     INTEGER NOT NULL DEFAULT 0,    -- 桌面 / 外壳 / 自身
    unattributed_seconds INTEGER NOT NULL DEFAULT 0     -- 无前台 / 未知
);

CREATE TABLE IF NOT EXISTS settings (
    key   TEXT PRIMARY KEY,
    value TEXT
);

CREATE TABLE IF NOT EXISTS limits (
    scope   TEXT    NOT NULL,             -- 'total' 或 'app'
    target  TEXT    NOT NULL DEFAULT '',  -- app 时为软件键；total 时为空串（见 §3.4）
    seconds INTEGER NOT NULL,
    PRIMARY KEY (scope, target)
);
```

- `app_name` 存**合并键**而非展示名：展示名会随版本变化的映射表而变，存库会分叉；
  读取时用 `ForegroundAppRules.NormalizeDisplayName` **现算**（`devenv` → `Visual Studio`，已实测）。
- WAL：文件级持久属性，只在 `Initialize` 设置一次；`busy_timeout` / `synchronous` 是连接级，每次开连接重设。
- 每条操作开一条连接（依赖连接池）——SQLite 连接非线程安全，此方式比手工维护长连接 + 锁更不易出错。

## 7. 已知局限（如实声明）

1. **断电丢尾段**：未 flush 的内存增量（≤ flush 间隔）会丢。这是 §5.6 明确接受的取舍；实测该窗口为 1s 量级。
2. **单实例假设**：写入是「增量累加」，两个进程同时对同一库写入会**互相累加**（结果偏大）。产品需单实例（M12 自启时一并处理）。
3. **续算只覆盖「今日」**：重启只回灌当天数据（历史日期保留在库中，供 M10 的 7 天柱状图使用）。
4. **展示名不落库**：见 §4；重启后对**未知**软件会短暂显示为进程名（合并键），下次它成为前台即恢复友好名。
5. **`settings` / `limits` 只建了表与读写 API**：卡片坐标接线属 M8，限额引擎与提醒属 M9；本里程碑不消费它们。
6. **产品库路径仅在自检里做了字符串断言**：真正的「产品启动时打开默认库」接线属 M5。
7. `FailNextCommits` 是**仅供自检**的故障注入开关（`internal`），生产代码永不设置。

## 9. 与开发文档的差异修正

| 项 | 原文 | 现文 | 原因 |
|---|---|---|---|
| 库路径 | `%AppData%\ScreenSpy\data.db` | `%LOCALAPPDATA%\ScreenSpy\data.db` | Roaming 会被域账户同步，数据库不宜漫游 |
| `limits.target` | `TEXT`（可空） | `TEXT NOT NULL DEFAULT ''` | NULL 不参与 UNIQUE 匹配，会导致 upsert 退化为「每次新增一行」 |
| 写入策略 | 「每 15 秒批量 flush」 | 已实现：15s + **切换软件强制** + **退出强制** + 余数结转 + 失败重试 | 落地细节 |
