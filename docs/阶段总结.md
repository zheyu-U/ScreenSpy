## 1. 项目定位（一句话）

常驻 Windows 后台的小工具：统计**真实活跃使用时长**（剔除挂机 / 锁屏 / 睡眠），**按软件分别统计**，
以**半透明极简卡片**贴附在桌面展示，并提供**每日总限额 + 单软件限额**提醒（80% / 100% 阈值，去重只提醒一次）。
个人自用，**纯提醒、不锁屏**；**不做多显示器**。

## 3. M0：一次"证伪"与一次"翻案"

### 3.1 路线 A（真嵌入 `WorkerW` / `Progman` 子窗口）失败

**症状**：窗口**从未上屏**，但所有 API 全绿——典型的**假阳性**。

| 原判定项 | 实际证明了什么 |
|---|---|
| `SetParent` 返回非零 / `GetAncestor(GA_PARENT)` 等于目标 | 窗口树关系改成功了 |
| `IsWindowVisible == true` | `WS_VISIBLE` 位置位了 |
| `UpdateLayeredWindow` 返回 true | 位图写进了分层表面 |
| 连续提交 N 帧无异常 | 循环没抛异常 |

**客观证据**（7 个纯色探针 + 截屏像素判定）：唯一可见的是**顶层对照探针 P0**；
所有子窗口探针（分层 / 不透明 × WorkerW / Progman）**均为 0 像素**。

**根因**：`Progman` 扩展样式含 **`WS_EX_NOREDIRECTIONBITMAP`**，由 **DirectComposition** 呈现；
**第三方子 HWND 不在其合成树内 → 永不上屏**。（`DWMWA_CLOAKED` 全为 0，说明不是"遮盖"机制。）

**附带修正**：26H2 上 `SHELLDLL_DefView`（图标层）**直接是 `Progman` 的子窗口**；
壁纸层是 `Progman` 的全屏子 `WorkerW`；**不存在**旧文档 §5.8 说的"顶层同级 `WorkerW`"。

### 3.2 翻案：求证 Rainmeter 源码

**Rainmeter 根本不用 `SetParent`（全仓库 0 次桌面嵌入调用）**。它的做法是：

- 顶层窗口 `WS_POPUP` + `WS_EX_LAYERED | WS_EX_TOOLWINDOW`，`UpdateLayeredWindow(ULW_ALPHA)` 渲染；
- `SetWindowPos(hwnd, HWND_BOTTOM, …)` 压低，并在 `WM_WINDOWPOSCHANGING` 里
  **强制 `SWP_NOZORDER` 自锁 z 序**；
- 用隐藏 helper 窗口做 z 序探针，**检测「显示桌面」状态**，
  一旦发现桌面被抬起，就把自己**插回桌面宿主之上、topmost 带之下**（250ms 常态 / 100ms 显示桌面期间）。

**关键洞察**：它**不是阻止最小化**，而是**z 序复位**。

### 3.3 定案：路线 B+（已通过客观验证）

| 机制 | 落地 |
|---|---|
| z 序自锁 | `WM_WINDOWPOSCHANGING` → `flags \|= SWP_NOZORDER` |
| 隐藏探针窗口 | 用于 z 序探测（`HWND_BOTTOM`，不建表面） |
| 显示桌面检测 | **`显示桌面 ⟺ HostZ < ProbeZ`** |
| 复位 | 正常→`HWND_BOTTOM`；显示桌面→`TOPMOST` 后 `NOTOPMOST`（插到 topmost 带之下） |
| 事件加速 | `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)` |
| 采样密度 | 250ms ⇄ 显示桌面期间 100ms |
| 窗口样式 | `WS_POPUP` + `WS_EX_LAYERED \| TRANSPARENT \| NOACTIVATE \| TOOLWINDOW` |

**验证结果（两轮一致，判据为截屏像素）**：

| 步骤 | 标记像素 | `IsIconic` | ShowDesktop | z(Host/Probe/Card) |
|---|---:|---|---|---|
| S1 基线 | 576 | False | False | 161/159/160 |
| **S2 Win+D** | **576** | **False** | **True** | **15/161/14** |
| S3 还原 | 576 | False | False | 161/159/160 |
| S4 不透明窗口压上 | 0 | False | False | 161/159/160 |
| S5 撤遮挡 | 576 | False | False | 161/159/160 |

**需求达成**：卡片在桌面 ✅ / 会被其它窗口覆盖 ✅ / **Win+D 不最小化 ✅**；
另有**鼠标穿透**（`WS_EX_TRANSPARENT` + 命中测试返回桌面 `SysListView32`）、
**任务栏与 Alt+Tab 隐藏**（`TOOLWINDOW` 且无 `APPWINDOW`）、**Win+D 还原无残影**（S3 与 S1 包围盒一致）。

## 4. M1：计时调度器 + 空闲检测

**产物**：`Collector/`（`IIdleClock`、`Win32IdleClock`、`ActivityRules`）
+ `Scheduling/`（`ITickSource`、`ActivityTick`、`ActivityScheduler`）。

**要点**：

- 每秒心跳，**按 `TickCount64` 差值累计**（而非固定累加）→ 抗定时器抖动与卡顿；
- 空闲 ≥ 阈值（默认 300s）判为挂机，该拍不计入；跨天自动重置；
- **32 位 tick 回绕归一化**（`LASTINPUTINFO.dwTime` 用无符号减法）；
- `ActivityTick` 为 `readonly struct`，避免每秒堆分配。

**验证**：`--m1-selfcheck` → **19 项确定性检查全部通过** + 真实采样无累计漂移。

**修复的唯一实质 bug**：`Ticked?.Invoke(ProcessHeartbeat())` ——
C# 中**空条件调用的实参只在接收者非 null 时求值**；无人订阅 `Ticked` 时
`ProcessHeartbeat()` **从未执行 → 心跳完全不累计**。自检因恰好订阅了事件而躲过；
已改为"先求值再抛事件"，并新增"无订阅者"回归检查。

## 5. M2：锁屏 / 睡眠监听

**三条防线**（单一手段都不够可靠）：

1. **事件（主路径）**：`SystemEvents.SessionSwitch` + `PowerModeChanged` —— 及时，但可能漏发；
2. **探测（初值 + 自愈）**：WTS 读 `SessionFlags`，兜住「启动即锁屏」（事件不补发）
   与「**解锁事件丢失**」（会**永久少计**，最危险的方向）；**探测不确定时绝不动状态**；
3. **时间空洞**（与事件无关的客观护栏）：单拍间隔 > 60s 一律不计，
   兜住 S0 新式待机下 `Suspend` 事件可能缺失的情况。

锁屏与睡眠用**两个独立标志位**：重叠时（锁屏后合盖、醒来先 Resume 再解锁）只要有一个为真就持续暂停。

**本机测不出、值得记的两个缺陷**：

1. `WTSINFOEX.SessionId` **不紧跟 `Level`**（实测 `Level@0`、4 字节填充、`SessionId@8`）
   → 改为**自定位 + 交叉校验**（用 `WTSSessionId` + `WTSConnectState` 验证候选位置）；
2. 由此引出的**会话号=1 错位陷阱**（与 `Level=1` 同值 → 每台会话号为 1 的机器探测恒错）
   → 候选偏移必须 ≥ 4，并加两条回归检查。

**睡眠测试（`--sleep-test`）**：**先拿"保命绳"再睡** ——
`SetWaitableTimer(fResume:TRUE)` 绝对 UTC 到期自动唤醒，注册失败即中止；
启用 `SE_SHUTDOWN_NAME` 并二次校验；**入睡前日志刷盘**；判定写成 6 项独立指标 + 纯逻辑规则。

**验证**：`--m2-selfcheck` → **51 项确定性检查全部通过**（42 + 9 项睡眠判定）+ 真实 WTS 探测与事件订阅正常。

## 6. M3：前台进程识别 + 过滤（2026-10-05 完成）

**产物**：`Collector/ForegroundAppRules.cs`（分类 / 过滤 / 规范化 / 合并键，**纯逻辑**）、
`ForegroundAppSample.cs`、`IForegroundAppSource.cs` + `Win32ForegroundAppSource.cs`（采样源）、
`AppUsageTracker.cs`（**按软件累计 + 时间守恒**计数）、`AppUsageBridge.cs`（**旁听**心跳，不侵入 M1/M2）、
`Demo/M3SelfCheck.cs`（`--m3-selfcheck`）、`Demo/AppLiveCardData.cs`（`--demo-card --m3`）。
详见 `docs/M3-验证.md`。

**要点**：

- **过滤**：桌面（`Progman` / `WorkerW` / `SysListView32` …）、系统外壳（任务栏 / 开始菜单 / 搜索 / 输入法）、
  锁屏（`LogonUI` / `Winlogon` / `LockApp`）、**自身**（按 pid 比较）；
- **分类优先按窗口类名**：`explorer.exe` **不**一律过滤 —— 它的文件管理器窗口（`CabinetWClass`）
  是真实应用，必须计入；
- **同名合并**：按**进程名**（跨 pid 合并 Chrome 的多子进程），**不用窗口标题**；
- **取不到就不猜**：无前台窗口 → `None`；取不到进程名（权限受限/进程已退出）→ `Unknown`，
  二者都**不计入任何软件**但分别计数；
- UWP 宿主 `ApplicationFrameHost` **先计入**（记为“待修正”）并单独计数，精确名留到 M11（§5.5）；
- **时间守恒**：`已归因 + 已过滤 + 未归因 == 调度器今日活跃`，必须**毫秒级精确**——
  一次性覆盖“漏记 / 重复记 / 单位错”三类问题。
- **原始活动日志（M3 增补）**：`Logging/` 以 JSONL 保留**未规范化**的进程名 / 窗口类名 / 窗口标题 / pid / hwnd，
  **仅变化时记录**（一行 = 一段状态，含 `dur_ms` 与 `ticks`）、按天分片、保留 30 天；产品默认开启、可关闭。
  另有一条不变量：**一天的原始日志行时长之和 == 当日活跃时长**（真实观察已验证）。
  详见 `docs/M3-原始活动日志.md`。

**验证**：

- **80 项确定性检查全部通过**（分类与过滤 11 / 规范化与合并键 7 / 累计与守恒 10 /
  Top 排序与稳定性 4 / UWP 2 / 未计入拍 4 / 跨天 4 / **端到端守恒 10** / **原始活动日志 25**）；
- **真实观察 15 s 通过**：16 次采样、15 次心跳全部归到 Visual Studio、取样失败 0、
  **守恒差 0 ms**、已过滤 0；
- `--demo-card --m3 --win-d` 卡片实测：**Win+D 期间前台=桌面，被正确计入“已过滤 1 s”**，
  截图显示「正在使用：桌面」「已过滤 0:01」「Visual Studio 0:04」，且 `0:04 + 0:01 = 今日 0:05`。

**已知局限**：UWP 真实名待 M11；权限受限进程记“未知”（不记错）；应用名映射表为小规模内置表
（未映射时退回进程名，不漏统计）；§5.4 的“切换软件各停留 1 分钟”仍建议由人工做一次长时对照。

## 6b. M4：SQLite 存储 + 批量 flush（2026-10-05 完成）

**产物**：`Storage/StorageOptions.cs`、`Storage/UsageDelta.cs`、`Storage/SqliteStore.cs`、`Storage/AppUsageStore.cs`、`Storage/UsageSeeding.cs`、`Collector/AppUsageSeed.cs`、`Demo/M4SelfCheck.cs`；配套改动 `ScreenSpy.csproj`（加 `Microsoft.Data.Sqlite` 10.0.12）、`App.xaml.cs`（加 `--m4-selfcheck` 路由）、`Collector/AppUsageTracker.cs`（**加法式** `Seed`）。详见 `docs/M4-验证.md`。

**要点**：

- **不每秒写盘**：心跳线程只**入队**（有界队列、永不阻塞、满则丢弃并计数）；真正的聚合与写盘在**后台线程**；
  **每 15s 批量 flush + 切换软件强制 flush + 退出强制 flush**。
- **余数结转（零漂移）**：内存按**毫秒**累加、只落**整秒**，不足 1 秒的余数留在内存继续攒（实测：10 × 900ms 逐拍 flush 恰为 **9 秒**）。
- **增量累加 + 单事务 + 成功后才扣减**：写盘失败**不丢数据**、也不会把已有数据改小（故障注入已验证：失败后待写原样保留、重试补齐）。
- **不读内存榜单**（关键）：调度器跨天**先** `DayRolled`（榜单清空）**后** `Ticked`，
  “到点读榜单再写库”会**永久丢掉昨天尾段**；故存储按**每拍自身的本地日期**累加增量，跨天天然写成两行。
- **启动续算**：开机把库中「今日 × 每软件」读回灌入榜单基线；基线**独立存放、不计入时间守恒不变量**。
- **踩坑**：`limits.target` 原设计可空，但 SQLite 认为 **NULL 之间互不相等**，
  `ON CONFLICT(scope,target)` 在 `total` 时**永远匹配不上**（upsert 退化成每次新增一行）→ 改 `NOT NULL DEFAULT ''`。

**验证**：

- **36 项全部通过**（A 确定性 34：schema/版本 2、幂等 1、增量 upsert 1、settings/limits 4、**余数结转 5**、
  攒与结转 2、**跨天分行 2**、**切换强制 flush 1**、**重启后仍在 1**、**续算 4**、**写失败不丢数据 3**、队列满 2；
  B 真实 2）。
- **B 段真实观察（15 秒，flush 间隔取文档默认 15s）**：
  `t=5s/10s` 时**落库 0s、待写 5000/10000ms**（证明确实在批量攒）；`t=15s` flush 一次写入 14s；
  **关闭后重开读出 15s** —— §5.6 验收达成，同时量化断电窗口（关闭前待写 1s ≪ 15s 上限）。

**已知局限**：断电丢尾段（≤ flush 间隔，实测 1s 量级，为 §5.6 明确取舍）；**单实例假设**（两进程同写会互相累加，需 M12 保证单实例）；
续算只覆盖当天；展示名不落库（重启后未映射软件短暂显示为进程名）；`settings`/`limits` 只建表与 API（接线属 M8/M9）。

退出时 flush 尾段；覆盖开关（`--data-dir` 等）注入，未知参数当警告显示。

**验证**：构建 **0 错误 0 警告**；M1 / M2 / M4 自检回归全通过；
单实例提示实测存在（`#32770` 对话框自 0.5s 持续到 10.1s）且**未误建数据库**；
**端到端实测 `devenv` 归属并写进 SQLite**（库文件含 `app_usage` 表与字符串 `devenv`）；
日志目录不可写时程序与落库均照常；无参数启动成功创建 `%LOCALAPPDATA%\ScreenSpy\data.db` 与 `logs\app-activity-*.jsonl`；
关闭窗口触发尾段 flush（库 4096 → 28672 字节）。

**新教训（第 14 条）**：**“能启动”与“看得见在启动”是两件事** —— 采集链路接进产品后若界面不动，
就只能靠翻库文件确认有没有生效；把状态做成可见面板，才让“接线是否成功”变成一秒内可判断的事。

## 8. 核心教训（跨 M0–M5 复用）

1. **API 全绿 ≠ 像素上屏**——判据必须落到像素 / 命中测试；
2. **不要嵌入桌面树**（26H2 是 DComp 呈现，第三方子窗口不上屏）；
3. **Win+D 免疫靠 z 序复位，不是阻止最小化**；
4. **不要用"读源码推断"替代"实测"**（照抄的判据极性曾出错）；
5. **本机测不出的 bug 靠"换个环境会怎样"发现**（WTS 会话号 = 1）；
6. 判定嵌入**不能用 `GetParent`**（带 `WS_POPUP` 时返回 owner）→ 用 `GetAncestor`；
7. `SetParent` 不会自动把 `WS_POPUP` 改成 `WS_CHILD`；
8. `WindowFromPoint` 不可靠（已弃用），改用像素 + z 序枚举；
9. 像素判定必须先校验"桌面是否可见"，否则会得出假结论；
10. **空条件调用的实参只在非 null 时求值**（`a?.M(f())`）——无人订阅即静默不执行；
11. **自检的前提若与真实场景不同，就会掩盖缺陷**（M1 的订阅差异）；
12. **“保留原始信息”与“聚合展示”是两层，必须分开存**——聚合为了可读性必须规范化（`devenv` → `Visual Studio`），
13. **（M4）持久化订阅者不要依赖别人的内存状态。** 跨天时调度器**先清榜、后发拍**，而事件按**订阅顺序**调用 —— “到点去读一眼榜单再落库”会拿到**已清空的新一天**，昨天尾段**永久丢失**。要落盘就按**拍自身的日期**自己累加。
    但原始层一旦丢失就永远补不回来；这个取舍应当**显式决策**，而不是让聚合顺手把原始数据吃掉（M3 增补的原始活动日志）。
14. **（M5a）“能启动”与“看得见在启动”是两件事** —— 采集链路接进产品后若界面不动，就只能翻库文件确认；
    把状态做成可见面板，才让“接线是否成功”变成一秒内可判断的事。
15. **（M5b）不要用语义模糊的便捷属性去判定状态** —— `Process.MainWindowHandle` 在同一次运行里先报 0、后报非零
    （它会挑“当前可见的顶层窗口”）；改用 `EnumWindows` 直接列出全部顶层窗口后，结果 2/2 稳定。

## 12. 2026-10-06 追加：活跃口径统一（并修复“重启后今日变小”）

### 12.1 发现的缺陷（“不报错”的那一类）

M4 的启动续算只读 `app_usage`（**纯软件**），而“桌面 / 外壳 / 自身”与“无前台 / 未知”这两类
**从来只存在内存**。于是同一天重启后，主界面大字号、卡片、托盘 tooltip 的“今日”会
**凭空变小**（丢掉桌面停留、任务栏那一段）—— 不崩溃、不告警，只是数字悄悄变小。
（当时 `ProductRuntime` 的注释还写着“含被过滤/未归因”，说明是**知情的局部取舍、但没写出后果**。）

### 12.2 定稿口径（用户确认）

| 类别 | 归类 | 计入“今日真实活跃” | 落库去处 |
|---|---|---|---|
| `App` / `UwpHost` | 已归因（软件榜） | ✅ | `app_usage` |
| `Desktop` / `Shell` / `Self` | **不计入使用时长** | ✅ | `daily_activity.filtered_seconds` |
| `None` / `Unknown` | **无前台 / 未知** | ✅ | `daily_activity.unattributed_seconds` |
| `LockScreen` | **锁屏（剔除）** | ❌ 完全不计入 | 不落库 |

- 守恒等式扩为**四项**：`已归因 + 不计入使用时长 + 无前台/未知 + 锁屏剔除 == 被计入的活跃`。
- `TodayTotal = 本次运行 − 锁屏剔除 + 库中基线`（锁屏 / 睡眠**完全不计入**）。
- 显示：主面板新增一行标记；卡片新增两行小字（**为 0 时隐藏**）。

### 12.3 改动与验证

- 代码：`AppUsageTracker`（锁屏剔除桶 + 基线两个分量）、`ForegroundAppSample`（`IsFiltered` 收窄 + 新增 `IsLockScreen`）、
  `SqliteStore`（schema **1→2**，新增 `daily_activity`，与 `app_usage` **同事务**写入）、
  `AppUsageStore`（非软件增量也入队落库）、`UsageSeeding` + `ProductRuntime`（一并续算）、
  `RuntimeStatus`（`LockExcluded` / `DayFiltered` / `DayUnattributed`）、`MainWindow`、`CardModel` / `CardRenderer` / `CardData`。
- 迁移是**纯增量**（全部 `IF NOT EXISTS`），旧库只多一张空表，**不改动、不丢失**既有数据。
- 自检：**M3 77→80 / M4 30→36 / M6 36→41**，M1 / M2 / M5b 回归全通过；构建 **0 错误 0 警告**。（其后见 §13：M6 又追加 D 组，达 **52 项**。）
- 变异测试：M4 改回“丢弃非软件增量” → **恰好 4 项 FAIL**；M6 让 `TodayTotal` 不扣锁屏剔除 → **恰好 1 项 FAIL**。均证明回归不是空检查。

### 12.4 教训（第 16 条）

**“展示口径”与“持久化口径”必须同源**：只要“算进去的”和“存下来的”不是同一组，
重启 / 跨天 / 降级这些边界上就会安静地对不上。凡是进入对外数字的量，都要问一句
“**它落库了吗？续算时灌回来了吗？**”

- **过程中修掉的两个问题**：

  2. **自检自身的同义反复**（由变异测试揭穿）：`--m7-selfcheck` 第一版用**产品常量**断言键名，于是把常量改名后“测试跟着一起改”，仍然全绿；改成**字面量**后才咬住。

- **待人工**：`SWP_FRAMECHANGED` 的有效性**无法在进程内断言**（命中测试由我们自己的 `WndProc` 应答），必须人眼确认「嵌入形态下鼠标穿透到桌面图标 / 浮动形态下能真的拖动窗口」（清单见 `docs/M7-验证.md` §7）。
- **第 17 条教训**：**与“外部契约”有关的断言必须钉死字面量，不能引用实现侧的常量** —— 引用常量的断言会在常量被改名时跟着一起改，从而**永远通过**（“测试自己证明自己”）。
  它与“**不要**在测试里另抄产品的字面量”并不矛盾：后者针对**行为**（期望值应与产品输出同源，例如行名与列宽），前者针对**契约**（键名 / 协议字段这类对外承诺，必须由测试独立钉死）。分界是：**改错了会不会有外部影响** —— 没有就同源，有就必须独立。

## 15. 2026-10-06 追加（四）：M7 第二轮 —— 两个入口的分工与互斥

- **起因（用户提问）**：「`调整位置` 和 `切换为浮动窗口` 背后逻辑是否一样？」—— 核对后：**底层是同一个机制**（都走 `CardWindow.SwitchMode` → `WM_APP` → 卡片线程 → `ApplyMode`，只有一份实现、一份坐标），但**上层是两个不同动作**：调整是**临时插曲**（不改常态，结束时报坐标再回常态），切形态是**改常态本身**（只有切换真的成功才写库）。
- **顺带发现的实现缺陷**：`IsAdjusting => Mode == Floating`。对**常态就是浮动**的用户恒为真 → 被判成“永远在调整中”：「调整位置」永远显示“完成调整”，而“调整中要禁用的形态按钮”会被**永久禁用**（**再也切不回嵌入**，且不报错）。修法：`IsAdjusting` 读独立的 `_adjusting` 标志，新增 `CanAdjust`；形态按钮改读**常态**（`RestingMode`）而不是当前形态。
- **用户决定**：调整位置时**禁用另一个按钮**。落地为一条纯函数规则 `ComposePositionControlAvailability`：**调整中禁用形态按钮**（否则会绕过「完成调整」的坐标上报，最多约 1 秒静默偏差，且会把临时浮动变成永久常态）；**常态为浮动时禁用「调整位置」**（那时卡片随处可拖，点了无事可做）。托盘「调整组件位置」在常态为浮动时同样**禁用**。
- **兜底**：`App.ToggleCardMode` 开头先 `EndAdjust()` 再改常态（双重保险）。
- **验证**：`--m7-selfcheck` **78 项全部通过**（新增 D 组 14 项）；回归 6 项全绿；构建 0 错 0 警；本轮两轮变异测试分别命中 **2 项** / **4 项** FAIL。
- **实测补充**：`ToolStripItem.PerformClick()` 在 `Enabled=false` 时**不触发** Click —— 此前只是“以为如此”，本轮由自检实测确认。
- **第 18 条教训**：**当两个概念只在“常见情况”下重合时，必须各记一份状态，不要用一个表达式去推另一个**。`调整中` 与 `当前是浮动` 在常态嵌入时恰好等价，于是这个错只在一种用户配置下显形，而且不报错、只是把人困住。
- **待人工**：按钮“禁用”只断言到纯函数那一层（不验 WPF `IsEnabled` 真被赋值）；`SWP_FRAMECHANGED` 的有效性同样只能人眼确认。清单见 `docs/M7-验证.md` §7。
