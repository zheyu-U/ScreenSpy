## 4. 关键设计

### 4.1 “绑定”怎么实现：一个委托 + 每秒拉取

本项目**不使用 WPF 数据绑定**（全库唯一的 `Binding` 字样，是一句“不用绑定”的注释）。卡片的“绑定”是：

```csharp
// CardWindow 构造时接受取数函数；Draw() 每秒调用一次
CardModel model = _modelFactory();
_renderer.Draw(host.Surface.Graphics, host.Surface.Size, model);
host.Surface.Present(host.Handle, null, null);   // 逐像素上屏
```

产品侧传入的实现是 `App.BuildCardModel`：

```csharp
return CardData.FromStatus(runtime.Snapshot());
```

即**复用组合根的状态快照**。三个好处：

1. `Snapshot()` 已把所有跨线程读取收敛成一次平面拷贝，且**永不抛异常** —— 卡片线程每秒调它很安全；
2. 卡片与主界面、托盘消费的是**同一份口径**，不会三处数字互相打架；
3. 与 M5a 确立的既有约定一致（UI 只消费快照，不直接触碰组件）。

### 4.2 “今日”口径：派生值必须是计算属性

原先 `RuntimeStatus` 只有 `TodayActive`（本次运行），而 Top5 来自被 `Seed` 灌过基线的 tracker（今天一整天）。
于是**重启后大字号显示 0:00:xx 而 Top5 有数小时** —— 不崩溃、不报错，纯粹在骗人（与 M5b 修掉的 `Paused` 同类）。

修法：新增 `TodayTotal`，并**做成计算属性**：

```csharp
public TimeSpan TodayTotal => TodayActive + Seeded;
```

> 为什么不做成可写字段：第一版实现里它是字段、由 `ProductRuntime.Snapshot()` 赋值，
> 自检立刻 FAIL —— 手工构造的 `RuntimeStatus`（只设 `TodayActive`/`Seeded`）会得到 `0:00`。
> 这正说明**派生值一旦变成可写字段，就会有人忘了填**，而且忘了填不报错。
> 计算属性让它永远与两个来源一致。

保留下来的语义边界：`TodayActive` 仍是“本次运行”，M3 的**时间守恒等式仍只描述本次运行**
（基线不计入 `AttributedTotal`），因此主界面的守恒一行明确标注了“本次运行”。

### 4.3 可交互与可拖动

- 样式只用 `WS_EX_LAYERED | WS_EX_TOOLWINDOW`：前者是逐像素 alpha 的唯一途径，
  后者让组件不占任务栏/Alt+Tab；**故意不加** `TRANSPARENT`（穿透）与 `NOACTIVATE`（不可激活）。
- 拖动不自己处理 `WM_MOUSEMOVE`，而是让 `WM_NCHITTEST` **整窗返回 `HTCAPTION`**，拖动交给系统代劳 ——
  最小代码、标准行为，且**可以在进程内客观断言**（`SendMessage(WM_NCHITTEST)` 的返回值）。

### 4.4 一个容易踩的坑：位置不能被每帧重绘拽回

`LayeredSurface.Present(hwnd, x, y)` 内部是 `UpdateLayeredWindow` 带 `pptDst`，
**每帧都会按指定坐标移动窗口**。对桌面形态（B+）这是正确的；对可交互形态则意味着
“用户刚拖走，下一秒就被拽回原位”。

因此 `CardWindow` 采用：`SetWindowPos` 定位一次 + 每帧 `Present(handle, null, null)`（`pptDst = NULL`，只更新内容）。

### 4.5 生命周期与释放顺序

- 卡片在**独立 STA 线程**上创建窗口并跑消息循环（`WM_TIMER` 与拖动都依赖消息泵）；
- `Start()` 等到**首帧画完**才返回（因此调用方拿到句柄时，卡片确实已经渲染过）；
- `Dispose()` 由卡片线程自己销毁窗口（避免跨线程拆除）；
- `App.OnExit` 顺序：**卡片 → 托盘 → 运行时**。卡片每秒读运行时快照，一旦运行时先释放就会出现
  “已释放却仍在取数”的窗口期；
- 卡片创建/启动失败**只留痕、不弹窗、不影响统计**（它是纯展示件；为一个装饰件打断启动不划算）。

7. **榜单末行的占比列留空**（2026-10-06，用户决定）：软件行的占比是“占已归因软件时长”（由榜单接口给出），末行是非软件活跃，两者分母不同；同列并排容易让人误以为可以相加、相减，故**整列留空**，而不是给一个含义与邻行不同的百分数。空位宽度与软件行同源，行名仍与软件行对齐；软件行的占比语义未改动。

> **后续修正（2026-10-06，M7 完成后）**：上表第 3、5、6 条**当时成立，现已随 M7 解决**，此处保留原文作为 M6 阶段的记录：
> - 第 3 条（位置不持久化）→ M7 已持久化到 `settings.widget_pos_x/y`；
> - 第 5 条（卡片不贴桌面）→ M7 已实现嵌入形态（B+，**会被其它窗口盖住**），产品**默认**即该形态；
> - 第 6 条（托盘「调整组件位置」禁用占位）→ M7 已接上可点；**且**当卡片**常态为浮动**时该项会**禁用**（那时没有可调整的东西，口径与主界面按钮一致；由可选回调 `isAdjustAvailable` 驱动，不传该回调则维持 M6 当时的菜单形态）。
>
> 另外两条口径变更：M6 当年那个“可交互普通窗口”自 M7 起名为**浮动形态**（产品默认形态改为**嵌入**）；「调整位置」与「切换形态」两个入口**互斥**（调整中禁用形态按钮）。详见 `docs/M7-验证.md`。

## 9. 结论

1. M6 的核心不是“把卡片画出来”（M0 已解决），而是**把它接进产品并统一口径**；渲染层与 B+ 窗口层几乎原样复用。
2. 落地后的形态：**无参数启动即出现卡片**（可拖、会被覆盖、不进任务栏），托盘可显示/隐藏，`--no-card` 可关闭。
3. 三条最值得记住的设计约束：
   - **派生值用计算属性，不用可写字段**（否则漏填时静默变 0）；
   - **对外展示口径与守恒口径必须分开命名**（`TodayTotal` vs `TodayActive`），否则一处改动会同时破坏恒等式与显示。
   - **展示行也做成纯函数并让自检断言它本身**（`MainWindow.ComposeNonAppTopRow`），而不是在测试里把口径重算一遍 —— 重算的那份永远“通过”；
   - **列宽也是契约**：留空的占比列由 `BlankShareCell` 产出（宽度取自 `ShareCellWidth`），与软件行的 `ShareCell` **同源**；
     自检则拿产品产出的软件行比对**行名起始列** —— 这样“留空”不会悄悄把行名挤歪。
4. **下一个自然目标是 M7**：把 `CardWindow` 的窗口行为换成 B+（渲染与取数直接复用），
   或先做 **M8**（位置持久化，顺带把托盘那个禁用占位点亮）。
