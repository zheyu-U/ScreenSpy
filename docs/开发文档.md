## 1. 项目概述

### 1.1 目标
做一个常驻 Windows 后台的小工具，统计**真实的活跃使用时长**，并能**按软件分别统计**；
把这些数据以**半透明极简卡片**的形式**嵌入桌面壁纸层**展示；同时提供**每日总限额 +
单软件限额**的提醒能力。

### 1.2 核心价值
- 让"我今天到底在电脑上花了多久、都花在哪了"一目了然；
- 在接近自己设定的上限时得到提醒。

### 1.3 非目标（明确不做，避免范围蔓延）
- ❌ 不做强制锁屏 / 阻止使用（纯提醒）；
- ❌ 不做多显示器；
- ❌ 不做云同步 / 账号；
- ❌ 小组件不响应鼠标（纯展示）。

## 3. 技术选型（✅ 已确定）

> ✅ **本节已定稿。** 语言、UI 框架（分两端）、开发环境均已确定。

### 3.1 语言与框架（最终结论）

| 层 | 选型 | 理由 |
|----|------|------|
| 语言 | **C# / .NET 10** | 调用 Win32 API 最顺手；生态成熟；常驻后台开销低；可打包成自包含 exe |
| 桌面小组件（呈现层） | **手写 Win32 顶层分层窗口 + SkiaSharp 渲染（M13 起；外观升级后为唯一实现）+ `UpdateLayeredWindow`** | "逐像素半透明卡片"只有 `UpdateLayeredWindow`（配合 `WS_EX_LAYERED`）能真正实现；不套现成框架，只干"画卡片"一件事，更短更稳更可控。**不嵌入桌面树**（M0 定论：26H2 上第三方子窗口不上屏，见 §5.8） |
| 管理主界面（不嵌入） | **WPF**（已确定，2026-10-05） | 普通窗口，不涉及嵌入；WPF 的排版/数据绑定/图表能力更强，利于后续"近 7 天柱状图"（§5.11）；与既有 `ScreenSpy` 工程（`UseWPF=true`）一致 |
| 数据库 | SQLite（`Microsoft.Data.Sqlite`） | 单文件、免安装、够用 |
| 托盘 | `System.Windows.Forms.NotifyIcon` | 标准做法 |
| 系统事件 | `Microsoft.Win32.SystemEvents` | 锁屏 / 电源事件现成 |

> **关键依据**："半透明深色卡片 + 白色清晰文字"本质需要**逐像素透明度**，
> 而 WPF 的 `AllowsTransparency=true` 与 WinForms 的透明机制**本质都是"顶层窗口专用"**，
> 一旦 `SetParent` 挂到 WorkerW 变子窗口，透明极易失效（即 §7.2 的冲突）。
> 故小组件改为**手写 Win32 分层窗口**（详见 §3.2）。

### 3.2 为什么小组件不直接用 WPF / WinForms

- 逐像素半透明在 Windows 里只有 **`UpdateLayeredWindow`（配合 `WS_EX_LAYERED`）** 能真正实现；
- 该扩展样式**自 Windows 8 起已支持子窗口**，因此"带 `WS_EX_LAYERED` 的子窗口 + `UpdateLayeredWindow` + `SetParent` 到 WorkerW"理论可行；
- 但 WPF / WinForms 开箱即用的透明方案都服务于"顶层窗口"，作为子窗口嵌入后易出问题——
  与其跟框架的合成机制搏斗，不如小组件这一块用一个极简手写窗口；
- 管理主界面**不嵌入**，故仍可放心使用 WPF / WinForms。

### 3.3 被否决的方案

| 候选 | 否决理由 |
|------|----------|
| Python (PySide + pywin32) | 写 P/Invoke（尤其 `UpdateLayeredWindow` 传结构体指针）痛苦；常驻守护 + 打包 exe 体积大、启动慢 |
| Electron / Tauri | 运行时几百 MB；把网页内容嵌进 WorkerW 最后还是得穿回原生层调 Win32，绕远且更重 |

### 3.4 开发环境（最终结论）

| 项 | 结论 |
|----|------|
| **IDE** | **Visual Studio 2026** |
| SDK | .NET 10 SDK（是 SDK，非 Runtime，编译需要） |
| 目标系统 | Windows 11 26H2（实测 WorkerW 的前提） |
| VS 工作负载 | ".NET 桌面开发"（同时含 WPF、WinForms、C# 编译器） |

**为何选 Visual Studio（而非 VS Code）**：本项目越"贴着 Windows 底层"，VS 的
**编辑并继续**（运行时改代码不重启）与**强诊断工具**（CPU / 内存 / 句柄快照）越值钱。
小组件是常驻进程、**每次重启都要重新嵌入桌面**，VS Code 省下的体积/启动时间在此换不回来。

### 3.5 尚待最终敲定（不影响主体推进）

- ✅ **管理主界面：已定为 WPF**（2026-10-05）——与既有 `ScreenSpy` 工程（`UseWPF=true`）一致；
- ✅ **小组件渲染后端：已定为 SkiaSharp**（2026-10-08，M13）——M0 实测 GDI+ 路径可用，M13 起换为 SkiaSharp

**设计要点：**
- **单进程**：自己用，单进程足够，省去跨进程通信的复杂度；
- **采集与 UI 解耦**：采集模块只往存储里写；UI 定时从存储读。即使 UI 崩了，数据也不丢；
- **各组件状态各自独立**，互不阻塞。

## 5. 功能模块详解（逐功能）

> 每个功能按「目标 / 技术方案 / 关键 API / 验收标准 / 依赖」五段式描述。

### 5.1 计时调度器（项目地基）

> ✅ **已实现（M1，2026-10-05）**：`Scheduling/ActivityScheduler.cs` + `Scheduling/ITickSource.cs` + `Scheduling/ActivityTick.cs`；采用 `System.Threading.Timer` + **按 `TickCount64` 差值累计**（抗抖动/卡顿）。验证见 `docs/M1-验证.md`。

- **目标**：提供一个稳定的"每秒心跳"，驱动采集与 UI 刷新。
- **技术方案**：用 `DispatcherTimer` 或 `System.Threading.Timer`，间隔 1s。
- **关键点**：采集逻辑要轻量（毫秒级），绝不能阻塞 UI 线程；采集放后台线程。
- **验收**：程序运行 10 分钟，无内存持续增长，tick 无明显漂移。
- **依赖**：无（第一个做）。

### 5.2 活跃时间采集（空闲检测）

> ✅ **已实现（M1，2026-10-05）**：`Collector/IIdleClock.cs` + `Collector/Win32IdleClock.cs` + `Collector/ActivityRules.cs`；**32 位 tick 回绕已归一化**（uint 无符号减法）。验证见 `docs/M1-验证.md`。

- **目标**：判断"用户此刻是否真的在用电脑"。
- **技术方案**：调用 `GetLastInputInfo()` 拿到"最后一次键鼠输入时间" `lastInput`；
  计算 `idle = now - lastInput`；若 `idle > 阈值`（默认 5 分钟，可配置）则判定为挂机，停止计时。
- **关键 API**：
  ```csharp
  [DllImport("user32.dll")]
  static extern bool GetLastInputInfo(ref LASTINPUTINFO plii);
  ```
- **细节**：`LASTINPUTINFO.dwTime` 是 32 位 tick，约 49.7 天回绕一次。
  实现取 `TickCount64` 的**低 32 位**再做 **uint 无符号减法**（`ActivityRules.IdleFromTickCount32`），回绕自动正确；
  **切忌有符号相减**（回绕附近得负数 → 误判成“刚有输入” → 挂机被计时）。
- **边界**：阈值取**严格小于**（恰好等于阈值算挂机），避免阈值处抖动导致一秒两判。
- **验收**：主动停止键鼠操作超过 5 分钟后，总时长不再增长。
  - ⏳ 该分支已由确定性检查覆盖（阈值边界 / 挂机 / 恢复）；**真实静置 5 分钟待人工执行**。
- **依赖**：§5.1。

### 5.3 锁屏 / 睡眠事件监听

> ✅ **已实现（M2，2026-10-05）**：`Collector/SessionStateTracker.cs`（纯逻辑状态机）、
> `Collector/SessionSignalSource.cs`（`SystemEvents` 适配）、`Collector/Win32SessionStateProbe.cs`（WTS 探测）、
> `Collector/SessionPauseBridge.cs`（接线到调度器）；`Demo/SleepTest.cs`（睡眠测试：唤醒定时器 + 纯判定规则）。
> 验证见 `docs/M2-验证.md`（**51 项确定性检查全部通过**；含真实锁屏 `--lock-test` 与真实睡眠 `--sleep-test` 两个可执行测试）。

- **目标**：锁屏、休眠期间不计入使用时间。
- **技术方案（三条防线，层层递进）**：
  1. **事件（主路径，及时）**：`SystemEvents.SessionSwitch`（`SessionLock` / `SessionUnlock`，另含控制台/远程 断开-连接）
     + `SystemEvents.PowerModeChanged`（`Suspend` / `Resume`）→ 写 `ActivityScheduler.Paused`；
  2. **探测（初值 + 自愈）**：`WTSQuerySessionInformation(WTSSessionInfoEx)` 读 `SessionFlags`，
     用于「启动时已锁屏」（事件不会补发）与「解锁事件丢失」（会**永久少计**，最危险的方向）两处校正；
     结果不确定时**不作任何改动**，绝不用猜测覆盖事件状态；
  3. **时间空洞（与事件无关的兜底）**：单拍间隔超过 `MaxCreditedInterval`（默认 60s）即判为
     睡眠 / 长时间挂起，一律不计入 —— 即使 `Suspend` 事件在新式待机（S0）下缺失，也不会把整晚算成活跃。
- **逻辑**：锁屏与睡眠是**两个独立标志位**（不是单一状态）。二者会重叠（锁屏后合盖睡眠，唤醒时先 `Resume` 再解锁），
  只要有一个为真就持续暂停，避免“仍在锁屏却恢复了计时”。
- **精度**：暂停**按拍生效**（心跳 1s），边界误差 ≤ ±1 拍。
- **关键 API**：
  ```csharp
  SystemEvents.SessionSwitch += ...;        // Microsoft.Win32（WindowsDesktop 框架自带，无需额外 NuGet）
  SystemEvents.PowerModeChanged += ...;
  WTSQuerySessionInformation(WTS_CURRENT_SERVER_HANDLE, WTS_CURRENT_SESSION,
                             WTSSessionInfoEx /* 25 */, out buffer, out bytes);
  ```
- **踩坑留档（WTS 结构体布局）**：`WTSINFOEX` 的 `SessionId` **不紧跟** `Level`。本机实测：
  `Level@0`、**4 字节填充**、`SessionId@8`、`SessionState@12`、`SessionFlags@16`。
  因此实现采用**自定位 + 交叉校验**（用 `WTSSessionId` 与 `WTSConnectState` 两个独立查询验证候选位置），
  而非硬编码偏移。另：扫描必须从偏移 **≥ 4** 起步 —— 否则当**会话号为 1**（与 `Level = 1` 同值）时
  会命中错位“伪头部”并导致解码恒错（已写成回归检查）。
- **验收**：锁屏 10 分钟，这 10 分钟不计入。
  - ✅ 全部逻辑分支已由 51 项确定性检查覆盖（含重叠顺序、自愈、时间空洞、错位回归、**睡眠测试判定规则**）；
  - ⏳ **真实锁屏 → 解锁闭环待人工执行一次**：`--m2-selfcheck --lock-test --seconds=120`（会真的锁屏，需本人解锁）。
  - ⏳ **真实睡眠闭环待人工执行一次**：`--m2-selfcheck --sleep-test --sleep-seconds=20`
    （**会真的挂起整机**；程序先注册 `fResume=TRUE` 的唤醒定时器，**注册失败就绝不入睡**，到期自动唤醒）。
- **依赖**：§5.1。

### 5.4 前台进程识别（按软件统计的核心）

> 🆕 **软件身份层（M9-1，2026-10-06 已实现）**：见 `docs/M9-1-验证.md`。
> 归属链路上**新增一层"身份解析"**，解决"同一个软件有多个进程名"（`Code` / `Code - Insiders`、
> `chrome` / `msedgewebview2`）导致的**静默少计**：统计与限额若挂在原始进程名上，
> 单软件限额只会统计到其中一部分。
>
> ```
> 进程名(原始键)  →  【别名 raw → canonical】  →  软件(归一键)  →  【app_meta】  →  显示名 + 分类
> ```
>
> * **只有一个解析点**：`ForegroundAppRules.Create(..., AppIdentity?)`。下游（榜单 / 卡片 / 存储 /
>   将来的限额引擎）全部只见**归一键**；多一处解析就多一处可能与别处分叉。
> * 身份层**只作用于会被归属到软件的两类**（`App` / `UwpHost`）；桌面 / 外壳 / 锁屏用的是 `#desktop`
>   这类伪键，它们不是"软件"，**不该被用户改名或分配分类**（自检里有这条红线）。
> * **合并 = 三处一起改**：库内历史行（`SqliteStore.MergeAppKey`）+ 内存榜单
>   （`AppUsageTracker.MergeKeys`，**毫秒与基线一起搬**）+ 待写增量（`AppUsageStore.MergePendingKeys`）。
>   少一处，今天就会同时出现"合并前"与"合并后"两条账 —— 不报错、只是数字对不上。
> * `settings`（卡片形态/坐标）与 `limits` **不受合并影响**。
> * **不可拆分**：合并后原始键的信息在聚合层已不存在（原始活动日志 JSONL 仍保留原始进程名，可追溯）；
>   「取消合并」的语义是"**对今后生效**"。

> 🆕 **自定义软件名称（M9-1b，2026-10-06 已实现）**：见 `docs/M9-1-验证.md` 的 §3.6 / §3.7。
> 用户可以给软件起一个**显示名**（主界面「软件与分类」每行的「重命名…」→ 弹对话框）。
> * **纯展示层**：库里 `app_usage` 只存归一键，显示名是**读取时现算**的 ——
>   因此改名**不修改任何统计数据**（毫秒、归一键、分类、守恒等式都不动），却天然作用于**所有日期**，
>   榜单 / 卡片 / 将来的图表一起变，**不需要回填历史**。
> * **禁止重名**：两行同名时界面上分不清谁是谁，而它们的时长是各算各的（用户会以为是一回事、
>   却把设置下到了另一个上），所以明确拒绝而不是容忍。规则在 `Collector/AppNamingRules.cs`（**唯一一处定义**）；
>   冲突范围 = 别的软件**用户设过的名字** ∪ 别的**今日出现的软件**当前显示名 ∪ **系统友好名表**的全部默认名。
> * **两处刻意的"不对称"**（都是为了让用户不被卡住）：① 本来就是默认名时，「恢复默认名」是空操作 → 一律放行；
>   ② 恢复默认名只与别人的**自定义名**比较，不与别人的**默认名**比较
>   （名字表本身就可能两个键共用一个默认名，如 `calc` / `CalculatorApp` 都叫"计算器"）。
> * **改名要四处一起生效**：身份层（今后采样 + 重启续算）、内存榜单（现在）、
>   "当前软件"（卡片上那一行，现在）、以及界面列表的立即重建 —— 少一处就会出现"上面变了、下面没变"。
> * **界面形态**：**弹对话框**（`AppRenameDialog.cs`），它自己不做判断，校验由 `ProductRuntime.ValidateRename`
>   传入 —— 避免"对话框说能改、保存时却说不能"的分叉。

> ✅ **已实现（M3，2026-10-05）**：`Collector/ForegroundAppRules.cs`（纯逻辑：分类 / 过滤 / 规范化 / 合并键）、

> 验证见 `docs/M3-验证.md`（**80 项确定性检查全部通过**；真实观察：归属与过滤正常、**时间守恒差 0 ms**、桌面被正确计入“不计入使用时长”）；
> **原始活动日志**（保留未规范化的进程名 / 窗口类名 / 窗口标题 / pid / hwnd，JSONL、仅变化时记录、产品默认开启）
> 见 `docs/M3-原始活动日志.md`。
>
> 🔄 **口径统一（2026-10-06）**：把“被计入的活跃”明确分成四类，并**全部落库**（见 §5.6 的 `daily_activity`）：
> 锁屏/登录界面改为 **完全不计入**（不再混在“已过滤”里）；桌面 / 外壳 / 自身统一为一栏
> **「不计入使用时长」**；无前台 / 未知另立一栏 **「无前台 / 未知」**。
> 后两者**都计入“今日真实活跃”**，只是不归属到任何软件。守恒等式相应扩为四项
> （已归因 + 不计入使用时长 + 无前台/未知 + 锁屏剔除 == 被计入的活跃）。
> **为什么必须落库**：原先这两类只存在内存、续算只灌回“已归因软件”，于是**重启会让“今日”凭空变小**
> （桌面停留、任务栏等被丢掉）—— 不报错、只是数字变小，正是本项目最忌讳的那类缺陷。

- **目标**：知道"此刻最前面是哪个软件"，把这一秒归到它头上。
- **技术方案（每秒一轮）**：
  1. `GetForegroundWindow()` 拿到前台窗口句柄；
  2. `GetWindowThreadProcessId()` 拿到进程 PID；
  3. `Process.GetProcessById(pid)` 拿到进程名；
  4. 规范化成"软件名"，写入存储。
- **关键 API**：`GetForegroundWindow`、`GetWindowThreadProcessId`。
- **要过滤的窗口**（否则会污染统计）：
- **分类与口径**（`ForegroundAppKind`，2026-10-06 统一）：

  | 类别 | 归类 | 计入“今日真实活跃” | 落库去处 |
  |---|---|---|---|
  | `App` / `UwpHost` | 已归因（软件榜） | ✅ | `app_usage` |
  | `Desktop` / `Shell` / `Self` | **不计入使用时长** | ✅（仍是在用电脑） | `daily_activity.filtered_seconds` |
  | `None` / `Unknown` | **无前台 / 未知** | ✅ | `daily_activity.unattributed_seconds` |
  | `LockScreen` | **锁屏（剔除）** | ❌ 完全不计入 | 不落库 |

  > 锁屏通常由 M2 的暂停判定直接挡掉（那几拍根本不“被计入”，连桶都进不去）；
  > 这里的 `LockScreen` 只兜住“锁屏已发生、M2 尚未察觉”的**检测延迟窗口**（通常几秒）。
  > 它单独计数（`LockScreenExcludedTotal`）而不混进展示口径，是为了让守恒等式仍然闭合、能发现漏记。
- **同名合并**：按进程名合并（Chrome 会开很多子进程，但前台通常只有一个）。
- **验收**：逐个切换几个软件各停留 1 分钟，统计时长误差在几秒内。
- **依赖**：§5.1、§5.5。

### 5.5 UWP / 商店应用名修正

> ✅ **已实现（M11，2026-10-06，见 `docs/M11-验证.md`）**：`Collector/UwpAppRules.cs`（纯逻辑，**两条路径**）
> + `Collector/UwpWindowResolver.cs`（Win32 枚举）+ 取证工具 `Diagnostics/UwpWindowDiagnostics.cs`（`--diag-uwp`）。
> **52 项自检全部通过** + **两轮变异测试**（去掉路径 2 → 恰好 1 项 FAIL；去掉唯一性约束 → 恰好 1 项 FAIL）。

- **目标**：解决 UWP 应用（「设置」「计算器」等）被统计成 `ApplicationFrameHost.exe` 的问题。
- **⚠️ 实测推翻了本节原来的技术方案（Windows 11 26H2 / 26300.9457，2026-10-06）**：
  原文写的是「枚举宿主的子窗口，找到真正承载应用的子窗口」。用 `--diag-uwp` 实地勘察发现：
  `ApplicationFrameWindow` 的子窗口**只有宿主自己的**（`ApplicationFrameTitleBarWindow` ×2 + `ApplicationFrameInputSinkWindow`），
  **没有 CoreWindow**；应用本体是一个**独立顶层窗口**（类名仍是 `Windows.UI.Core.CoreWindow`，
  属于真实应用进程，如 `SystemSettings.exe`），且它与宿主之间**没有父子 / owner 关系**。
  > 若只按原文写：**编译通过、自检通过、实际永远认不出任何 UWP 应用**，且不报错 —— 典型的「不报错的错」。
  > 因此增设取证入口 `--diag-uwp`（打印真实窗口的类名 / pid / 进程名 / 标题 / 父子与 owner 关系 / 样式）。
- **技术方案（两条路径，先 1 后 2）**：
  1. **子窗口路径**：`EnumChildWindows` 找类名含 `CoreWindow` 且 pid 与宿主不同的子窗口（覆盖 Windows 10 / 部分构建）；
  2. **顶层 + 标题配对路径**：`EnumWindows` 收集「可见、类名含 `CoreWindow`、pid 与宿主不同」的顶层窗口，
     取**标题与宿主标题相同**者（26H2 实测形态）。
- **三条保守约束**（宁可认不出，不可认错）：
  1. 宿主标题**为空则不做配对**（空标题的窗口太多，配上必是错的）；
  2. 候选必须**可见**、pid 与宿主不同、进程名非空，且不是已知的「非应用」宿主
     （`TextInputHost` / `ShellHost` / `explorer` / `dwm` / `csrss` / `ApplicationFrameHost`）；
  3. 配对上的候选必须**恰好一个** —— 0 个或 ≥2 个都判「未识别」。
  识别失败时**退回宿主 lump**（键 `applicationframehost`，显示「UWP 应用（未能识别/旧合并）」），**不猜名字**。
- **标题只用于「配对」，不参与「身份」**（不违「标题不参与身份」这条红线）：
  软件身份 = **进程名小写**，与桌面软件**同一命名空间、同一张友好名表**（UWP 与桌面软件平权）；
  展示名**由键推出**（`NormalizeDisplayName(key)`），与重启续算时逐字一致、不会跳变。
- **`Kind` 仍是 `UwpHost`**：表示「这一拍来自 UWP 宿主」（诊断与计数用），而不再表示「名字未知」；
  因此 `CountsAsApp`、守恒等式与 UWP 计数全部原样不变。
- **旧数据**（决策）：M11 **不迁移**（schema 仍为 v3）；历史上累积在 `applicationframehost` 键下的行**保留**，
  与「当前识别失败」**共用同一显示名** —— 同一个键只能有一个名字（教训 16/20）。
- **验收**：打开「设置」并保持前台，统计里显示「设置」而非 `ApplicationFrameHost`；
  `--m11-selfcheck` 的 C 组用**真实窗口**做端到端断言（用标题把应用本体窗口与其宿主配起来，断言解析出的进程一致）。
- **依赖**：§5.4。
- **已知局限**：若应用本体窗口的标题与宿主标题不一致（或为空），则认不出，退回宿主 lump（保守，见 M11 文档 §7）；
  另：未收录的 UWP 应用会显示进程名，可用 M9-1b「重命名」自定义。

### 5.6 数据存储（SQLite）

- **目标**：持久化“每天 × 每软件”的累计时长与设置。
- **状态**：✅ **已实现**（2026-10-05，见 `docs/M4-验证.md`）：**36 项自检全部通过**
  （A 确定性 34 + B 真实观察 2；2026-10-06 因 `daily_activity` 新增 6 项）；
  「重启后今天的时长仍在」已用**关闭并重开数据库**实测证明。
- **技术方案**：SQLite 单文件（`Microsoft.Data.Sqlite` **10.0.12**，与本机 .NET 运行时同补丁号）。
  位置：**`%LOCALAPPDATA%\ScreenSpy\data.db`**
  （⚠️ 2026-10-05 修订：原文写 `%AppData%`，但 Roaming 在域账户会被同步，数据库文件不宜漫游；
  且与原始日志目录 `%LOCALAPPDATA%\ScreenSpy\logs` 保持一致）。
- **表设计**（`PRAGMA user_version = 3`）：
  > 🔄 v3（M9-1，2026-10-06）新增三张表：`app_alias`（原始进程名 → 归一键，只存用户做过的合并）、
  > `app_meta`（用户显示名 + 归属分类，只存用户改过的行）、`categories`（分类表）。
  > **v2 → v3 是唯一一次会删数据的迁移**：按既定决策（D57）清空 `app_usage` 与 `daily_activity`
  > 的全部行（"历史数据不要了，从今天重新开始"），因为身份口径变了、旧行会让同一软件分成两半。
  > `settings`（卡片形态/坐标）与 `limits`（限额）**必须保留** —— 它们是用户设置、不是时间数据
  > （自检里有专门断言）。分版本判断：v1 的库里还没有 `daily_activity`，直接 DELETE 会报错。
  > 分类口径：**一个软件只属于一个分类**（D53），于是 `各分类之和 == 各软件之和` 精确成立。
  ```sql
  -- 每天每软件累计（单位：秒）
  CREATE TABLE IF NOT EXISTS app_usage (
      date      TEXT NOT NULL,   -- 'YYYY-MM-DD'
      app_name  TEXT NOT NULL,   -- 合并键（进程名小写）
      seconds   INTEGER NOT NULL DEFAULT 0,
      PRIMARY KEY (date, app_name)
  );

  -- 每天“不计入使用时长 / 无前台·未知”的秒数（2026-10-06 新增，schema v1 → v2）
  -- 与 app_usage 分开，是为了让 app_usage 保持“纯软件”：Top 排名与占比分母不被污染。
  -- 锁屏不在此表（按口径完全不计入）。
  CREATE TABLE IF NOT EXISTS daily_activity (
      date                 TEXT PRIMARY KEY,   -- 'YYYY-MM-DD'
      filtered_seconds     INTEGER NOT NULL DEFAULT 0,   -- 桌面 / 外壳 / 自身
      unattributed_seconds INTEGER NOT NULL DEFAULT 0    -- 无前台 / 未知
  );

  -- 设置表（键值对）
  CREATE TABLE IF NOT EXISTS settings (
      key    TEXT PRIMARY KEY,
      value  TEXT
  );

  -- 限额表
  CREATE TABLE IF NOT EXISTS limits (
      scope      TEXT NOT NULL,             -- 'total' 或 'app'
      target     TEXT NOT NULL DEFAULT '',  -- app 时为软件键；total 时为空串（见下）
      seconds    INTEGER NOT NULL,
      PRIMARY KEY (scope, target)
  );
  ```
  > **踩坑留档**：`limits.target` 原设计可空，但 SQLite 认为 **NULL 之间互不相等**，
  > 于是 `ON CONFLICT(scope,target)` 在 `scope='total'` 时**永远匹配不上**，
  > upsert 会退化成“每次新增一行”。故改为 `NOT NULL DEFAULT ''`，total 一律用空串。
- **写入策略（重要）**：**不要每秒写盘**（会疯狂写 SSD）。
  已实现：**每 15 秒批量 flush + 切换软件时强制 flush + 退出时强制 flush**。
  - 心跳线程只做**入队**（有界队列，永不阻塞、永不抛异常，满则丢弃并计数）；
    真正的聚合与写盘在**后台线程**上 —— 既减少 IO，也绝不干扰计时。
  - 写入模型为**增量累加 + 单事务**（`seconds = seconds + 增量`），且**提交成功后才扣减待写数据**：
    写盘失败不会丢数据，也不会把已有数据改小（对比“绝对值覆盖”在算错时会静默毁数据）。
  - **余数结转**：内存按**毫秒**累加、只落**整秒**，不足 1 秒的余数留在内存继续攒 → 长期运行**零漂移**。
  - **不读内存榜单**：调度器跨天时**先** `DayRolled`（榜单被清空）、**后** `Ticked`，
    若“到点去读榜单再写库”会丢掉昨天尾段；故存储自行按**每拍自身的本地日期**累加增量，跨天天然写成两行。
  - **启动续算**：开机把库中“今日 × 每软件”（`app_usage`）**连同**今日的
    “不计入使用时长 / 无前台·未知”（`daily_activity`）一起读回并灌入（`AppUsageTracker.Seed`）；
    基线**单独存放**、不计入时间守恒不变量，因此“显示今天一整天”与“守恒只描述本次运行”两不冲突。
    ⚠️ 两半**必须一起灌**：只灌软件基线会让“今日真实活跃”在重启后变小（2026-10-06 修复，自检有专门回归）。
- **位置配置**：小组件坐标也存 `settings` 表（键 `widget_pos_x` / `widget_pos_y`）；
  读写 API 已就绪，**接线属 §5.10 / M8**；`limits` 表供 §5.7 / M9 使用。
- **验收**：重启程序后今天的时长仍在；断电场景最多丢 15 秒。
  ✅ 已实测：15 秒真实观察中**前 10 秒库中仍为 0s**（增量都在内存），
  关闭并重开后读出 **15s**；关闭前“待写 1000ms”即断电风险窗口（远小于 15 秒上限）。
- **依赖**：§5.4。

### 5.7 限额引擎与提醒（✅ 已实现：M9-2，2026-10-06）

> 验证见 `docs/M9-2-验证.md`：`--m9-selfcheck` 新增 **F / G / H** 三组（41 + 20 + 15 = 76 项）；
> 构建 0 错误 0 警告；实测 153 项通过 / 0 失败（E/H 共 23 项因产品实例占用单实例互斥体按设计跳过）；
> 两轮变异测试各命中 7 / 4 项。

- **目标**：**总限额 / 单软件限额 / 分类限额** 到达时提醒。
- **口径**（三处**同源**，否则会出现「限额说超了、大字号看着没超」）：
  - 总限额比 **「今日真实活跃」**（`= 本次运行活跃 − 锁屏剔除 + 库中基线`，与主界面大字号 / 托盘 tooltip / 卡片同一个数）；
  - 单软件限额比**该软件今日时长**，键是**归一键**（§5.4 身份层）；
  - 分类限额 = **该分类下各软件时长之和**（一个软件只属于一个分类，故不会重复计）；
  - 锁屏 / 睡眠按既有口径**完全不计入**。
- **技术方案**：
  - 判定**旁听心跳**（`AppUsageBridge.Observed`，默认 1s），不另起定时器；没有限额时直接返回（零成本）；
  - 阈值**可配置**：设置键 `limit_thresholds` = 逗号分隔的**百分比**（默认 `"80,100"`），解析后升序、去重；
  - **一次跨两档只提醒最高那档**（从 70% 涨到 110% 只弹「已达到」，不连弹两条）；
  - **去重**：设置键 `notified|{日期}|{scope}|{target}|{阈值千分比}` —— **带日期**，跨天自动重置；
    阈值用**千分比整数**（800 / 1000）而不是小数字符串（小数格式漂移会让去重静默失效 = 每秒弹一条）；
  - **改限额 / 改阈值时清掉今天的去重标记** → 同一档会重新提醒（否则「把限额调低却再也不提醒」）；
  - 存储不可用时退回**内存去重**（本次运行内仍只提醒一次）—— 降级时绝不刷屏；
  - 判定路径**永不抛异常**（每秒都会走的路径，一次异常不该让心跳停摆）。
- **提醒形式**：**托盘气泡**（`NotifyIcon.ShowBalloonTip`）。
  - 发送动作集中在 `TrayIconHost.ShowNotification` **一处** —— 将来升级为真 Toast（`Microsoft.Toolkit.Uwp.Notifications`，
    需 AUMID 注册）时，限额引擎、组合根、界面**一行都不用改**；
  - 不阻止使用（§1.3 非目标）。
- **分层**（可确定性推演的原因）：
  - `Limits/LimitRules.cs` + `Limits/LimitEngine.cs` = **纯逻辑**（无 IO、无状态）；
  - `Limits/LimitGuard.cs` = 有状态（加载 / 判定 / 去重读写 / 编辑 API / `Notified` 事件）。
- **依赖**：§5.6。

### 5.8 桌面组件呈现（❌ 真嵌入已证伪 → ✅ 改用 B+ 方案）

- **M0 定论（2026-10-05，见 `docs/M0验证结论.md`、`docs/M0-B+验证.md`）**：
  **不嵌入桌面树**。在 Windows 11 26H2 上，`SetParent` 进 `Progman`/`WorkerW` 的**第三方子窗口不会上屏** ——
  `SetParent` 返回值、`GetAncestor`、`IsWindowVisible`、`UpdateLayeredWindow` **全部"成功"**，
  但**截屏像素判定为 0 像素**。根因：`Progman` 带 `WS_EX_NOREDIRECTIONBITMAP`，由 **DirectComposition** 呈现，
  只有 shell 自己注册进合成树的子 HWND 才会被呈现。
  （早期"路线 A 已通过"是**假阳性**：判据只校验了记账层，从未校验像素。）
- **采用方案（路线 B+，已客观验证）**：**顶层分层窗口 + z 序自锁 + 显示桌面复位**
  1. 窗口保持**顶层**（**不** `SetParent`）：`WS_POPUP` + `WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW`；
  2. **z 序自锁**：在 `WM_WINDOWPOSCHANGING` 中强制 `SWP_NOZORDER`，任何外力都挤不走它（关键机制，源自对 Rainmeter 的求证）；
  3. 平时压 `HWND_BOTTOM`（**桌面之上、其它普通窗口之下** —— 正是想要的观感）；
  4. **「显示桌面」检测 + 复位**：用隐藏探针窗口与桌面图标宿主比 z 序先后
     （判据：**桌面宿主跑到探针之前 ⇒ 处于"显示桌面"状态**），命中时把窗口插到"最上层非 topmost 位置"
     （任务栏等 topmost 之下、桌面与普通窗口之上）；采样密度 250ms ⇄ 显示桌面期间 100ms；
  5. `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)` 让检测即时响应（定时器兜底）。
- **关键事实**：Win+D **不会**最小化卡片（`IsIconic` 始终 False），只是把桌面宿主抬到最前把它**盖住**；
  因此正解是 **z 序复位，而不是拦截最小化**。
- **26H2 桌面结构（留档，供日后兼容性排查）**：`SHELLDLL_DefView`（图标层）直接是 `Progman` 的子窗口；
  壁纸层是 `Progman` 的全屏可见子 `WorkerW`；**不存在**"顶层、无 `SHELLDLL_DefView` 的同级 `WorkerW`"。
- **以下为 M0 早期已被证伪的"真嵌入"方案（仅作留档，勿再实施）**：
  1. 找到 `Progman` 窗口，向它发送未公开消息 `0x052C`，促使系统生成壁纸层 `WorkerW`；
     **先查找、只有找不到才注入**——重复注入会堆积多余 `WorkerW`。
  2. **按桌面结构自适应选择"壁纸层宿主"**（按下列顺序判定）：
     - **(a) 新版桌面（26H2 实测形态）**：`SHELLDLL_DefView`（图标层）直接是 `Progman` 的子窗口，
       壁纸层是 **`Progman` 的全屏可见子 `WorkerW`** → 取该子 `WorkerW`；
     - **(b) 经典结构**：图标层位于某个顶层 `WorkerW` 内 → 取"它之后、**可见且覆盖全屏**的顶层 `WorkerW`"
       （必须加尺寸/可见性校验，否则会误选无关进程的 `WorkerW`）；
     - **(c) 兜底**：直接把组件嵌进 `Progman`，并用 `SetWindowPos(hwnd, 图标层句柄, …)`
       把组件压到图标层之下。
  3. `SetParent(我的窗口句柄, 壁纸层宿主)` 把自己挂进去；
     随后**显式**把窗口样式由 `WS_POPUP` 改为 `WS_CHILD`（`SetParent` 不会自动改，见 §7.1）。
- **关键 API**：`FindWindow`、`EnumWindows`、`EnumChildWindows`、`SendMessageTimeout`、`SetParent`、`SetWindowPos`。
- **留档结论**：该方案在 26H2 上**不可行**（原因见本节开头：第三方子窗口不被合成，不上屏）。
- **验收**：卡片在桌面可见、会被其它窗口覆盖、**Win+D 不最小化**、鼠标穿透、任务栏/Alt+Tab 不可见。
  → **以上五项均已实测通过**（`docs/M0-B+验证.md`、`docs/M5a-产品启动接入.md`）。
- **依赖**：§5.9（UI 要先能画出来）。

### 5.9 组件 UI（极简卡片）

- **目标**：把数据画成半透明深色卡片。
- **内容布局（自上而下）**：
  1. 大字号：`今日 3:42`
  2. 限额进度条：`3:42 / 5:00`（接近变黄、超了变红）——**M9 之前整块隐藏**（见下）
  3. 当前软件：`正在使用：Visual Studio Code`
  4. Top5：软件名 + 时长 + 进度条
  5. **不计入使用时长 / 无前台·未知**（2026-10-06 新增）：两行小字，分别显示**今天一整天**的
     “桌面 / 外壳 / 自身”与“无前台 / 未知”时长；**为 0 时整行隐藏**（避免 `0:00` 占版面）。
     它们同样**计入“今日真实活跃”**，标出来才不会被误以为漏算。
- **技术要点（与 §5.8 强相关，已按 §3 结论定稿）**：
  - 采用**手写 Win32 分层窗口**（**顶层**，不做 `SetParent` —— 见 §5.8）：窗口带 `WS_EX_LAYERED` 扩展样式；
  - 卡片先在内存里渲染成一张 **32 位 ARGB 位图**（GDI+ `Graphics` 绘制深色半透明底 + 白色文字），
    再交给 **`UpdateLayeredWindow`** 做逐像素合成，从而实现"背景半透明、文字清晰"；
  - 该窗口**不是子窗口**，也不需要 `SetParent`：真嵌入已在 26H2 上被证伪（§5.8、§7.2）；
  - **已落地（M13）**：渲染后端已换为 **SkiaSharp**（像素等价迁移，走路径 (b)：Skia 位图 → 拷进 DIB）。
    接口是 `ICardRenderer`（"给我一块像素缓冲"），**外观升级（2026-10-08）后 GDI+ 实现已移除**，回退改由 git 承担；卡片几何/配色/排版改为 `CardGeometry` / `CardTheme` / `CardLayout` 三个唯一来源（见 `docs/外观升级-验证.md`）。

#### 5.9.1 ✅ 已实现（M6 建卡片，M7 扩为双形态；2026-10-06）

**M6 与 M7 的分工（已确认的决策，M7 已落地）**：M6 先把卡片做成**可交互的普通窗口**（能看、能拖、能调版式），
M7 再把窗口行为换成桌面分层形态。两者**共用同一套渲染层**，因此 M7 不需要重做卡片 UI。

**M7 的形态决定（已确认）：不做成两个窗口，而是「同一个窗口的两种参数组合」** ——
单 HWND、单 STA 线程、**共用一份坐标**；切换时只改三样东西（窗口样式、命中测试、z 序自锁），
且必须投递到**窗口线程**执行（`WM_APP`）。于是切换不跳位、不闪断、无销毁重建空档，
只有一条生命周期与一套自检 —— 否则必然出现“一种形态修了、另一种没修”的双份漂移。
原 `Desktop/DesktopCardHost.cs` 因此**退场**（B+ 核心 `DesktopZOrderManager` 原样保留）。

| 维度 | 嵌入形态（Embedded，**默认**） | 浮动形态（Floating，即 M6 当年那个） |
|---|---|---|
| 窗口样式 | `WS_EX_LAYERED \| TOOLWINDOW \| TRANSPARENT \| NOACTIVATE` | `WS_EX_LAYERED \| TOOLWINDOW` |
| 鼠标 | 穿透（`WM_NCHITTEST` → `HTTRANSPARENT`） | 可点、可拖（`HTCAPTION`） |
| z 序 | 自锁 + 压 `HWND_BOTTOM` + 显示桌面复位 | 无自锁、抬到最前 |
| 定位 | `Present(hwnd, x, y)`（`pptDst`，坐标即 `_x/_y`） | `SetWindowPos` 定位一次；每帧 `pptDst=NULL`（否则拖动会被每帧拽回） |
| 何时进入 | 常态（默认） | 「调整位置」临时进入；或把**常态形态**切成浮动 |

- **“绑定”如何实现（本项目的既定做法：不用 WPF 数据绑定、不用属性通知）**：
  `CardWindow` 接受一个 `Func<CardModel>`（取数函数），每秒被调用一次，返回一份**纯数据** `CardModel`，
  交给 `CardRenderer` 立刻画出来。产品侧传入的实现是
  `() => CardData.FromStatus(runtime.Snapshot())` ——
  即**复用组合根的状态快照**（`ProductRuntime.Snapshot()` 已是线程安全、永不抛异常的平面拷贝），
  于是卡片、主界面、托盘看到的是**同一份口径**，不会三处数字互相打架。
- **M6 的产品化改动**（2026-10-06 口径统一后为四处）：
  1. 去掉 M0 阶段的调试秒针 `t=Ns`（它是“卡片还在刷新”的肉眼证据，产品上只会让人困惑）；
  2. **限额整块隐藏**：`CardModel.LimitText` 为空则渲染器跳过该区域 —— 真实限额属 M9，
     宁可不显示，也**不显示一个不存在的约束**；
  3. **“今日”口径统一为“今天一整天的真实活跃”**：`RuntimeStatus.TodayTotal`
     （= 本次运行 − **锁屏剔除** + 库中今日基线，计算属性）取代原先的 `TodayActive`（本次运行）。
     原先主界面大字号用“本次运行”、同屏 Top5 用“今天一整天”，**重启后两者会不一致**
     （大字号掉回 0:00 而榜单仍有数据）。2026-10-06 又补上：锁屏/睡眠**完全不计入**（减项），
     而“不计入使用时长 / 无前台·未知”**计入**（已并入本次运行与库中基线）；
  4. **卡片新增非软件活跃两行**（见上“内容布局”第 5 条）。
- **卡片的产品接入（M7 起）**：`App` 在 `OnStartup` 里先读**卡片放置**（形态 + 坐标，来自 `settings`），
  再按该形态创建 `CardWindow` 并启动（独立 STA 线程 + 消息循环）；
  默认随产品启动显示，托盘菜单可「显示卡片 / 隐藏卡片」；`--no-card` 可关闭。
  释放顺序为 **卡片 → 托盘 → 运行时**（卡片每秒读运行时快照，必须最先停）。
- **M7 新增的产品化改动**：
  1. **形态可切换且持久**：主界面「切换为浮动窗口 / 切换为嵌入桌面层」改的是**常态形态**，写库；
     只有切换**真的成功**才写库 —— 否则库里的形态与屏幕上的形态不一致，下次启动就照着错值走；
  2. **「调整位置」是临时的**：进入浮动可拖 →「完成调整」时把**当前真实坐标**交给上层落库、再回到常态形态；
     常态形态为浮动时它不会被“调整”改写成嵌入（这条有专门回归）；
  3. 浮动形态下**每拍比对实际坐标**（`GetWindowRect`），变化即落库 —— 拖动是系统代劳的，
     没有我们参与的消息可听，所以用轮询而不是事件；
  4. 坐标**从库读出后夹回屏幕内**（换过分辨率 / 拔过显示器时，否则卡片会落在屏幕外 = 卡片消失且无任何提示）；
  5. **「调整中」是独立状态，且两个入口互斥**（2026-10-06 第二轮，见 §5.10）：
     `IsAdjusting` 读独立标志（**不是** `Mode == Floating`），`CanAdjust` 表示“调整位置是否有意义”。
- **验收**：`--m6-selfcheck` **52 项全部通过**（A 数据映射 19 / B 窗口 14 / C 托盘 8 / D 榜单末行 11）；
  另有变异测试（把 `TodayTotal` 改成不扣锁屏剔除）恰好命中 **1 项** FAIL，证明回归不是空检查。
  详见 `docs/M6-验证.md`；M7 部分见 `docs/M7-验证.md`（**78 项**，A 14 / B 36 / C 14 / D 14）。

### 5.10 位置自定义（临时编辑模式 / 方案 C）—— ✅ 已实现（M7，2026-10-06）

- **目标**：让用户能像拖普通窗口一样，把组件放到任意位置。
- **实现（与方案 C 的差异已确认：不改样式重建，而是切同一个窗口的形态）**：
  1. 托盘菜单「调整组件位置」或主界面「调整位置」→ 卡片**运行时切到浮动形态**
     （去 `WS_EX_TRANSPARENT`/`WS_EX_NOACTIVATE`、解除 z 序自锁、抬到最前、命中测试 `HTCAPTION` 可拖）；
  2. 用户拖到满意位置后按「完成调整」；
  3. 记录**当前真实坐标**（`GetWindowRect`，不是“我们以为的位置”）→ 落库 →
     **回到常态形态**（自锁 + 穿透 + z 序复位并压底）。
- **坐标存储**：`settings` 表的 `widget_pos_x` / `widget_pos_y`（**绝对屏幕像素**，左上角），
  外加 `widget_mode`（`embedded` / `floating`）作为**常态形态**。
  键名是**与既有数据库的兼容契约**，因此自检用**字面量**钉死它 —— 第一版自检引用了产品常量，
  变异测试当场证明那样“常量一改名、断言跟着改、永远通过”，等于没测。
- **分辨率或缩放变化时的换算处理见 §7.3**；当前的**兜底**是读出后**夹回屏幕内**，
  保证卡片不会落在屏幕外（落在屏幕外 = 卡片消失，且屏幕上没有任何提示）。
- **验收**：进入调整能自由拖动；完成后回到常态形态且位置正确；重启后位置与形态保持。
  ✅ 已由 `--m7-selfcheck` 逐条客观断言，其中最关键的一条是
  **「两形态共用一份坐标」**：浮动下移动窗口 → 回嵌入后位置不变，且嵌入形态重绘**不会把它拽回**默认坐标。
- **两个入口的分工与互斥（2026-10-06 第二轮，已确认）**：
  「调整位置」与「切换形态」**底层是同一个机制**（都走 `CardWindow.SwitchMode` → `WM_APP` → 卡片线程），
  但**上层是两个不同动作**：前者是**临时插曲**（不改常态，结束时存坐标再回常态），
  后者是**改常态本身**（只有切换真的成功才写库）。因此两者**不得同时可用**：

  | 状态 | 「调整位置」 | 「切换形态」 |
  |---|---|---|
  | 常态嵌入、未调整 | 可用 | 可用 |
  | **调整中** | 可用（「完成调整」） | **禁用** |
  | **常态浮动** | **禁用** | 可用 |

  调整中禁用形态按钮，是因为它**不经过**「完成调整」的“先取当前坐标再上报”，
  最后一次拖动可能还没写进库（**最多约 1 秒的静默偏差**）；且常态为嵌入时在调整中点它，
  会把**临时**的浮动变成**永久**常态。兜底：`App.ToggleCardMode` 开头先 `EndAdjust()` 再改常态。
  「调整位置」在常态为浮动时禁用，是因为那时卡片随处可拖、每拍自动记位置，点了本就无事可做。
- **一个必须各记一份状态的教训**：第一版把「调整中」写成 `IsAdjusting => Mode == Floating`。
  对**常态就是浮动**的用户 `Mode` 永远是浮动 → 这类用户被判成“永远在调整中”，
  「调整位置」永远显示“完成调整”，而“调整中要禁用的形态按钮”会被**永久禁用**
  （**用户再也切不回嵌入**，且不报任何错）。现改为独立 `_adjusting` 标志 + `CanAdjust`。
  形态按钮也**只表述常态**（`RestingMode`），不再读当前形态。
- **依赖**：§5.8、§5.9。

    维度可切 **每天总量 / 某个软件 / 某个分类**（软件候选取自近 7 天的库，分类候选取自身份层）。
    **今天也读库**（用户决策），因此最多滞后约 15 秒 —— 这条代价**写在界面上**（说明文字里明说），不藏在代码里。
    **空槽与 0 分开**：那天没有记录 → 空槽 + `—`；那天有记录但该软件没用过 → `0:00`。
    刷新节奏与落库间隔对齐（**每 15 秒**读一次库）；维度/目标下拉框**按需重建**，不跟每秒刷新（否则会销毁用户正打开的列表）。
    存储不可用时**明确给出原因**，而不是画一张空图（空图会被读成这几天真的没用电脑）。
    分层：**口径**（`ChartBuilder`）与**几何**（`BarChartLayout`）是纯逻辑、可确定性断言；
    **绘制**只有薄薄一层（`Charts/BarChartView`）—— 用户已说明日后要重做 UI，届时只替换这一层，口径与断言原样保留。
    验证：`--m10-selfcheck` 新增 **A/B/C/D 四组（81 项）** + 两轮变异测试（命中 25 / 6 项），M1–M9 全量回归 exit 0。
  - **软件与分类（M9-1 ✅ 已实现，2026-10-06）**：列出**今日全部软件**（不只 Top5），每行一个分类下拉框；
    另有「新建/删除分类」、「合并软件（A → B）」、「取消合并（对今后生效）」。
    这一节含**可交互控件**，因此**按需重建**（进窗口 / 点「刷新列表」/ 每次改动之后），
    **绝不跟着每秒刷新重建** —— 那会把用户正打开的下拉框销毁掉，表现为"点了没反应"。
    保存失败时会把显示值**拉回上一次的真实值**（而不是留在屏幕上骗人）。
  - **限额设置（总 / 单软件 / 分类）（M9-2 ✅ 已实现，2026-10-06）**：一键进入对话框填「小时 + 分钟」，
    可保存 / 清除；单软件限额在「软件与分类」每行的「限额…」上；阈值框可直接改（非法时不写库并说明原因）；
    「已设限额」列表可逐条删除。**进度文字每秒刷新**（纯文本无交互），而下拉框 / 列表 / 阈值框**按需重建**
    （阈值框在用户正在输入时不会被覆盖）。卡片限额进度条随之出现（`LimitText` 非空即显示，取**最紧急**那条）；
    托盘「设置…」= 打开主界面（限额与分类都在那里）。
  - **开机自启开关（M12 ✅ 已实现）**：一个复选框 + 一行说明；**注册表是唯一事实来源**（每秒回读注册表，
    因此"在别处改过启动项"也会在 1 秒内反映到界面）；四种状态各说各话
    （已启用 / 未启用 / 同名残留指向别处 / 注册表不可用），且提示里**明说"登录时只进托盘"**。详见 §5.12。
- **验收**：各项可见、可操作；关闭主界面程序仍在托盘运行（✅ 已实测，见 M5b 文档 §5.4）。

### 5.12 开机自启（M12 ✅ 已实现，2026-10-06）

- **技术方案**：**注册表 Run 键**（`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`，值名 `ScreenSpy`）。
  计划任务方案**不做**：Run 键够用且不需要提权。代价如实记在 `docs/M12-验证.md` §7 ——
  Run 键**无法延迟启动、无法提权**，将来若需要就得改走计划任务。
- **实现**：`AppHost/AutoStartRules.cs`（纯逻辑：命令行构造 / 解析 / 匹配 / 自启窗口策略）+
  `AppHost/AutoStartRegistration.cs`（注册表层：读写与**回读**；键路径与值名可注入，便于自检在真实临时键上做往返）。
- **写入的命令行**：`"<exe 全路径>" --autorun` —— **路径一律加引号**。
  含空格的路径不加引号会被系统按空格拆成两段，表现为"登录后什么都没发生"，**且不报错**。
- **判定"已启用"要三条同时成立**：能解析出路径 **∧** 带 `--autorun` **∧** 路径 = 本进程 exe。
  只比路径的话，界面会说"已启用开机自启"，而登录时其实会**弹出主界面**（不是承诺的形态）——
  又一次"界面在骗人"。
- **注册表是唯一事实来源**（用户决策）：**不**往 `settings` 表存一份"期望状态"。
  两份状态一旦不一致（用户在任务管理器删掉 / 被策略拦下 / 被别的工具覆盖），
  界面就会显示"已启用"而实际没有。因此界面**每秒回读**注册表：
  写失败立刻弹回真实值并说明原因；在别处改过 1 秒内反映；存在**同名但指向别处**的残留则标出来。
- **写操作一律回读**：`Enable()` / `Disable()` 不假设写入成功（"看起来成功"但被重定向 / 被拦掉时，回读是唯一判据）；
  关闭是**幂等**的（值本来不存在不算失败）。
- **权限与边界**：只碰 **HKCU**（当前用户，无需管理员，不影响其他账户）；
  **删除只删值、绝不删键**（真实 Run 键是 Windows 自己的，删掉会影响其它自启项）。
- **`--autorun`**（`StartupOptions`）：自启拉起时**只进托盘、不显示主界面**（用户决策）。
  它**不影响任何统计口径**，只决定要不要显示窗口。由注册表命令行给出这个信号，
  而不是靠"猜父进程"（那类判据在真实环境里不稳定）。
- **降级例外**：`ShouldShowMainWindow(autoRun, trayAvailable) => !autoRun || !trayAvailable` ——
  自启 + **托盘不可用**时**必须**显示窗口，否则没有任何入口能呼出界面（"看不见也关不掉"；
  M5b 那条降级契约在自启场景下的延续）。
- **弹窗策略**：自启时若遇「已有实例」或「启动失败」，**仍按现状弹对话框**（用户决策，D79）。
  这关闭了 M5a/M5b 留下的待办"无人值守下弹窗并不合适" —— 原记录与结论保留，此处记录最终决定。
- **验证**：`--m12-selfcheck` **A/B/C 三组 59 项全部通过**（B 组在**真实的 HKCU 临时键**上做
  写 → 读 → 改 → 删 往返，含一条"**直接读原始值核对**"的断言）+ **两轮变异测试**（命中 3 / 1）；
  M1–M11 全量回归 exit 0。
- **验收**：重启电脑后程序自动在托盘出现 —— **需你重启（或注销再登录）一次做最终验收**，
  见 `docs/M12-验证.md` §8 第 9 条。
- **依赖**：§5.11（要有开关）；§5.13（`--autorun` 的启动分支）。

### 5.13 产品启动流程（M5a ✅ 已实现）

- **入口**：`App.OnStartup` 在自检/演示参数之后判定 —— **无参数即产品启动**；`App.OnExit` 释放运行时（flush 尾段）。
  M6 起产品启动还会创建桌面卡片（`Widget/CardWindow`，独立 STA 线程；`--no-card` 关闭），
  并在 `OnExit` 里按 **卡片 → 托盘 → 运行时** 的顺序释放。
- **组合根**：`AppHost/ProductRuntime`，装配顺序为「单实例保护 → M1 → M2 → M3 → M4/日志 → 启动续算 → `Start()`」（顺序即契约，详见 `docs/M5a-产品启动接入.md`）。
- **单实例**：命名互斥体 `Local\ScreenSpy.SingleInstance`；已有实例时**提示后退出**（M4 是增量累加，两进程同写会互相累加、数据偏大）。
- **降级策略**：库 / 日志 / 会话监听任一失败都**继续运行并显示警告**；只有计时核心失败才整体启动失败。
- **覆盖开关**：`--data-dir=` / `--db=` / `--log-dir=` / `--no-store` / `--no-raw-log` / **`--no-card`（M6）** / **`--autorun`（M12：只进托盘、不显示主界面）** / `--idle-threshold=` / `--heartbeat=` / `--flush-ms=` / `--probe-ms=`；**未知参数会作为警告显示**（避免拼错后静默退回默认路径）。
- **验收**：无参数启动后 `%LOCALAPPDATA%\ScreenSpy\data.db` 与 `logs\app-activity-*.jsonl` 均被创建；实测 `devenv` 归属并写进 SQLite；关闭窗口即 flush。

### 5.14 托盘与常驻形态（M5b ✅ 已实现）

- **交付**：`AppHost/TrayIconFactory.cs`（GDI+ 程序化两态图标，不新增二进制资源）+
  `AppHost/TrayIconHost.cs`（`NotifyIcon` + 右键菜单；**创建失败返回 `null` 而不抛异常**，由上层决定关闭策略）。
  M6 起 `TryCreate` 有**两个重载**：4 参（不带卡片，M5b 原样）与 6 参（带卡片显示状态与开关）；
  卡片项只在 6 参重载下出现，因此 M5b 当时的菜单形态与自检**不被改动**。
- **两个独立的暂停来源**（关键设计）：`ActivityScheduler.Paused`（M2 锁屏/睡眠，**会被周期探测重写**）与
  **`UserPaused`**（托盘「暂停统计」）；生效暂停 = 两者**或**。
  **绝不能共用同一字段** —— 否则用户的暂停会在 M2 下一次探测（默认 5s）时被静默清除。
  回归保护见 `M1SelfCheck` 的 6a–6d。
- **暂停语义**：仅**不计时**；心跳、前台采样、原始日志照常 → 日志中留下 `reason=paused` 段落，事后可追溯。
- **关闭不退出**：托盘可用时 `Closing` 取消并 `Hide()`；**托盘不可用时绝不隐藏**（否则会变成"看不见也关不掉"），
  回退为关闭即退出并弹一次警告。
- **退出路径**：托盘「退出」→ `Shutdown(0)` → `OnExit` 先收托盘、再 `Dispose` 运行时（刷日志与落库尾段）。
- **验收**：`--m5-selfcheck` **21 项全部通过**；实机 `EnumWindows` 证实关闭后主窗口 `visible=False` 而**进程存活**；
  隐藏期间 WAL 仍在增长（28872 → 37112 字节，M4 的 15s flush 照常）；
  UI 自动化在通知区域命中图标（tooltip 实时刷新今日时长）。详见 `docs/M5b-托盘与关闭不退出.md`。

## 7. 难点与风险

### 7.1 【最高风险】Win11 26H2 上桌面嵌入是否有效 —— ❌ 已定论：**不成立，改用 B+**

- `Progman/WorkerW/0x052C` 是**未公开 API**，微软无承诺；
- **26H2 刚发布，网上几乎不会有针对它的现成结论** → 已在**本机实测**（Windows 11 26H2 / build 26300.9457）；
- **最终结论（2026-10-05，详见 `docs/M0验证结论.md`、`docs/M0-B+验证.md`）**：
  1. `0x052C` **仍然有效**：注入后 `Progman` 多出一个全屏、可见的子 `WorkerW`（即壁纸层）；
  2. 26H2 的壁纸层是 **`Progman` 的全屏子 `WorkerW`**，
     而**不是**经典结构里"顶层、不含 `SHELLDLL_DefView` 的同级 `WorkerW`"（已据此改写 §5.8）；
  3. ❌ **真嵌入（路线 A）不成立**：`SetParent` 进 `Progman`/`WorkerW` 的**第三方子窗口不会上屏** ——
     `SetParent` 返回值、`GetAncestor`、`IsWindowVisible`、`UpdateLayeredWindow` **全部"成功"**，但**截屏像素为 0**。
     根因：`Progman` 带 `WS_EX_NOREDIRECTIONBITMAP`，由 **DirectComposition** 呈现，
     只有 shell 自己注册进合成树的子 HWND 才会被呈现；
  4. ✅ **改用路线 B+**：顶层分层窗口 + z 序自锁 + 显示桌面复位（见 §5.8），
     已实测满足"在桌面 / 会被窗口覆盖 / Win+D 不最小化"，另有鼠标穿透与任务栏/Alt+Tab 隐藏。路线 C（DirectComposition）决定不做；
  5. ⚠️ **方法学教训**：早期"路线 A 已通过"是**假阳性** —— 判据只校验了记账层（API 返回值），
     从未校验"像素是否真的上了屏"。**API 全绿 ≠ 画面有东西**。
- **以下四个坑是"真嵌入"尝试中踩到的（留档）**：
  - 判定嵌入是否成功**不能**用 `GetParent`——对仍带 `WS_POPUP` 的窗口它返回的是 owner（此时为 NULL），会误判为失败；
    应改用 `GetAncestor(hwnd, GA_PARENT)`（直接父窗口）与 `GetAncestor(hwnd, GA_ROOT)`（是否归入 `Progman` 树）；
  - `SetParent` **不会**自动把 `WS_POPUP` 改成 `WS_CHILD`（微软文档明示，为了兼容性），需显式 `SetWindowLong(GWL_STYLE)`；
  - 选择经典结构的顶层 `WorkerW` 时必须校验"**可见 + 覆盖全屏**"，否则会误选无关进程的 `WorkerW`；
  - `0x052C` 会**新增** `WorkerW`，实现时应**先查找、找不到才注入**。
- **剩余待人工确认项**：M0 的观感类清单现已由 B+ 的客观判定覆盖（见 §5.8 验收）；
  §7.4 的"伪嵌入"降级方案**已成为既定方案本身**（路线 B+）。

### 7.2 【高风险】半透明 vs SetParent 的冲突（✅ 已定稿对策）
- **问题**：若用 WPF，`AllowsTransparency=true` 依赖分层窗口，
  这类窗口作为子窗口挂到 WorkerW 上**可能失效或渲染异常**；
- **已定对策（依 §3 结论）**：小组件**不用 WPF/WinForms 的透明机制**，
  改为**手写 Win32 分层窗口**——用 `WS_EX_LAYERED` + `UpdateLayeredWindow` 实现逐像素半透明；
  该窗口是**顶层**窗口（B+ 方案），**不涉及 `SetParent`**，因此"子窗口 + 分层"的冲突在最终方案里根本不存在；
- **✅ 已由 M0 / M5a 实测确认**：26H2 上"顶层分层窗口 + 逐像素半透明"工作正常，
  且已满足"在桌面 / 会被窗口覆盖 / Win+D 不最小化"三项要求；
- **历史留档**：曾被担心的"分层子窗口 + 嵌入 WorkerW"组合**实际上没有机会被验证** ——
  因为真嵌入本身就不可行（第三方子窗口不上屏，见 §5.8 / §7.1）；
- **不理想时的兜底**：改用 `SetLayeredWindowAttributes`（整体透明度）替代逐像素透明。

### 7.3 【中风险】DPI 缩放 / 分辨率变化
- 125%/150% 缩放下坐标会偏移；
- 分辨率变化后绝对坐标可能跑出屏幕；
- **对策**：存相对锚点（Q2）+ 读取 `GetDpiForWindow` 做换算。

### 7.4 【已启用】路线 B+：伪嵌入（取代真嵌入）

- **本方案已成既定方案**（M0 定论：真嵌入不成立）：窗口设 `WS_EX_LAYERED | TRANSPARENT | NOACTIVATE | TOOLWINDOW`、
  压到 `HWND_BOTTOM`、加 **z 序自锁**、监听"显示桌面"并复位 z 序；
  视觉上等同桌面组件（会被其它窗口盖住 —— **这正是本项目想要的观感**）；
- 保持"纯展示、可自定义位置"体验不变；
- 实测记录见 `docs/M0-B+验证.md`、`docs/M5a-产品启动接入.md`。

### 7.5 其他
- ~~UWP 应用名识别（§5.5，可延后）~~ ✅ **M11 已实现**（两条路径 + 三条保守约束；见 §5.5）；
- 频繁写盘伤 SSD（已用批量 flush 缓解，§5.6）。

## 9. 测试要点

1. **空闲检测**：停手 5 分钟，验证不再计时；
2. **锁屏/睡眠**：锁屏、合盖 10 分钟，验证不计入；
3. **软件识别**：逐一使用若干软件各 1 分钟，核对时长与归属；
4. **UWP**：前台用计算器，验证显示为"计算器"；
5. **限额提醒**：设超短限额，验证只在阈值处弹一次；
6. **数据持久化**：重启 / 强杀进程，验证最多丢 15 秒；
7. **嵌入**：切换窗口、显示桌面、改壁纸，验证组件表现；
8. **位置**：编辑模式拖动 → 完成 → 重启，验证位置保持；
9. **DPI**：在 125% 缩放下重复位置测试；
10. **自启（M12）**：主界面勾选「登录时自动启动」→ 注册表 Run 键出现带引号的 `"…\ScreenSpy.exe" --autorun`；
    手动跑一次 `--autorun` 应**只出现托盘、不弹主界面**；取消勾选后该值消失；
    **注销再登录**验证托盘自动出现（自检验不到，需人工）。
11. **卡片（M6）**：无参数启动后卡片应出现在 (200,700)；可用鼠标拖动；会被其它窗口覆盖；
    托盘「隐藏卡片 / 显示卡片」往返生效；`--no-card` 启动则无卡片；重启产品后卡片上的“今日”不应掉回 0:00。
