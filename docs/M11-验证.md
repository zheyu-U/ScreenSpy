# M11 验证：UWP 应用真实名修正（§5.5）

> 日期：2026-10-06　|　环境：Windows 11 **26H2 / 26300.9457**、`.NET 10.0.12`、`net10.0-windows`
> 自检入口：`ScreenSpy.exe --m11-selfcheck [--dir=<目录>] [--log=<文件>]`
> 取证入口：`ScreenSpy.exe --diag-uwp`（纯诊断，不改任何东西）

---

## 1. 目标与决策

**目标**：UWP / 商店应用（"设置"、"计算器"等）原先**不论哪一个**都被统计成 `applicationframehost`，
用户无法对它们设单软件限额、也无法在榜单里区分它们。

**两项决策（由用户在动手前拍定）**：

| # | 决策 | 选择 | 备选与代价 |
|---|---|---|---|
| 1 | 真实名的**来源** | **子窗口进程名 + 扩展友好名表** | ① 再加"窗口标题"作显示名：标题更友好，但它**不参与键**，重启续算时拿不到标题 → 名字会从"标题"跳回"进程名"；要一致就得把检测到的名字写进 `app_meta`（= 系统替你设了一个"自定义名"）。② WinRT 包信息：最准最全，但要把 TFM 改成 `net10.0-windows10.0.19041.0`（工程配置变更 + 非打包应用下 WinRT 调用失败处理） |
| 2 | 旧 `app_name='applicationframehost'` 历史行 | **保留并改标注**（不迁移） | ② 迁移里删掉：界面不再出现这个 lump，但那部分时长永久消失。③ 保留且不改名字：零改动，但「待修正」在 M11 之后已不准确 |

## 2. ⚠️ 最重要的一件事：实测推翻了文档 §5.5 的技术方案

文档 §5.5 原文写的是：

> 若前台进程名是 `ApplicationFrameHost`，则**枚举其子窗口**，找到真正承载应用的子窗口……

**这句话在 Windows 11 26H2 上不成立。** 用新加的 `--diag-uwp` 实地勘察，得到的是：

```
【1】顶层窗口中类名含 CoreWindow 的
  · hwnd=0x40374 pid=9332  proc=SystemSettings  class=Windows.UI.Core.CoreWindow  title="设置"  POPUP visible=是
  · hwnd=0x40464 pid=17220 proc=TextInputHost   class=Windows.UI.Core.CoreWindow  title="Windows 输入体验" POPUP visible=是
  · （另有 explorer / ShellHost 的 "DesktopWindowXamlSource"，均为不可见的 CHILD）

【2】ApplicationFrameWindow（共 3 个）及其全部后代
  ● hwnd=0x30654 pid=17920 proc=ApplicationFrameHost class=ApplicationFrameWindow title="设置"
      └ ApplicationFrameTitleBarWindow     (pid=17920 = 宿主自己)
      └ ApplicationFrameTitleBarWindow     (pid=17920 = 宿主自己)
      └ ApplicationFrameInputSinkWindow    (pid=17920 = 宿主自己)
      → 后代共 3 个，**没有 CoreWindow**

【3】parent 或 root owner 指向宿主窗口的顶层窗口
  · 只有 IME 窗口（不可见）
  → **应用本体与宿主之间没有父子 / owner 关系**
```

结论：

- 应用本体是一个**独立的顶层窗口**（类名仍是 `Windows.UI.Core.CoreWindow`，属于**真实应用进程** `SystemSettings.exe`）；
- 它**不是**宿主的子窗口，也不被宿主 owner；
- 因此"枚举子窗口找 CoreWindow"这条路在 26H2 上**永远找不到任何东西**。

> **这意味着**：只按教科书写，代码会**编译通过、自检通过（如果自检也只按教科书构造假数据）、实际永远认不出任何 UWP 应用**，
> 且**不报任何错**。这是本项目一路在防的那类缺陷的又一例 —— 只不过这次骗的是"我们自己写的验证"。

## 4. 关键设计

### 4.1 两条解析路径（先 1 后 2）

```
宿主 ApplicationFrameWindow (ApplicationFrameHost.exe)
  │
  ├─ 路径 1：EnumChildWindows → 类名含 CoreWindow 且 pid ≠ 宿主的子窗口   （Windows 10 / 部分构建）
  │
  └─ 路径 2：EnumWindows → 可见、类名含 CoreWindow、pid ≠ 宿主、**标题 == 宿主标题**的顶层窗口  （26H2 实测形态）
```

### 4.2 三条保守约束（宁可认不出，不可认错）

1. **宿主标题为空 ⇒ 不做配对**（空标题的窗口太多，配上必是错的）；
2. 候选必须**可见**、`pid ≠ 宿主`、进程名非空，且不是已知的"非应用"宿主
   （`TextInputHost` / `ShellHost` / `explorer` / `dwm` / `csrss` / `ApplicationFrameHost`）；
3. 配对上的候选必须**恰好一个** —— **0 个或 ≥2 个都判"未识别"**。

识别失败时**退回宿主 lump**（键 `applicationframehost`），**绝不猜名字**。

### 4.3 标题只用于"配对"，不参与"身份"

| | 用途 | 说明 |
|---|---|---|
| 标题 | **配对**：哪个应用窗口属于这个宿主 | 不落库、不参与键；因此不影响重启后的名字 |
| 进程名 | **身份**：键 = 进程名小写 | 与桌面软件**同一命名空间、同一张友好名表**（UWP 与桌面软件平权） |
| 展示名 | **由键推出**（`NormalizeDisplayName(key)`） | 与重启续算走的 `AppNamingRules.EffectiveName(identity, key)` **逐字一致** |

> 为什么坚持"展示名由键推出"：若用进程名原始大小写，采样时显示 `FooBar`、重启续算后显示 `foobar`，**名字会跳变**。
> 这正是教训 16/20（展示口径与持久化口径必须同源）的又一次应用。

### 4.4 `Kind` 仍是 `UwpHost`

识别成功**不改变分类**：`Kind = UwpHost` 表示"这一拍来自 UWP 宿主"（诊断与 UWP 计数用），
而不再表示"名字未知"。因此 `CountsAsApp`、守恒等式、`UwpTicks` 计数全部原样不变。

### 4.5 旧数据：不迁移，共用同一个名字

- **schema 仍为 v3**（不新增迁移）；
- 旧的 `app_name='applicationframehost'` 行**保留**；
- 它与"当前识别失败"**共用同一个显示名**「UWP 应用（未能识别/旧合并）」——
  因为**同一个键只能有一个名字**（否则界面会出现两个名字指着同一份数据）。

### 5.1 真实观测（本机，2026-10-06）


## 7. 已知局限

1. **标题不一致就认不出**：若应用本体窗口的标题与宿主不同（或为空），路径 2 不成立 → 退回宿主 lump（保守）。
   这类情形会在**诊断计数** `UwpUnresolvedSamples` 上体现，可通过 `--diag-uwp` 复核。
2. **同名多窗口不猜**：若同时存在两个标题相同的可见 CoreWindow（理论上罕见），判为未识别（约束 3）。
3. **原始日志仍记宿主名**：JSONL 记录的是 `ApplicationFrameHost`（原始证据层不改），
   真实应用名体现在**聚合数据的键**上。若将来需要，可在日志里加一列（本轮刻意不做，避免动 M3 已冻结的日志格式）。
4. **未收录的 UWP 应用会显示进程名**（如 `microsoft.windowsstore`），可用 M9-1b「重命名」自定义。
5. **`applicationframehost` 键的旧行**与"当前识别失败"共用同一显示名（理由见 §4.5）。
6. **WPF 界面层不在自检覆盖内**：本轮未改动界面。

## 9. 结论

- **构建**：0 错误 0 警告；
- **`--m11-selfcheck`**：**52 项全部通过**（A 38 / B 9 / C 5），且**两次连跑结果一致**；
- **M1–M10 全量回归**：全部 exit 0；
- **两轮变异测试**：均恰好命中（1 项 / 1 项）；
- **真实世界验证**：本机"设置"应用被正确识别为 `systemsettings / 设置`，且**端到端断言**通过。

**一句话**：M11 的价值不只在"终于认得出 UWP 应用"，更在于**它证明了文档里的技术方案是错的** ——
并且把"怎么发现这件事"（`--diag-uwp`）与"怎么防止它再错"（真实端到端断言 + 变异测试）一起留在了工程里。
