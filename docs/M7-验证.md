## 1. 目标与用户口径（已确认的决策）

用户在 M7 开工前把范围改成了「M7 + M8 合并」，并明确了四条：

| # | 用户原话（要点） | 落地结果 |
|---|---|---|
| 1 | 卡片可以做成**可调**的，既能「嵌入」，也能像现在（M6）这样 | **单个 `CardWindow` 双形态**，运行时切换；默认**嵌入** |
| 2 | 持久可切换，默认嵌入 | `widget_mode` 落库；主界面「切换为浮动窗口 / 切换为嵌入桌面层」 |
| 3 | 主页面可调整位置（临时进入） | 主界面「调整位置 / 完成调整」+ 托盘「调整组件位置」（**同一个动作**） |

| 5 | 可以做成一个窗口 | **单 HWND、单 STA 线程、共用一份坐标** |

> 第 5 + 6 条决定了整个实现：**不做两个窗口**，而是「同一个窗口的两种参数组合」。

## 3. 关键设计

### 3.1 为什么是“一个窗口两种形态”

做成两个窗口（沿用 `DesktopCardHost` + `CardWindow`）会有三笔债：
位置要同步、切换要销毁重建（闪断 + 空档）、两条释放路径与两套自检。
合一个窗口之后，位置**字面上就是同一个字段**（`_x/_y`），切换不跳位，
生命周期只有一条，也不会出现“一种形态修了、另一种没修”。

### 3.2 跨线程切换：`WM_APP`

改窗口样式、启停 z 序管理器（`SetWinEventHook`）、`MoveZOrder` **都必须在卡片自己的线程上做**。
因此上层只 `PostMessage(WM_APP)`，窗口线程收到后执行 `ApplyMode`；
需要同步结果的调用方（自检、界面按钮）用一个 `ManualResetEventSlim` 等待，**带超时**（3s），绝不无限等。

### 3.3 切换的确切顺序（不可交换）

```
→ 嵌入：先把窗口当前坐标读回（两形态共用同一份）
        → 开自锁 + 切穿透样式（SetInteraction，带 SWP_FRAMECHANGED）
        → 启动 z 序管理器并立刻 Poll(force)（让 z 序马上归位）
        → 采样加密到 250ms
→ 浮动：先停 z 序管理器并释放自锁（否则拖动会被自锁顶着）
        → 切可交互样式 → MoveZOrder(HWND_TOP) → 采样放宽到 1000ms
```

两条路径最后都**立刻重画一帧**，避免切换瞬间留着“旧样式下的旧内容”。

### 3.4 「常态形态」与「调整中」是两件事（三个概念，不是两个）

- `_restingMode` = 用户选定的常态（持久）；`_mode` = 此刻真实形态；`_adjusting` = 是否处于**临时**调整会话。
- 早先的写法在进入调整时把常态改写成“进来之前的形态” —— 那样用户选了浮动常态后，
  一旦进入过调整，常态就被悄悄改回嵌入（**一个不报错的错**）。现在 `BeginAdjust` **不动常态**，
  `EndAdjust` 回到 `RestingMode`。这条有专门回归。

**第二轮修正**：第一版把「调整中」写成 `IsAdjusting => Mode == Floating`。这对**常态就是浮动**的
用户是错的 —— 他们的 `Mode` 永远是浮动，于是：

- 「调整位置」按钮永远显示“完成调整”（其实没在调整）；
- 而“调整中要禁用的另一个按钮”（形态切换）会被**永久禁用** → **用户再也切不回嵌入**。

因此 `IsAdjusting` 现在读独立的 `_adjusting` 标志，并额外提供 `CanAdjust`
（= 常态不是浮动，即“调整位置”是否有意义）。两条不变量：

| 不变量 | 含义 |
|---|---|
| `IsAdjusting == true` ⇒ `Mode == Floating` | 调整中必然是浮动的（反之**不**成立） |
| 切回嵌入（无论是否经过 `EndAdjust`）⇒ `_adjusting` 归零 | 标志不会卡在“调整中”，否则形态按钮会被永久禁用 |

### 3.5 位置怎么记

| 场景 | 何时落库 |
|---|---|
| 点「完成调整」 | 读 `GetWindowRect`（**真实坐标**，不是“我们以为的位置”）→ 上报 → 回常态 |
| 浮动**常态**下直接拖 | 每拍（1s）比对实际坐标，变了就上报 —— 拖动是**系统代劳**的，没有我们参与的消息可听 |

回调可能来自**卡片线程**：`SqliteStore` 每次操作都是短连接，因此线程安全。

### 3.6 读出后夹回屏幕内

坐标是上一次会话存的，中间可能换过分辨率、拔过显示器。
直接照搬会让卡片落在屏幕外 —— 那就等于**卡片消失了，而且屏幕上没有任何提示**。
因此 `ClampToScreen` 保证左上角落在屏内；屏幕尺寸未知（0×0）时**不夹取**（不许把好坐标改成 0,0）。

### 3.7 两个按钮互斥（第二轮）

| 状态 | 「调整位置」 | 「切换形态」 | 为什么 |
|---|---|---|---|
| 常态嵌入、未调整 | 可用（「调整位置」） | 可用（「切换为浮动窗口」） | 两条路都通 |
| **调整中** | 可用（「完成调整」） | **禁用** | 见下 |
| **常态浮动** | **禁用** | 可用（「切换为嵌入桌面层」） | 卡片本来就可拖、每拍自动记位置，“调整”无事可做 |

「调整中禁用形态按钮」堵住的是**一个真实的偏差**：形态按钮走的是“改常态”那条路，
**不经过** `EndAdjust` 的“先取当前坐标再上报”，于是最后一次拖动可能还没写进库
（最多约 1 秒的静默偏差）；而且常态为嵌入时，在调整中点它还会把**临时**的浮动变成**永久**常态。

禁用规则做成了一个**纯函数**（`MainWindow.ComposePositionControlAvailability`），
因此可以确定性断言 —— 自检不需要真的把 WPF 窗口显示出来，也不靠肉眼看按钮灰不灰。

**顺带修掉的口径不一致**：形态按钮此前读的是**当前形态**（`Mode`）而不是**常态**（`RestingMode`）。
调整中当前形态是浮动，于是形态按钮会显示「切换为嵌入桌面层」——
两个按钮同时“指向嵌入”，把两者的分工搅在一起。现在它只表述常态。

**兜底**：主界面按钮禁用了，但 `App.ToggleCardMode` 这条路仍可能被别的入口调到，
所以它**开头先 `EndAdjust()`**（把当前坐标上报上去）再改常态 —— 双重保险，
且这条也有自检断言（调整中切常态后，库里的坐标必须是**拖动后**的位置）。

## 4. 过程中发现并修掉的问题

### 4.1 窗口类名被多个实例复用（**既有隐患，M7 才踩到**）

`NativeWindowHost` 用静态 `HashSet` 去重窗口类名，而 `lpfnWndProc` 是**实例方法指针**：
类一旦注册，**类过程就与那一个实例绑死了**。于是同名类的第二个实例，其所有消息都会走到
**第一个实例**的 WndProc 上 —— 第二个窗口的 `OnTick`、命中测试、z 序自锁**全部静默失效**
（不报错，只是不工作）。单卡片的产品形态看不出来，但 M7 会**反复创建 z 序探针**，必然踩到。

修法：注册名带实例序号（`ScreenSpyCard#3`），每实例独占一个类名。
这条直接决定了 M7 的自检能不能被信任 —— 否则“反复切换 3 轮”那一项测的其实不是被测对象。

### 4.2 第一版键名断言是**同义反复**（变异测试当场揭穿）

`--m7-selfcheck` 的第一版这样断言键名：

```csharp
store.GetSetting(WidgetPlacementStore.KeyX) == "321"   // ← 与写入共用同一个常量
```

把 `KeyX` 改成 `"widget_pos_x_typo"` 后**全部通过** —— 因为断言与写入一起改了。
这正是本项目最忌讳的“测试自己证明自己”。改成**字面量**之后再变异，
恰好命中 2 项 FAIL（键名 + 非法值回退）。键名是**与既有数据库的兼容契约**，值得钉死。

### 4.3 「调整中」的判定把它与「当前形态」混为一谈（第二轮，**实现缺陷**）

第一版：`IsAdjusting => Mode == Floating`。对**常态就是浮动**的用户，`Mode` 永远是浮动，
于是这类用户被判成“永远在调整中”：

- 「调整位置」永远显示“完成调整”（其实没在调整）；
- 若按用户要求“调整中禁用另一个按钮”，那个形态按钮会被**永久禁用** ——
  **用户再也切不回嵌入**，而且不报任何错。

修法：`IsAdjusting` 改读独立的 `_adjusting` 标志（只在 `BeginAdjust` 真的切成功后置位、
`EndAdjust` 与“切回嵌入”时归零），并新增 `CanAdjust`。见 §3.4。

> 这条值得记：它是**“把两个不同概念塞进同一个表达式”**的典型后果 —— 表达式在多数情况下
> 恰好“看起来对”（常态嵌入时确实等价），只在一种用户配置下错，且错了不报错、只是把用户困住。

## 6. 已知局限（**本自检覆盖不到**，需人眼或后续里程碑）

1. **`SWP_FRAMECHANGED` 的必要性无法在进程内断言**：命中测试是我们自己的 `WndProc` 应答的，
   样式位也已被 `SetWindowLong` 改掉 —— 所以“少写 FRAMECHANGED”这种错，自检看不见。
   **必须靠人眼**：嵌入形态下点桌面图标是否穿透、浮动形态下能否真的拖动窗口（见 §7）。
2. **“别的窗口把卡片盖住”只是 z 序层面的客观判据**（有窗口在它之上、非 topmost），
   没做“打开一个窗口后截屏看像素”的端到端判定（`--demo-card` 的截屏判定覆盖的是可见性那一半）。
3. **锁屏后的 z 序行为**未在 M7 复测（沿用 M0 结论；M0 那次是 Win+D 场景，实测通过）。
4. **相对锚点 / 分辨率与缩放变化时的换算**未做（属 M8 余项）。当前兜底是夹回屏内。
5. **卡片尺寸 / 不透明度 / 字号 / 配色**不可调（本轮只做位置与形态）。
6. 浮动态下拖动是**每 1 秒**才被检测到并落库：拖完立刻点「完成调整」也不会丢（那条路径直接读坐标），
   但“只拖不按任何按钮、且在 1 秒内直接杀进程”会丢掉这一次移动（最多 1 秒的位置变化，非时长数据）。
7. 托盘「设置」仍为禁用占位（M9）。
8. **按钮“禁用”只断言到纯函数那一层**：D 组验的是 `ComposePositionControlAvailability` 的规则，
   **不验** `UpdatePositionControls` 有没有把它真的赋到 `Button.IsEnabled` 上（那需要真的把 WPF
   窗口显示出来，自检刻意不做这一层）。因此§7 清单里保留了“看着按钮是不是灰的”这一步。
   同理，“禁用项点不动”验的是真实菜单对象，而主界面那两个按钮的点击路径没被自检覆盖。

## 9. 结论

M7 把「桌面嵌入」与「位置自定义」一次做完，并且**用同一个窗口**完成 ——
嵌入形态是 M0 验证过的 B+（**会被别的窗口盖住**、鼠标穿透、Win+D 不最小化），
浮动形态就是 M6 当年那个可交互普通窗口，两者**共用一份坐标**、可随时切换且持久。

第二轮把两个入口的**分工**钉死（这是用户直接问到的点）：

- **底层是同一个机制** —— 两个按钮最终都走 `CardWindow.SwitchMode(mode)`（`WM_APP` → 卡片线程 → `ApplyMode`），
  只有一份切换实现、一份坐标；
- **上层是两个不同动作** —— 「调整位置」是**临时插曲**（不动常态、结束时存坐标再回常态）；
  「切换形态」是**改常态本身**（只有切换真的成功才写库）；
- **两者不得同时可用** —— 调整中禁用形态按钮（否则会绕过坐标上报，最多 1 秒静默偏差，
  且会把临时浮动变成永久常态）；常态为浮动时禁用「调整位置」（无事可做）。

代码层证据：**78 项自检 + 四轮变异测试**（其中一轮揭穿了自检自身的同义反复，已修正；
两轮为第二轮新增规则的守门员）；回归 6 项全绿；构建 0 错 0 警。
屏幕层证据：见 §7，**需人工走一遍**（`SWP_FRAMECHANGED` 的有效性、按钮真实灰不灰，都无法在进程内断言）。

### 9.1 一条方法上的收获

第二轮的两个缺陷（§4.3 的 `IsAdjusting`、以及形态按钮读当前形态而不是常态）都是**同一类**：
**把一个“看起来常常成立”的表达式当成了定义**（`调整中 == 当前是浮动`）。
它在最常见的那条路径上恰好等价，只在一种用户配置下错，而且不报错、只是让人困惑或把人困住。
项目里已经沉淀过同类教训（见 `阶段总结.md` §8 的教训清单），这条可以并入其中：
**当两个概念只在“常见情况”下重合时，必须各记一份状态，而不是用一个表达式去推另一个。**
