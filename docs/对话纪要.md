## 3. 语言与框架选型（已确定）

### 3.1 最终结论

| 层 | 选型 | 说明 |
|----|------|------|
| **语言** | **C# / .NET 10** | 调用 Win32 API 最顺手；生态成熟；常驻后台开销低；可打包成自包含 exe |
| **桌面小组件（嵌入层）** | **手写 Win32 分层子窗口 + GDI+ 渲染 + `UpdateLayeredWindow`** | 为实现"逐像素半透明卡片"，无论用哪个框架大概率都要回到这条路，故直接手写更可控 |
| **管理主界面（不嵌入）** | **WPF**（已确定，2026-10-05） | 普通窗口，不涉及嵌入，用现成框架即可；WPF 排版/绑定/图表更强，且与既有 `ScreenSpy` 工程（`UseWPF=true`）一致 |
| **数据库** | SQLite（`Microsoft.Data.Sqlite`） | 单文件、免安装、够用 |
| **托盘** | `System.Windows.Forms.NotifyIcon` | 标准做法 |
| **系统事件** | `Microsoft.Win32.SystemEvents` | 锁屏 / 电源事件现成 |

### 3.2 关键理由：为什么小组件不直接用 WPF

- "半透明深色卡片 + 白色清晰文字"本质需要**逐像素透明度**，Windows 里只有 **`UpdateLayeredWindow`（配合 `WS_EX_LAYERED`）** 能真正实现；
- WPF 的 `AllowsTransparency=true` 与 WinForms 的透明机制**本质都是"顶层窗口专用"**，一旦 `SetParent` 挂到 WorkerW 变子窗口，透明极易失效或渲染异常（即 §7.2 的冲突）；
- 因此小组件**不套现成框架**，改为极简手写窗口（只干"画卡片"一件事），更短、更稳、更可控。

### 3.3 被否决的选项

| 选项 | 否决理由 |
|------|----------|
| Python (PySide + pywin32) | 写 P/Invoke（尤其 `UpdateLayeredWindow` 传结构体指针）痛苦；常驻守护 + 打包 exe 体积大、启动慢 |
| Electron / Tauri | 运行时几百 MB；把网页内容嵌进 WorkerW 最后还是得穿回原生层调 Win32，绕远且更重 |

### 3.4 待最终敲定项

- ✅ **管理主界面：已定为 WPF**（2026-10-05）；
- ⏳ **小组件渲染用 GDI+ 还是 Direct2D/DirectWrite** —— M0 已实测 GDI+ 可用；追求更锐利再上 D2D。

## 4. 开发环境（已确定）

| 项 | 结论 |
|----|------|
| **IDE** | **Visual Studio 2026** |
| **SDK** | .NET 10 SDK（是 SDK，非 Runtime，编译需要） |
| **目标系统** | Windows 11 26H2（实测 WorkerW 的前提） |
| **VS 工作负载** | ".NET 桌面开发"（同时含 WPF、WinForms、C# 编译器） |

### 4.1 选择 Visual Studio（而非 VS Code）的理由

| 维度 | Visual Studio | VS Code |
|------|---------------|---------|
| WPF / WinForms 可视化设计器 | ✅ 有 | ❌ 无 |
| 编辑并继续（运行时改代码不重启） | ✅ 有 | ❌ 无 |
| 调试器强度 | 强（并行堆栈、监视、句柄排查友好） | 中等（依赖 C# Dev Kit） |
| 性能 / 诊断工具（CPU、内存、句柄快照） | ✅ 内置 | ❌ 基本没有 |

**核心理由**：本项目越"贴着 Windows 底层"，VS 的两个杀手锏（**编辑并继续** + **强诊断**）越值钱。由于小组件是常驻进程、**每次重启都要重新嵌入桌面**，VS Code 省下的体积/启动时间在这个场景换不回来。
